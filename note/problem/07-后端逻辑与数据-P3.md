# P3 后端内部逻辑与数据问题（11 项）

第三轮后端内部审计发现。事务"同事务+emit 后置"主模式、SM-2/贪心排期/BFS 算法、
FK 删除顺序、LIMIT/OFFSET、锁序（无死锁组合）均验证通过，未列入。

## 1. agent/方案/讲义的 cancel UPDATE 无状态守卫，终态竞态窗口把 done/failed 行改回 'cancelling' 且无人翻转
- 证据：`agent/mod.rs:899-903`、`learning/mod.rs:820-831`、`learning/lecture.rs:737-744`——无条件 UPDATE 置 cancelling；对比有守卫的 `practice/mod.rs:1310-1315`、`knowledge/mod.rs:684-693`（WHERE status='running' + changed==0 报错）。
- 影响：worker 完成 commit 与摘除 active 标志之间的毫秒级窗口内点取消，终态被覆盖，此后该会话 send 永远报 `run_active`、plan resume 报 `plan_active`，直到重启 recover 才解锁。[是否接受该竞态待确认]
- 传递链条：触发（用户在 Agent/方案/讲义任务即将完成的瞬间点"取消"）→ 根因（`agent/mod.rs:900-903`、`learning/mod.rs:822-825`、`learning/lecture.rs:747` UPDATE 无 `AND status='running'` 守卫，与 `practice/mod.rs:1310`、`knowledge/mod.rs:684` 的守卫写法不同）→ 传导（worker 终态已 commit 但 active 标志未摘除，取消通过 `agent/mod.rs:890-897` 的存在性检查，把 done/failed 行改回 'cancelling'，worker 已退出无人再翻转）→ 症状（行停留 cancelling，后续 send/resume 因状态不符报 `run_active`（`agent/mod.rs:944`）/`plan_active`（`learning/mod.rs:464`），直到重启 recover）。
- 影响范围：功能面：Agent 会话 send/resume、方案 resume、讲义取消三条命令及 agent_runs/learning_plans/learning_lectures 表；触发条件：需在任务收尾毫秒级窗口内点击取消，正常使用偶发、无法稳定复现；受损面：可用性——会话/方案被 cancelling 卡死至重启，无数据损坏、不重复计费。

## 2. `agent_tool_calls` 注册行可永久停留 'running'
- 证据：`agent/tools.rs:415-418`（INSERT 'running'）→ `:461-467`（参数校验失败直接 return，未走结果回写）→ 行停留 running；`agent/mod.rs:1011-1052` recover 不覆盖该表。
- 影响：同 id 重放命中 `tool_active` 拒绝执行；数据库累积僵尸 running 行（恢复路径因换新请求 id 通常可绕过）。
- 传递链条：触发（模型返回的 tool call 参数不是合法 JSON 对象，或进程在登记后、执行前中断）→ 根因（`agent/tools.rs:415-418` 先 INSERT status='running' 登记行，`:461-467` 参数校验失败直接 return，不走结果回写）→ 传导（行停留 running；`agent/mod.rs:1011-1052` recover 仅处理 agent_runs，不触及 agent_tool_calls）→ 症状（同 id 重放走 `:419-459` 匹配分支命中 `tool_active`（`:451-454`），僵尸行在库中累积）。
- 影响范围：功能面：Agent 工具执行与 agent_tool_calls 表的同 id 重放路径；触发条件：仅当模型产出畸形参数或执行中崩溃，正常参数不命中，恢复路径换新请求 id 可绕过；受损面：可用性——个别工具调用被拒执行，已存数据不受损。

## 3. share_index（根库）与 shared_plans（工作库）写入不在同一事务，reset 失败路径无补偿
- 证据：`sharing/mod.rs:299-317`（create 有补偿删除）；`store.rs:602-606`（reset 在主事务 commit 前清根库索引，事务失败则索引已清而 shared_plans 仍在，无补偿；reindex 仅由备份导入触发）。
- 影响：reset 失败后跨用户分享令牌查找失效，直到下次备份导入。
- 传递链条：触发（多用户环境下执行重置应用，且重置主事务随后提交失败）→ 根因（`store.rs:602-606` 在主事务 commit 前经 `sharing::clear_index` 清根库 share_index（独立连接、即时生效），与 `sharing/mod.rs:310-316` create 失败时的补偿删除不对称）→ 传导（主事务回滚，shared_plans 行回滚仍在工作库，根库索引已空）→ 症状（跨用户令牌查找走根库落空，分享链接失效；reindex 仅由备份导入触发（`backup/mod.rs:38`），此前无法自愈）。
- 影响范围：功能面：reset 命令、根库 share_index 表与跨用户分享令牌查找；触发条件：多用户（owner_id 存在）+ reset 事务提交失败（罕见；单用户走 `store.rs:605` 同事务删除不受影响）；受损面：可用性——已分享方案在下次备份导入前无法凭令牌访问，数据未丢。

## 4. `adopt_recommendations` 先提交任务再启动专注，start_focus 失败时任务已写入
- 证据：`reports/mod.rs:967-978`——replace_collection 提交任务后 start_focus 失败即整体报错不回滚；预检查（:961-966）与 start_focus 间也有竞态。
- 影响：采纳"记录一次专注"类建议失败时任务已加入清单但用户收到报错。
- 传递链条：触发（用户采纳"记录一次专注"类建议时已另有专注进行中，或 start_focus 内部失败）→ 根因（`reports/mod.rs:967-969` 先 replace_collection 提交任务清单，`:974-975` 再 start_focus，失败经 `?` 整体返回、无回滚）→ 传导（任务已写入 tasks 集合并 emit 事件；`:961-966` 预检查与 start_focus 之间另一专注启动同样命中）→ 症状（用户收到 focus_active 等报错，但建议对应任务已出现在清单，报错与实际效果不一致）。
- 影响范围：功能面：报告页 adopt_recommendations 命令与 tasks 集合；触发条件：默认配置即可命中——采纳含专注的建议时已有专注在进行或启动失败；受损面：数据一致性——提示与落库结果不符，用户可能重复采纳产生重复任务。

## 5. 文档 §12 自相矛盾且实现分裂：cancelling 重启翻转目标不一致
- 证据：`docs/architecture/02-operation-principles.md` §12 mermaid（cancelling→interrupted）与文字（cancelling→cancelled）矛盾；实现中 7 个域 cancelling→cancelled，而 `sync/mod.rs:799-816` 与 `providers/routing.rs:1265-1310` 落 interrupted。
- 影响：重启后已取消的同步/路由任务显示"已中断"，与多数域语义不符；验收对照状态机产生歧义。
- 传递链条：触发（用户在同步/路由任务处于 cancelling 时重启应用）→ 根因（文档 §12 mermaid（`02-operation-principles.md:512`）cancelling→interrupted 与通用规律文字（`:542`）cancelling→cancelled 自相矛盾）→ 传导（实现分裂：多数域如 `agent/mod.rs:1023-1028` 翻 cancelled，而 `sync/mod.rs:810` 对 running/cancelling 一律置 interrupted、`providers/routing.rs:1281-1289` 上游仍 running 或无记录时置 interrupted）→ 症状（重启后已取消的同步/路由任务显示"已中断"，与方案/Agent 等域"已取消"语义不一致）。
- 影响范围：功能面：sync_jobs 与 provider_route_runs 两表的重启恢复及状态展示、验收对照矩阵；触发条件：取消后未及完成即重启（cancelling 状态跨重启）即命中；受损面：视觉/语义——状态标签与用户预期不符，无数据损坏。

## 6. materials 是唯一自动重跑的域，与"重启=永不自动重跑"总则相反
- 证据：`materials/mod.rs:1073-1102`——recover 把 queued/parsing 重置 queued 后直接重新解析。
- 影响：本地解析幂等、风险低；属未声明的行为差异。
- 传递链条：触发（用户重启应用时恰有 queued/parsing 状态的资料解析任务）→ 根因（`materials/mod.rs:1103-1104` recover 对未取消任务 transition 回 queued 后立即 spawn_job 重新解析，与"重启=永不自动重跑"总则相反）→ 传导（解析器对同一原件重新提取文本，幂等覆盖 materials/material_jobs 记录）→ 症状（重启后解析自动继续且无"已中断"标记，用户未显式 resume）。
- 影响范围：功能面：materials 域 recover 与资料解析队列；触发条件：重启时存在未完成解析任务即命中（默认行为，无配置开关）；受损面：低——本地解析幂等、不产生费用，仅行为与文档总则不一致。

## 7. 强度缩放基数可被 update_goal 破坏
- 证据：`planning/mod.rs:271-274`（scaled 按"当前强度→目标强度"比例，隐含排期已按当前强度缩放）vs `:461`（update_goal 直接覆写 daily_minutes 不乘强度因子），此后 regenerate 按未缩放基数重建。
- 影响：goal 更新+重生成后再切强度，排期按错误基数缩放（防累积缩放本身验证成立）。
- 传递链条：触发（用户在"调整学习目标"改每周投入并重生成，之后再切换强度）→ 根因（`planning/mod.rs:271-274` scaled 按 factor(target)/factor(current) 缩放，隐含现有分钟数已含当前强度因子；`:461` update_goal 用 weekly_hours×60/7 直接覆写 daily_minutes，不乘强度因子）→ 传导（regenerate 按未缩放基数重建排期，事件分钟数失去"基数×当前因子"前提）→ 症状（再切强度时按错误基数缩放，每日任务分钟系统性偏大或偏小）。
- 影响范围：功能面：update_goal、regenerate 与切强度（alternatives/changeIntensity）命令及排期分钟数；触发条件：需"goal 更新+重生成后再切强度"操作序列，全新安装默认流程不命中；受损面：数据正确性——排期时长失真，费用与已有记录不受影响。

## 8. notes 'updated' 字段混用本地偏移与 UTC 两种格式
- 证据：`notes/mod.rs:214-216`（导入用 now_local 带 +08:00）vs `learning/knowledge.rs:321`（批注用 UTC）。
- 影响：同一字段两种偏移表示；当前无 SQL 排序依赖，属格式统一性隐患。
- 传递链条：触发（用户先导入笔记文件、又在自习室保存学习批注）→ 根因（`notes/mod.rs:214-216` 导入用 now_local 格式化，东八区产出 +08:00 偏移；`learning/knowledge.rs:321` 批注用 learning::now()（`learning/mod.rs:110` now_utc）产出 Z 后缀）→ 传导（两种 RFC3339 字符串写入同一 notes 集合的 "updated" 字段，无归一化）→ 症状（同字段混用本地偏移与 UTC 表示，当前展示无即时错序）。
- 影响范围：功能面：notes 集合 updated 字段的两个写入口（笔记导入与学习批注）；触发条件：默认配置即命中，两类操作并存时必然出现；受损面：格式统一性隐患——现无 SQL 排序依赖，未来按字符串排序/比较会错序。

## 9. 报告趋势图日标签用 UTC 日期，窗口边界却是本地午夜
- 证据：`reports/mod.rs:642-643`（本地午夜转 UTC）vs `:679-681`（按 UTC 日期字符串分组标签）。
- 影响：本地 0–8 点产生的证据记入前一天曲线点，横轴与窗口边界口径不一致。
- 传递链条：触发（东八区用户在本地 0–8 点产生练习/复习证据后查看学习报告趋势）→ 根因（`reports/mod.rs:642-643` 窗口边界由 `period_bounds`（`:431-436`）本地午夜转 UTC；`:679-681` 分组标签用 `day(date)`（`:222-224` 取 value.date()），created_at 为 UTC 字符串故得 UTC 日期）→ 传导（本地 00:00–08:00 的证据 UTC 时刻属前一 UTC 日，被归入前一天 trend 组）→ 症状（趋势图横轴日期与窗口边界口径不一致，凌晨证据画到前一天的曲线点）。
- 影响范围：功能面：学习报告 learning_report 的趋势分组（evidence 明细查询）；触发条件：东八区默认环境下凌晨学习即命中；受损面：数据正确性（轻）——曲线点归属日偏移一天，窗口总量统计不变。

## 10. practice detail 逐题 N+1 查询
- 证据：`practice/mod.rs:972-976`（每题一次 bookmark EXISTS）、`:1005-1011`（hints 模式每答案一次 hint 查询）；detail 在每次提交返回与每次 practice.* 事件刷新时执行。
- 影响：20 题集合每次刷新 20–40 次额外查询，主线程模型下放大为可感卡顿。
- 传递链条：触发（用户打开 20 题练习详情，或作答期间 practice.* 事件驱动刷新）→ 根因（`practice/mod.rs:972-976` 在题目查询闭包内逐题 SELECT EXISTS(practice_bookmarks)；`:1005-1011` hints 模式每条答案再单查一次 hint）→ 传导（detail（get_practice_set）在每次提交返回与每个 practice.* 事件触发的前端 refresh（`Practice.tsx:57`）时整段重跑，N+1 随题量放大）→ 症状（20 题集合每次刷新多出 20–40 次查询，主线程同步执行放大为可感卡顿）。
- 影响范围：功能面：get_practice_set 命令、practice_bookmarks/practice_questions 读取与练习页事件刷新链路；触发条件：默认配置即命中，题量越大、事件越密集越明显；受损面：可用性——响应延迟增加，无数据损坏。

## 11. [待确认] 约 40 处 BEGIN DEFERRED 事务先读后写，与流式 delta 自动提交并发可触发 BUSY_SNAPSHOT——03#6 database_busy 的后端根因
- 证据：`store.rs:498-505`（replace_collection 事务内先 SELECT 后 INSERT）等约 40 处 `unchecked_transaction`；并发写源 `providers/mod.rs:1107-1115` 每条 chat_delta 自动提交写 events；WAL 下 DEFERRED 升级写锁遇 BUSY_SNAPSHOT 不经 busy_timeout 重试。
- 影响：流式任务进行中用户并发保存偶发 database_busy 直接失败；发生率需压测确认。
- 传递链条：触发（真实供应商流式任务输出 delta 期间，用户并发执行保存等写操作）→ 根因（`providers/mod.rs:1107-1115` 每条 chat_delta 在共享连接上以自动提交写 events；`store.rs:498-505` 等 BEGIN DEFERRED 事务先 SELECT（next_revision/配额）后 DELETE/INSERT）→ 传导（WAL（`store.rs:130-131`）下 delta 提交使 DEFERRED 事务读快照过期，升级写锁遇 BUSY_SNAPSHOT，busy_timeout（`store.rs:122/134`）对 SNAPSHOT 不重试）→ 症状（用户保存偶发 database_busy（`error.rs:38`）直接失败，需手动重试）。
- 影响范围：功能面：所有经 replace_collection/unchecked_transaction 的写命令与流式任务（方案生成、Agent、讲义等）的并发窗口；触发条件：需配置真实供应商且流式进行中并发写，本地无模型流量不命中；受损面：可用性——偶发保存失败（事务回滚，数据不损坏）。

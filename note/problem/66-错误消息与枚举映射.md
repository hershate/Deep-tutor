### 66#4（=M-4）上游错误透传截断四协议两套做法

- 位置与链条：① 上游返回非 2xx 且 body 带 error.message → ② openai（:495）/gemini（:175）截断 200 字符再拼入 provider_error（gemini 注释明示防注入/长技术细节）→ ③ anthropic（:300）/responses（:308）**不截断**直传 → ④ 同一防御需求下 Anthropic/Responses 协议的长错误（或含注入样式的 payload）可整段到达前端 toast。
- 影响范围：使用 Anthropic Messages 或 OpenAI Responses 协议档案的用户在上游故障时收到超长/未过滤错误文本；功能正确，防御面不一致。两处各加同款截断即对齐。

### 66#5（=M-5/M-6/M-7）错误码语义漂移三处

- 位置与链条：
  - `storage_failed` 挪用（learning 域 6 处）：① 步骤产物类型不一致/请求标识缺失等**数据不变量**错误 → ② 借 storage_failed 码 → ③ 前端如按码提示「检查应用数据目录」即误导（error.rs 通用文案就是这么写的）。
  - `not_found` 挪用：① reports「建议已随证据变化，请刷新」实为冲突类、usage「费率保存后未找到记录」实为写后读失败 → ② 均挂 not_found → ③ 语义分类（重试/刷新/报错）失真。
  - `quota_exceeded` 一码三义：① 行数配额（store，「已用尽」）/尺寸上限（parse/notes，「超过 N 上限」）/配置项数（routing，「最多 16 个」）→ ② 同码不同义不同措辞 → ③ 前端无法按码统一处理（如配额场景引导清理、尺寸场景提示拆分）。
- 影响范围：当前前端主要显示 message 不按码分支，**实际用户影响为零**；风险在未来做按码逻辑（自动重试/引导）时三处全部误判。属代码健康度问题。

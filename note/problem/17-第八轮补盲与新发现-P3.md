## 二、新发现 P3（7 项）

### E-1 调度器 stop/start 跨线程竞态可致 `sync::stop` 永久挂死 + 线程泄漏
- 触发：`sync::stop`（备份导出/导入时，`backup/commands.rs:24/:47`）与
  `start_scheduler`（保存同步配置 `sync/mod.rs:396`、重登 `guard.rs:85`）
  并发执行——两个用户操作恰落在同一窗口。
- 根因：`desktop/src-tauri/src/backend/sync/scheduler.rs:78` `stop_scheduler`
  **先** `STOP.store(true)` **后**加锁 take；此间隙内 `start_scheduler`
  （`:49-51`）看到 STOP=true 便清零 STOP 并 spawn 新线程**覆盖**旧句柄
  （`:52-69`）。
- 传导：stop 随后 take 到的是**新**句柄，`join()`（无超时）等一个 STOP 已被
  清零、每秒循环永不退出的线程 → `sync::stop` 永久不返回，备份命令悬挂；
  且被覆盖的旧线程同样看到 STOP=false 继续运行——**双调度线程泄漏**
  （重复任务被 sync_busy 挡住，但线程不回收）。
- 影响：备份/同步运维面；顺序调用无此问题，概率低但后果为命令挂死。
  修法：stop 全程持锁再置 STOP；或 start 覆盖句柄前对旧句柄 join。

### E-2 同步配置导入为无回滚的部分提交，失败错误无「已导入 N 个」上下文
- 触发：跨实例导入远端配置，某 `enabled:false` 档案的 id 恰撞本地当前激活
  档案（自增 id 场景易撞）。
- 根因：`providers/sync_config.rs:165-183` import 循环逐档案 upsert，
  `providers/mod.rs:479-486` 对「停用当前激活档案」返回 `provider_in_use`，
  循环中断——前 N-1 个已落库、路由/active 未恢复、无回滚；该错误不带
  追加进度上下文（该文案只包 save_settings 失败，`:204-209`）；
  `set_active` 失败（`:210-213`）同理。
- 症状：用户看到裸 `provider_in_use`，档案表被部分改写，重试再次部分叠加。
- 修法：预检全部 upsert 约束或整批事务。

### E-3 媒体 `info()` 每次整读最大 50MB 进内存做哈希，前端再整拉再哈希一次
- 触发：每次打开媒体预览（`MediaPlayer.tsx:19`）。
- 根因：`materials/media.rs:134` `fs::read` 一次性整读 + `Sha256::digest`，
  非流式（同文件 `chunk()` 即为流式句柄）。
- 传导：50MB 视频每次预览后端分配 50MB Vec 全量哈希；前端随后把同一 blob
  完整拉进 WebView 再哈希（`MediaPlayer.tsx:32-33`）——双重整读。
- 影响：内存/性能放大，功能正确。修法：流式哈希或缓存摘要。

### E-4 笔记 zip 导出标题含哨兵串时，导出→再导入静默串数据
- 触发：笔记标题含 `\n\n标签：` 或 `\n\n更新时间：` 子串（外部 frontmatter
  title 或批注标题入口可构造多行值）。
- 根因：`export/notes.rs:81` 把 title/tag **原样**写入以 `\n\n标签：` 为
  分隔的哨兵格式；导入解析取第一个分隔符（`notes/mod.rs:88`
  `split_once("\n\n标签：")`）。
- 症状：再导入时标题截断、tag 吸收标题残余，无报错。次生：文件名净化
  （`notes.rs:31-38`）不修剪尾部空格/句点，个别 Windows 解压工具会再修剪。
- 修法：导出侧转义换行或改用 manifest 承载元数据。

### E-5 ExportCenter 文件名 `slice(0,80)` 可切断代理对——16#B-1 同族
- 触发：方案目标第 79/80 个 UTF-16 单元恰为 emoji/扩展区汉字代理对前半。
- 根因：`desktop/src/components/ExportCenter.tsx:26` `safe.slice(0, 80)` 按
  UTF-16 单元截断；对照后端 `notes.rs:31-39` 用 `chars().take(80)` 按标量
  截断——**两端口径还不一致**（80 单元 ≈ 40 个 CJK 字符 vs 80 个字符）。
- 症状：defaultPath 序列化出孤立代理，后端 serde_json 解析失败，用户看到
  晦涩报错而非保存对话框。
- 修法：与 16#B-1 一并按码点截断统一口径。

### E-6 ExportCenter「请选择已生成单元」占位项重选后变为 unit 0
- 根因：`ExportCenter.tsx:101` 占位 `<option value="">` +
  `setUnitIndex(Number(''))` → 0；`canExport`（`:83`）只查非 null。
- 症状：单元 0 未生成时由后端 `lecture_not_ready` 兜住；已生成则**静默导出
  单元 0**，与「未选择」意图不符。状态机小洞，一行守卫可解。

### E-7 random.rs「安全随机不可用」错误码家族分裂
- 根因：`random.rs:35` `/dev/urandom` 打开失败的 `?` 走 `From<io::Error>`
  映射为泛化 `storage()`（`error.rs:45-49`）；读取失败走专用
  `secure_random_unavailable`（`:37-42`）。
- 症状：同类故障两种错误码，前端难以按码归类。均 fail-safe 无安全后果。
  （注：random.rs 本体清洁——BCryptGenRandom/urandom CSPRNG、token 32 字节
  256 位熵、`dt_` 43 字符校验数学自洽，产品决策承诺全部兑现。）

## 四、清洁确认（此前未单独验证、本轮证实无问题）

- random.rs 熵源与 256 位承诺（BCryptGenRandom/urandom，无时间种子）。
- scheduler.rs 24h 到期判定：锚点 MAX(finished_at) 含失败/取消（无重试风暴）、
  崩溃残留 interrupted 补锚点、时间戳同源 UTC 字典序=时间序、与 01#5 备份后
  重启交互正确、sync_busy 防叠加。
- sync_config.rs 畸形输入健壮性：1MB 前置、128 层深限、≤200 档案、路由引用
  全量校验、deny_unknown_fields 深度脱敏、上传前自校验闭环。
- media.rs 256KiB 承诺、symlink/canonicalize/is_file 三重路径守卫、SHA-256
  端到端校验、引用检查后删除、按 sha256 去重无共享误删。
- export/notes.rs 与 notes 域格式闭环：导出头与导入解析逐字符同语法、
  BOM 口径一致（md 不带 BOM）、updated 双端 UTC、内存构建+atomic_export。
- learning/types.rs 全部契约对齐（ModelReport snake_case 严格框定模型输出
  为有意设计；STEP_NAMES=8 与进度/重跑一致；前端类型一一对应）。
- ExportCenter 格式×范围矩阵与后端守卫对齐（ics/apkg 限制）、系统对话框+
  后端扩展名复检+08#2 数据根守卫达标。
- vite.config.ts/index.html/main.tsx 增量清洁：devUrl 一致、CSP meta 无需

## P3

### 46#1 无单实例防护——双开应用触发跨进程重复同步上传与保存版本冲突

- 位置：`desktop/src-tauri/Cargo.toml`（无 tauri-plugin-single-instance）、`src-tauri/src/main.rs`（无命名互斥体/二次启动检测，全仓 grep `single_instance|CreateMutex|already running` 零命中）；调度守卫 `src-tauri/src/backend/sync/scheduler.rs:47-55`（`static SCHEDULER` 为**进程内** Mutex）；任务并发守卫 `src-tauri/src/backend/sync/mod.rs`（`service.active()` 为进程内 `Mutex<HashSet>`）；任务 id `sync-{pid}-{n}`（mod.rs start_with_path，pid 使两实例 id 不撞键）。
- **传递链条**：① 用户双击快捷方式两次（Windows 常见）→ 两个进程各自 `startup::assemble` → 各自 `start_scheduler`（进程内守卫互不可见，双双启动）→ ② 两实例的调度线程每 60s 各自查 `MAX(finished_at)+24h`（scheduler.rs:28-43）——运行中任务的 finished_at 为 NULL，跨进程不可见 → ③ 到期时两实例同分钟内先后判定 due → 各自 `start_with_path`：进程内 active 集合各自为空、双双放行 → **两条 running 的 upload 任务并行上传**（远端最后写者胜、白耗一次带宽与流量；上传即产生远端历史版本，重复上传还会空耗 10 版本保留额度）→ ④ 期间两窗口并发保存任务/笔记时，`replace_collection` 撞 `revision_conflict`，弹「内容刚被其他操作更新，已为你刷新到最新，请重试一次」（useBackendState.ts:227-231）——用户并不知道自己开了两个实例，提示无从解释。
- **影响范围**：触发条件=双开（无任何拦截，Windows 任务栏固定图标二次点击即得）；后果为重复上传/版本额度空耗/莫名其妙的版本冲突提示，无数据损坏（SQLite WAL + 乐观并发兜底）。修复方向：接入官方 `tauri-plugin-single-instance`（聚焦已有窗口）或启动时命名互斥体快速失败；或至少在文档记录双开边界。

### 46#2 媒体预览经 JSON 数字数组传输全量字节——50MB 上限下仍 3–4× 内存峰值与秒级装载

- 位置：`desktop/src/components/MediaPlayer.tsx:22-44`（全量分块拉取→`parts` ArrayBuffer→`Blob(parts)`→`blob.arrayBuffer()` 再取一份做 SHA-256）、`desktop/src/backend/media.ts:4`（`data: number[]`）、后端 `src-tauri/src/backend/materials/media.rs`（`MediaChunk.data: Vec<u8>`，serde_json 把每字节序列化为一个 JSON 数字）。
- **传递链条**：① 打开 50MB 视频（导入上限 50MB，materials/mod.rs:473-476）→ ② 200 次 `read_material_media_chunk`（256KiB/次）：Rust 侧 `Vec<u8>` → serde_json 数字数组（256KiB 字节 ≈ 0.9–1.6MB JSON 文本）→ IPC → JS `JSON.parse` 出 262144 个 Number → `new Uint8Array(chunk.data)` 再复制 → ③ 全量到齐后 `Blob(parts)`（内部再聚合）+ `blob.arrayBuffer()`（再复制）做哈希 → ④ 瞬时内存峰值约文件 3–4 倍（50MB → 150–200MB 含解析垃圾），弱机装载 3–8 秒——播放首帧前必须 100% 装载并校验完成（SHA-256 全量校验是设计原则，代价是首帧延迟）。
- **影响范围**：所有媒体预览（音视频/图片）；图片通常小无感，50MB 视频明显。功能正确（校验失败不建播放器是既定原则 28#7）。修复方向：Tauri 2 命令返回 `tauri::ipc::Response` 二进制体（或 base64，~1.33× 而非 ~4×），并把哈希校验挪到 Rust 侧增量进行（读完即校验完），前端免第三次复制。

### 46#3 降级防护双轨版本号不同步——user_version 停在 1 而 SCHEMA_VERSION 已到 2

- 位置：`src-tauri/src/backend/store.rs:183-188`（降级拦截仅看 `PRAGMA user_version > 1`）、`:265-267`（user_version 永远只写到 1）、`:21`（`SCHEMA_VERSION: i64 = 2`，记在 meta 表）。
- **传递链条**：① 未来版本把 meta.schema_version 推到 3 但沿用惯例不 bump user_version → ② 用户回装 1.1.0 打开同一数据目录 → ③ store.rs:183 读 user_version 仍为 1，不触发「unsupported_schema 拒绝降级」→ ④ 落入 :232 指纹不匹配分支重跑 1.1.0 的 migrate()（幂等补列，无害）→ ⑤ 新版本写入的新列/新数据被旧代码静默忽略——无类型化提示的隐性降级。
- **影响范围**：当前版本无任何影响（不存在 meta 版本>2 的库）；风险完全前瞻，触发条件=「未来开发者只 bump SCHEMA_VERSION 不 bump user_version 且用户回装旧版」。受影响人群=做版本回退测试的用户；不受影响=正常升级路径（本轮 50 号真实演练通过）。修复成本一行（:183 改读 meta 或约定双 bump）。

### 46#4 learning::migrate 内联复制了 ensure_column 逻辑

- 位置：`src-tauri/src/backend/practice/variants.rs:41-52`（通用 `ensure_column`）；`src-tauri/src/backend/learning/mod.rs:250-263`（对 `evidence_key` 内联重写同一段 PRAGMA table_info 检查）。

- **影响范围**：仅代码维护性；无用户可见影响、无数据风险。修复方向：抽到 store 或共享模块，两处调用同一 helper。信息级。

## 正向结论（本轮核验过、无问题）

- **备份格式无历史包袱**：`deep-tutor-backup` 清单自诞生即 version 3（efff1268，2026-11-03），此后未变（archive.rs:541 严格等值校验）——不存在旧版本备份被 1.1.0 拒收的升级路径问题。
- **迁移幂等**：全部 migrate() 为 `CREATE TABLE IF NOT EXISTS` + `ensure_column`（先 PRAGMA table_info 再 ALTER）风格；唯一索引对 NULL 视为互异，升级库中存量 NULL evidence_key 不会阻断建索引。
- **升级覆盖有测试**：1.0.x→1.1.0 的补列/回填/重映射/长会话/撞键回归在案（df63ee0f、c3895ffe）；旧版单库向 user1 工作区迁移在 startup.rs:349-352 显式处理。
- **滚动 24h 调度与文档一致**：调度锚点为「上次完成时间 +24h」（scheduler.rs:28-43），与决策:159「24h 调度」口径相符；tick 每秒、每 60s 查一次，进程内 STOP/句柄竞态有 E-1 注记与测试。
- **前端资源无泄漏**：全仓唯一 `createObjectURL` 在 MediaPlayer 且卸载即 revoke（:46）。
- **日志面干净**：全部 eprintln/println 只输出错误码、事件 kind、workspaceId 等非敏感字段（grep 核对），release（windows_subsystem=windows）下静默无害；调度失败经 sync_jobs 表持久化对用户可见。
- **StrictMode 并发缝隙已处理**：StrictMode 开启（main.tsx:34）下双挂载的监听器/闭包存活问题已有 24#6/Review:46/Practice:63 注记与修法；ErrorBoundary 兜底整树白屏并提供重载（main.tsx:13-32）。
- **verify-native 无界面通道**：`--verify-native` 走独立目录 + bootstrap 断言 + `exit(0)`（main.rs:40-79），不弹窗、不进主窗口。

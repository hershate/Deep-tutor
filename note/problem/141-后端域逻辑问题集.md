### 141#1 agent send/resume 与 practice 主观题 submit 的域内 Mutex 覆盖整个 IMMEDIATE 事务，取消入口在长写事务并发期被堵死

- 位置：`desktop/src-tauri/src/backend/agent/mod.rs:641-684`（send：`active.lock()`
  在 :641、`store()?` 在 :645、IMMEDIATE 事务 :647-680、`drop(active)` 在 :684）；
  `agent/mod.rs:1298-1364`（resume 同型）；`practice/subjective.rs:142-206`
  （submit：`grading_active.lock()` 在 :142、事务 :149-204、drop 在 :206）。
- 传递链条：①备份导入（`backup/commands.rs:89-92` 在 spawn_blocking 中持全局
  store 互斥锁与库写锁数十秒）、维护 vacuum 或重置进行时，用户调用
  `send_agent_message`（同步命令，主线程执行，`agent/commands.rs:27-34`）；
  ②`send()` 先取 `active.lock()`，随后开 IMMEDIATE 事务——事务在 busy_timeout 上
  等待最长 10 秒，期间锁不释放；③`cancel_agent_run`（同步命令）在
  `agent/mod.rs:1233` 的 `active.lock()` 上排队，`stop_all`（登出/切换/维护停机
  集合，`security/guard.rs:44`）同样阻塞；④主线程冻结最长 10 秒+事务时长，取消
  与停机入口在用户最需要取消的窗口恰好被堵死。取消最终仍会生效（锁释放后），
  无数据损害。对照同域 `learning::start` 的模式（learning/mod.rs:451
  `register()` 锁内瞬时完成、事务在锁外、commit 失败补偿移除）与 providers
  81#4 口径（「锁内只做幂等检查与登记，查询/事务移出锁窗口」），本两处为反向
  模式。
- 影响范围：受影响=长写事务进行中同时发起 agent 消息/主观题作答并尝试取消/登出
  的并发窗口；不受影响=常态单命令场景（无并发长事务时锁窗口为毫秒级）。
  损害性质=主线程冻结面 + 取消入口延迟，非数据损坏。
- 修复方向：对齐 learning::start 模式——锁内只做运行中检查与登记，IMMEDIATE
  事务移出锁窗口，commit 失败补偿移除登记；practice subjective submit 同型一并
  收口。

### 141#2 save_draft/get_draft/delete_draft 同步命令共享全局 store 互斥锁，导入/重置期间打字自动保存冻结主线程

- 位置：`desktop/src-tauri/src/backend/commands.rs:166-197`（save_draft :167-179、
  get_draft :181-184、delete_draft :186-197，均为 `#[tauri::command]` 同步命令）；
  锁获取点 `commands.rs:8-15`（`store()` 取 `state.store` 全局 `Mutex<Store>`）。
- 传递链条：①`import_full_backup` / `reset_application` 在 spawn_blocking 中持有
  全局互斥锁贯穿整个导入/重置（backup/commands.rs:89-92、commands.rs:213-219，
  大库可达数十秒）；②用户打字触发草稿自动保存——`save_draft` 是同步命令，
  `store(&state)?` 在同一互斥锁上阻塞，且同步命令运行于主线程；③导入/重置期间
  窗口整体冻结（不可拖动，>5s 被 Windows 标「未响应」）。与 127#2 修复
  replace_collection 时注释自述的同一病症（「打字保存/勾选任务是高频路径」），
  但同批写路径 save_draft/delete_draft 与读路径 get_draft 未迁移。
- 影响范围：受影响=备份导入/重置期间的草稿保存与读取（高频打字自动保存）；
  不受影响=非导入/重置期。损害性质=主线程冻结，无数据损害（锁释放后命令正常
  完成）。`events_since` 同为同步命令但生产注册面已摘除（92 号），界内。
- 修复方向：按 127#2（replace_collection）同款迁 `#[tauri::command(async)]` +
  `spawn_blocking`。

### 141#3 plugins reload 对「磁盘清单存在、DB 无行」的残留态报 storage_failed，错误码语义漂移

- 位置：`desktop/src-tauri/src/backend/plugins/mod.rs:663-683`（UPDATE 在 :665 无
  changed 检查；SELECT generation 在 :678-682）。
- 传递链条：①插件目录 manifest.json 在磁盘存在而 plugins 表无该 id 行——可达
  路径：install() 失败清理是 best-effort（plugins/mod.rs:505-543，清理自身失败时
  残留）、外部清库、卸载反向残留；②reload() 读清单成功（磁盘文件在）→
  `UPDATE plugins SET ... WHERE id = ?` 影响 0 行（未检查）→ 继续 DELETE/INSERT
  订阅 → `SELECT generation FROM plugins WHERE id = ?` 返回
  QueryReturnedNoRows；③经 `From<rusqlite::Error>`（error.rs:47）泛化为
  `storage_failed`「无法读写本地数据，请检查应用数据目录后重试」——用户被引向
  检查磁盘/数据目录，真实情况只是一条不存在的插件记录；同域 `set_enabled`
  （mod.rs:559）、`uninstall`（mod.rs:739）对同一状态均正确报 `not_found`。
- 影响范围：受影响=磁盘残留清单 + DB 无行场景下的 reload 调用；不受影响=正常
  安装插件的 reload。损害性质=误导性错误码与排查方向，无数据损害。
- 修复方向：reload 的 UPDATE 加 `changed == 0 → not_found`（与 set_enabled/
  uninstall 同口径）。

### 141#4 sharing 未登录读取无效分享令牌时无负缓存，每次全遍历用户目录

- 位置：`desktop/src-tauri/src/backend/sharing/mod.rs:406-473`（read_token）。
- 传递链条：①未登录态（guard 白名单放行 read_shared_plan 族，guard.rs:314-317）
  提交一个无效/已撤销 token；②`read_token` 探测根库未命中 → `indexed_owner`
  未命中（只对命中建索引，mod.rs:172-183）→ 遍历 users/ 目录（上限 10,000，
  mod.rs:436），每用户 `Store::at_user` 新开连接（含 PRAGMA/指纹校验）；③每次
  无效 token 重复同样的全遍历，无负缓存。本地单机多用户场景用户数通常为个位数，
  遍历上限已防御，界内。
- 影响范围：受影响=本机 WebView 注入脚本反复触发无效 token 的 IO 放大；不受
  影响=正常分享读取。损害性质=资源卫生注记。
- 修复方向：可对近期已确认不存在的 token 哈希加小型 TTL 负缓存；或维持现状。

### 141#5 providers upsert/delete 的停用/在用约束预检在事务外读，毫秒级 TOCTOU

- 位置：`desktop/src-tauri/src/backend/providers/mod.rs:521-544`
  （check_disable_constraints，读 active() 与路由设置）、`mod.rs:679-692`
  （delete 的 active/routing 检查），均在各自写事务外执行。
- 传递链条：①upsert 调 check_disable_constraints 读活动档案与路由引用，检查
  通过；②并发 IPC 恰在该毫秒窗内 set_active 切换到同一档案（或路由设置加入
  引用）后本方提交 enabled=0；③结果为停用了刚成为活动供应商的档案，后续请求
  经 fallback 报 provider_disabled，用户可自行再启用。触发需双窗口毫秒级并发
  管理操作，正常单窗口序列不可达。
- 影响范围：受影响=双窗口毫秒级并发供应商管理；不受影响=单窗口序列。损害
  性质=约束瞬态绕过，可自愈，无数据损害。
- 修复方向：若认定多窗口并发管理在产品边界内，把约束复查挪进 upsert/delete
  的写事务（31#35 community 同型先例）。需真实双窗口并发实测确认可触发性后
  定级。

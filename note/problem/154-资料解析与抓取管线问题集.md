### 154#1 去重回补写错扩展名——11#15 修复存在跨扩展名漏洞，回补失效并留孤儿副本

- 位置：`desktop/src-tauri/src/backend/materials/mod.rs:597-610`——去重
  命中分支用**本次导入的 kind**构造 `destination = original_path(…, &kind)`，
  而返回的现有行 kind 可能不同。
- 传递链条：①`a.txt`（内容 X）入库，原件 `{sha}.txt` 被外部删除/杀毒
  隔离；②再导入字节相同的 `b.md` → 命中去重；③字节被写到 `{sha}.md`
  （无任何行引用该路径），现有行 kind 仍为 txt、`original_available`
  仍 false——回补失效，内容永久 missing_original；反向场景（.txt 原件
  仍在）则额外产生未引用的 `{sha}.md` 孤儿副本——维护扫描
  （maintenance/mod.rs:302-304）只识别 `.upload-`/`.restore-` 临时件，
  孤儿永不清。全部去重/回补测试（mod.rs:1671-1702、commands.rs:793-818）
  均为同扩展名用例。
- 影响范围：受影响=跨扩展名去重回补（原件丢失后的恢复路径）。
  损害性质=数据完整性（回补失效）+ 磁盘孤儿。
- 修复方向：destination 用现有行的 kind 构造（或按 sha 探测既有任意
  扩展名原件路径）。

### 154#3 EPUB 嵌套同名 script/style 提前解除忽略——畸形文件向正文注入脚本垃圾文本

- 位置：`desktop/src-tauri/src/backend/parse.rs:255-257`（Start 时
  `ignored_depth = depth`）+ `:305-307`（End 深度相等即清零）——嵌套
  同名标签的内层 End 使 ignored_depth 归零。
- 传递链条：①构造的 xhtml 含 `<script>a<script>b</script>c</script>`；
  ②内层 `</script>` 使 ignored_depth 归零；③仍处外层 script 内的文本
  "c" 被 push 进正文（epub 分支 :276 只要 `ignored_depth == 0` 即收文本）
  → 解析结果含脚本垃圾。非安全漏洞（无执行面），影响解析质量与引用
  白名单纯度。测试 `epub_uses_manifest_and_never_extracts_paths`
  （parse.rs:533）只覆盖平铺 script/style。
- 影响范围：受影响=嵌套同名忽略标签的 EPUB（对抗性/畸形文件）。
  损害性质=解析质量。
- 修复方向：ignored_depth 改为只增计数（同名嵌套时 End 按计数递减），
  或 Start 时若已在忽略态则不更新基准。

### 154#4 ZIP 条目名 GBK → cp437 乱码标题直接入库

- 位置：`archive.rs:75-80`、`notes/mod.rs:189-193`（条目名 `to_str()`
  直接作标题）；Cargo.toml:24（zip crate 2.6.1）。
- 传递链条：①中文 Windows 压缩工具（WinRAR/资源管理器「发送到压缩
  文件夹」）生成 ZIP 时以 GBK 编码文件名且未置 UTF-8 标志；②zip crate
  对未置标志条目按 cp437 解码——GBK 字节解出合法但乱码的 UTF-8 串；
  ③`to_str()` 恒成功（cp437 全可映射）——「资料包文件名无效」拒绝路径
  不可达，乱码标题照常入库并在资料列表/引用处展示，无任何警示。
- 影响范围：受影响=中文 Windows 常见压缩工具产出的资料包/笔记包导入
  标题可读性；不受影响=数据本体（内容与哈希正确，仅标题乱码）与
  UTF-8 标志包（macOS/新工具/代码生成）。现有测试全部 ASCII 条目名。
  损害性质=标题乱码静默入库。需运行时复证 zip 2.6.1 实际行为后定级。
- 待核：确认后按「非 UTF-8 标志且解码含高位字符→警示或 GBK 重解码」
  处置。

### 154#5 reqwest 未启用 gzip 自动解压——强制 gzip 站点可能产出静默乱码正文

- 位置：Cargo.toml:31（reqwest default-features=false，仅 blocking/json/
  native-tls，无 gzip feature）；`web/mod.rs:231-241`（直接读原始 body，
  不检查 Content-Encoding）。
- 传递链条：①客户端不发 Accept-Encoding，但个别站点/CDN 无条件返回
  `Content-Encoding: gzip` 的压缩字节；②Content-Length 预检（压缩后
  长度）与 content-type 检查照过；③`decode_body` 对 gzip 魔数字节走
  BOM→头→meta→UTF-8→GB18030 兜底链——GB18030 可映射大多数字节对，
  had_errors 可能为 false → 产出「解码成功」的乱码正文入库，无告警。
- 影响范围：受影响=强制 gzip 站点的抓取/检索正文质量；不受影响=正常
  未压缩站点与标准协商压缩站点（客户端未请求即不压缩）。web/tests.rs
  无压缩响应用例。损害性质=静默乱码（需实测确认站点存在性）。
- 待核：实测强制 gzip 站点；修复为启用 gzip feature 或按 Content-Encoding
  拒绝/解压。

### 154#9 解析管线边界核验结论（自洽项）

  >1%/跳页/网页截断/超 5MB 截断）；metadata_only 仅由备份恢复产生，

  「需要 OCR，不生成模拟文本」（parse.rs:92-97）。损坏 PDF 单页跳过
  计页（:134-141）。

  节流 :887）→85→100；首次 35% 因 35%10≠0 不写 kv，列表进度在 35→40%
  区间显示 10%（纯视觉）。DOCX 只取 word/document.xml、PPTX 只取

### 154#10 限额与编码口径汇总

- 单文件 50MB；解析文本 5MB；XML 条目 32MB；解析 ZIP 200×/总量 64MB；
  导入 ZIP 64 文件/200MB/条目 2048；PDF 2000 页；IPC 单批 32；网页
  1MB/256KB/3 跳/连接 5s/总 12s/候选 10/URL 900B/检索词 300B；笔记
  64MB/单条 1MB/1000 条；媒体块 256KiB。
- TXT/MD 非 UTF-8 一律拒绝（mod.rs:563-568、notes/mod.rs:225-277），
  与 web 侧三级解码+GB18030 兜底不对称——文件侧错误文案无「转码后
  导入」指引（web 侧有）；UTF-8 BOM 解析时剥离。
- `parse.rs:169/:208` ZipBudget.entries 只累加永不消费（条目上限实际
  由 :180 `archive.len() > 2048` 执行）——死计数，无功能缺口。

### 154#11 ZIP/媒体/SSRF 三面核验无新问题

- ZIP：声明值 200×/50MB（archive.rs:96-102）+ `take(50MB+1)` 实读比对
  + phase 2 magic bytes 再验，TOCTOU 无缺口；加密条目读取期失败映射
  「损坏、加密或读取失败」；`../` 由 enclosed_name 拦截（测试覆盖
  escape/bomb/65 文件/trailing-invalid 原子性）。
- 媒体：12 格式 magic bytes 含 mp3 双签名；chunk 边界 offset>total 拒、
  length≤256KiB、symlink+canonicalize 围栏（media.rs:93-118），篡改/
  越界/假扩展名均有测试。
- SSRF：resolve 全地址 public_address（含 NAT64 内嵌 IPv4、0.0.0.0/8，
  openai.rs:106-160）+ `resolve_to_addrs` 固定 IP 防 DNS rebinding
  （web/mod.rs:158）；重定向逐跳新建 client 重新 resolve；大小执行点
  为 Content-Length 预检 + `take(1MB+1)` 流中钳制 + 读后复核——非先全
  量下载；凭据 userinfo/查询参数 token 拒绝均有测试。

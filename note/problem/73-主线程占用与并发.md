# 73 · 主线程占用与并发（第二十七轮·Tauri 2 同步命令主线程执行面）

> 审计范围：189 命令逐一定位 sync/async + 重 IO 评估、Mutex poisoning、
> stop_all 语义、线程生命周期、锁争用。核心事实（tauri 2.12.5 源码核实）：
> IPC `run_invoke_handler` 在 WebView2 UI 线程内联执行——guard 包装层与全部
> 非 async 命令体都跑在主线程。10 个 async 命令模式本身已核实正确。
> 主审已抽验 D-1（guard.rs:77-84 主线程锁 store）属实。

## P2（用户可感冻结）

### 73#1（=D-1）guard prepare_store 与 async 备份的 store 互斥锁竞争重新冻结主线程

- 位置：`backend/backup/commands.rs:33-88`（spawn_blocking 内 `state.store.lock()` 持锁贯穿整个导出/导入）；`backend/security/guard.rs:77-84`（每条命令的 prepare_store 取同一锁，运行在主线程）。
- 传递链条：① import_full_backup（整库解包+重写，秒到分钟级）持锁 ② 期间前端任意 invoke（含 7-8 处 150ms 节流的 getProviderChat 轮询）→ ③ 主线程在 prepare_store 的 lock() 上挂起至导入结束，mutex 等待无超时——44#1 把重 IO 移出主线程的收益被 guard 锁竞争部分抵消；login switch（guard.rs:145）同样被阻塞。
- 影响范围：备份导入期间全应用冻结数秒至数十秒。
- 修复方向：guard 的锁窗口缩到零（无锁读 owner_id 比较，仅不一致时才锁+换库）；或备份改用独立快照连接（VACUUM INTO 已有，避免持共享锁）。

### 73#2（=D-2）vacuum_database 同步命令在主线程 integrity_check+事件裁剪+VACUUM

- 位置：`backend/maintenance/commands.rs:51-66`（同步）→ `maintenance/mod.rs vacuum()`。
- 传递链条：PRAGMA integrity_check 全库逐页扫描 → DELETE events → execute_batch("VACUUM") 整库重写 → wal_checkpoint。几十 MB 库 1-5s，GB 级 30-60s+，Windows 5 秒标「未响应」。
- 影响范围：手动整理数据库时全应用冻结；频率低但完全可感。
- 修复方向：maintenance 三命令（本条+下两条）整体移 `#[tauri::command(async)] + spawn_blocking`（44#1 同款，需带 principal 传播）。

### 73#3（=D-3）cleanup_orphan_files 同步命令：stop_all（最坏 ~140s）+ 全目录 walk + 500 项删除全程主线程

- 位置：`backend/maintenance/commands.rs:34-49`（OPERATION 锁→stop_all→持 store 锁→cleanup）。
- 传递链条：正常 1-5s；若 SSE 停滞使 stop_all 命中多个 deadline（agent/practice/knowledge/learning/providers 各 15s + sync 50s）→ 主线程冻结上限 ≈140s。
- 影响范围：清理期间全应用冻结。
- 修复方向：同 73#2 移后台。

### 73#4（=D-4）get_maintenance_report 同步命令在主线程跑 integrity_check + 全目录树 walk

- 位置：`backend/maintenance/commands.rs:26-32`。打开「体检」页即触发；0.3-5s（随库与文件数线性）。
- 修复方向：同 73#2。

### 73#5（=D-5）import_webpage 同步命令在主线程做网络抓取（connect 5s/总 12s 超时）

- 位置：`backend/web/commands.rs:12-27` → `web/mod.rs:155-160`（blocking client）。弱网/挂起站点时主线程冻结最长 ~12-17s。移后台。

### 73#6（=D-6）get_sync_versions 同步命令在主线程做 S3/WebDAV 网络请求（总超时 45s）

- 位置：`backend/sync/commands.rs:56-66` → `sync/versions.rs:162+`；client 总超时 45s（`providers/openai.rs:261-270`）+ pinned DNS 阻塞解析。打开同步版本列表 → 冻结至远端响应，S3 挂起最长 45-50s。移后台。

### 73#7（=D-7）get_library_overview 持 store 锁全量读笔记 + 每条 annotation 一次 Store::new 的 N+1

- 位置：`backend/notes/library.rs:67-75`（500×≤1MB 正文 JSON）+ `:124`（每条 annotation 调 `learning::get`——每次 `Store::new()` 新连接：PRAGMA×5+schema 指纹 SHA256）；annotations SELECT 无 LIMIT。
- 传递链条：数百次连接开关 ×1-3ms + 大 JSON 解析 ≈ 1-5s 主线程冻结。39#1/53#3 修过两处同族 N+1，此处漏网。
- 修复方向：单连接批取（53#3 同款）。

### 73#8（=D-8）export_material_original 同步命令整读原件（≤50MB）+SHA256+写盘全程主线程

- 位置：`backend/materials/mod.rs:1312-1324`。50MB 文件 0.3-2s（HDD 更差）；同族 get_material_media_info/verify_material_media 流式全文件哈希 0.1-1s。移后台或流式化。

### 73#9（=D-9）logout/登录切换的 stop_all 在主线程可阻塞至 ~140s

- 位置：`backend/security/guard.rs:26-66`（8 域串行 deadline）+ `:106-157`（switch 持 WORKSPACE_SWITCH 写锁执行）。常见 15-30s（agent 工具 ~12s 网络等待即命中 15s）、最坏 140s；期间所有后续 invoke 排队。
- 修复方向：stop_all 各域并行化（线程 scope）/收敛 sync 50s deadline；switch 本身移后台。

### 73#10（=D-10）reset_application 同步命令：串行 `?` 停机 + Store::reset 大事务 + remove_dir_all 整个 materials 目录（上限 ~10GB）

- 位置：`backend/commands.rs:82-117`。六个串行 `?`（首败短路——56#2 只修了 guard 侧，此处旧形态）；成功路径 remove_dir_all(backup)（200×50MB）+ agent-workspaces + sync。
- 影响范围：秒到数十秒主线程冻结；停机集合与 guard::stop_all 不一致（见 73#14）。
- 修复方向：改用 guard::stop_all；remove_dir_all 移后台（reset 返回后再异步删）。

## P3

### 73#11（=D-11）SSE 流客户端无读超时——停滞流使 worker 永不退出，stop_all 永远失败

- 位置：`providers/openai.rs:272-279`（streaming_client 仅 connect_timeout，无总/读超时；对比 blocking 45s）。worker 阻塞在停滞流读取上 → 15s deadline 必到 → stop_all 报「部分任务未能停止」，logout/cleanup/vacuum 被拒，线程泄漏至流断开。

### 73#12（=D-12）provider_route_runs 无裁剪、无 created_at 索引——list_provider_route_logs 全表扫+排序

- 位置：`providers/routing.rs:121-131`（表仅 request_id 主键，无任何 DELETE 裁剪）；`:1277+` `ORDER BY created_at DESC LIMIT 100` 无索引。行数随每次模型请求单调增长：十万行 ≈100-500ms 主线程。加索引+按量裁剪（events 90 天同款）。

### 73#13（=D-13~D-16/D-21 合并）连接开关高频族

- get_dashboard 一次 ~6 连接+两份完整方案列表（`engagement/mod.rs:783-860`，100-500ms/次进首页触发）；get_sync_overview 51 次连接（`sync/mod.rs` overview）；search_workspace 全表 LIKE+全方案图遍历主线程（`engagement/mod.rs:362-470`，同族 knowledge::search 已移后台）；guard 每命令固定成本（keyring 系统调用 1-10ms+JWT）；`STORE_OPEN_LOCK` 全局串行化所有 Store::new（生产 ~182 调用点，单次 0.5-3ms 含 schema 指纹 SHA256；突发 20-50 open/s 时主线程 5-15% 耗在建连）——两个例外长持锁点：升级后首开在锁内跑 15 域 migrate（秒级）、user1 迁移路径锁内整库 copy+checkpoint（GB 库数十秒）。
- 修复方向：State 内缓存长连接（SecurityState 模式）；search_workspace 移后台；dashboard 扇出瘦身。

### 73#14（=D-19）reset_application 停机集合与 guard::stop_all 不一致

- `commands.rs:86-91` 六个串行 `?`（首败即弃，后续域不停）且不含 materials::stop（由 prepare_reset 补）与 focus 域；guard.rs:24 注释宣称「清理/重置共用同一实现」与代码不符。

### 73#15（=D-20）cleanup/vacuum 与 import_full_backup 的互斥未检测

- import 的大事务持写锁（另一连接、非 stop_all 管辖）期间触发 cleanup/vacuum → purge 的 IMMEDIATE BEGIN 与 events DELETE 在 busy_timeout 内等最多 10s 后报 database_locked（cleanup 失败）；若 import 持 state.store 互斥锁则 cleanup 的 store(&state) 主线程无超时阻塞（归 73#1）。

### 73#16（=D-17）state.store/STORE_OPEN_LOCK/OPERATION 中毒即全应用命令永久拒绝

- 持锁点全部 `map_err` 无 poison 恢复：最现实向量是 backup spawn_blocking 内 panic（unwind 毒化解锁路径）→ 此后每条 invoke 报 store_unavailable 直至重启。SecurityState.connection 与 OPERATION 同类。修复方向：关键锁 poison 恢复（SCHEDULER 的 `into_inner` 模式已示范）或 poison 后自动重建 Store。

## 信息性

### 73#17（=D-18）域内 active/cancels 映射全部静默降级，无二次污染扩散

- 全部等待/轮询点 `if let Ok(...)`/`unwrap_or(false)`——中毒后 stop() 视作 idle 提前返回（vacuum/reset 的理论竞态窗口，需先有一次 panic）。

## 已核实安全（摘要）

- 10 个 async 命令 spawn_blocking+with_principal 模式正确，panic 经 JoinError 转类型化错误不崩进程；生产代码所有 `.lock().unwrap()` 均为 #[cfg(test)]。
- stop_all/各域 stop/cancel_chat 无互等死锁（取消只写 AtomicBool、锁序单向 state.store→STORE_OPEN_LOCK）；scheduler stop/join 竞态已由 E-1 修复。
- 退出无钩子（关窗即进程终止）——WAL 保证崩溃一致性（丢最后提交为既定决策 27#7）；无 detached 线程长期持连接阻塞 checkpoint（vacuum 的 checkpoint 被并发读挡住时按 B-16 优雅降级）。
- 有界命令族安全：events_since（索引+LIMIT 201）、read_material_media_chunk（256KiB/次，46#2 切片有效）、list_practice_history（50 点查）、community/reports 聚合（有索引）、sharing（2MB 包上限）、list_materials（200 上限）。

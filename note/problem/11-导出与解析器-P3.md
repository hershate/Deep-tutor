第四轮对 export/pdf.rs、anki.rs、其余格式、materials/parse.rs、去重暂存、
notes 导入的审计发现。验证通过未列入：PDF 布局计算/xref/ToUnicode、ICS

## 导出生成器（export/）

### 1. 任一字符缺字形即整份 PDF 失败，且不回退第二字体
- `pdf.rs:281-286`——首轮任一字符无字形即 Err；`:211-231` 字体链回退只发生在"文件读取/解析失败"，字形缺失在内层不触发换字体。内容含 emoji/生僻字/BOM 字符 U+FEFF 时整份失败。
- 传递链条：触发（导出内容含 emoji/生僻字/U+FEFF）→ 根因（`pdf.rs:281-286` render 首轮逐字符 `font.glyph()` 返回 None 即返回 `pdf_font_missing_glyph` 错误）→ 传导（`:211-231` system_font 的 msyh→simhei 轮换仅覆盖读取/解析失败，字形检查发生在字体选定后的 render 内层，不触发换字体重试）→ 症状（整份 PDF 导出失败，用户被提示改用 Markdown/TXT）。
- 影响范围：功能面：所有走 `pdf.rs` 的 PDF 导出路径；触发条件：默认配置即命中，任一字符不在 msyh cmap（`:126-182` 查表）即失败；受损面：可用性——整份导出不可用，无部分成功。

### 2. 无字形子集化：系统字体全量嵌入，一页 PDF 也 ≥约 10MB
- `pdf.rs:42-79`——program 复制源字体全部表（仅重建目录偏移）；msyh.ttc 约 19–21MB，Flate 后仍约 10MB。全仓无"子集化"声明，属体积体验问题。
- 传递链条：触发（任意一次 PDF 导出）→ 根因（`pdf.rs:42-79` Font::load 将源字体全部表 `program.extend_from_slice` 复制，仅重建目录偏移）→ 传导（产物内嵌整个字体 program；实测 C:/Windows/Fonts/msyh.ttc 为 19,704,352 字节）→ 症状（一页 PDF 也产出约 10MB 级文件，仓库内无子集化实现）。
- 影响范围：功能面：所有 PDF 导出产物；触发条件：默认配置必命中（Windows 唯一字体源即 msyh.ttc）；受损面：可用性/存储——文件体积与内容量无关，传输保存成本高。

### 3. SM-2 调度数据整体丢弃：所有卡片按"全新卡"写入 Anki
- `review/mod.rs:53-68` 的 due_at/interval/ease/repetitions/lapses 在 `export/mod.rs:87-92/421-425` 组装时丢弃；`anki.rs:110-113` 固定 type=0/queue=0/due=index/ivl=0——导出后全部回到新卡队列，应用内复习进度清零。
- 传递链条：触发（用户将复习卡导出为 Anki 包）→ 根因（`export/mod.rs:87-92` ExportCard 仅含 front/back/tag，`review/mod.rs:53-68` 的调度字段在 `:421-425` 组装时未被复制）→ 传导（`anki.rs:110-113` cards INSERT 硬编码 type=0/queue=0/due=index/ivl=0）→ 症状（导入 Anki 后所有卡片回到新卡队列，应用内复习进度清零）。
- 影响范围：功能面：Anki 导出唯一格式路径；触发条件：默认配置必命中，凡导出含复习记录的卡片即触发；受损面：数据正确性——复习历史与调度状态不可迁移。

### 4. note guid/id 锚定导出时间戳，再次导出导入 Anki 必产生整套重复笔记
- `anki.rs:51-54/82/90-96`——guid = sha256(本次时间戳 note_id:front)[:10]，非内容锚定；对比 deck/model 用 stable_id。更新内容后重导得到重复卡而非更新。
- 传递链条：触发（同一批卡片第二次导出并导入同一 Anki）→ 根因（`anki.rs:90-96` guid=sha256("{note_id}:{front}")[:10]，`:82` note_id=now_ms+index 即导出时间戳；对比 `:55-56` deck/model 用 stable_id 内容锚定）→ 传导（每次导出 now_ms 不同 → guid 全新 → Anki 按 guid 判为新笔记插入）→ 症状（更新内容后重导得到整套重复卡而非更新）。
- 影响范围：功能面：Anki 导出/再导入闭环；触发条件：默认配置必命中，第二次及以后导出即触发；受损面：数据正确性——Anki 库重复卡累积需手工清理。

### 5. [待确认] col/deck 配置 JSON 为最小子集，缺官方索引，csum 算法与 Anki 不同
- `anki.rs:67-79`——dconf 缺 new.order/separate/rev.fuzz 等键；建表无 ix_cards_nid 等官方索引；csum 取 sha256 前 4 字节（Anki 官方为 first-field 自有校验和）。schema 与 ver 11 逐列一致、无媒体正确；新版 Anki（2.1.50+）导入兼容性未实测。
- 传递链条：触发（导出的 collection.anki2 被新版 Anki 2.1.50+ 导入）→ 根因（`anki.rs:67` dconf 仅 new/rev/lapse 最小键集；`:70-76` 建表语句无任何 CREATE INDEX；`:83-89` csum=sha256(front) 前 4 字节，与官方 first-field 校验和算法不同）→ 传导（Anki 导入器按自身 schema 预期校验并迁移 col/cards）→ 症状（兼容性未实测，可能报 schema 异常或调度行为偏移）。
- 影响范围：功能面：Anki 导出格式整体；触发条件：需新版 Anki 实际导入方可确认，仓库内无真实导入验收；受损面：可用性/数据正确性——待确认；判定倾向：schema 逐列与 ver 11 一致、无媒体正确，风险集中在 dconf 缺键与 csum 算法，倾向"可导入但非官方语义"，需实测后关闭。

### 6. 学习报告 CSV 缺公式注入防护（三处文件级 CSV 出口唯一未覆盖者）
- `reports/mod.rs:999` escape 仅引号包裹；`:1025/:1033` goal_detail/plan.title 用户可控。对比 `export/formats.rs:81-87` 与 `providers/usage.rs:469-475` 均有 `= + - @` 守卫——计划标题以 = 开头导出后 Excel 打开即按公式执行。
- 传递链条：触发（方案标题或目标说明以 =/+/-/@ 开头后导出学习报告 CSV）→ 根因（`reports/mod.rs:999` escape 仅引号包裹与双引号转义；`:1025` goal_detail、`:1033` plan.title 用户可控值直接进单元格）→ 传导（对比 `export/formats.rs:81-87` csv_cell 与 `providers/usage.rs:469-475` 均有前导 `'` 守卫，此处遗漏）→ 症状（Excel/WPS 打开 CSV 按公式执行，可泄露本地文件内容或发起请求）。
- 影响范围：功能面：学习报告 CSV 出口；触发条件：默认配置即命中，需标题/说明以公式字符开头；受损面：数据正确性/安全——CSV 公式注入在用户表格软件中执行。

### 7. 用量 CSV 无 UTF-8 BOM，与另两个 CSV 出口不一致
- `providers/usage.rs:479` 表头无 \u{feff}（对比 formats.rs:108、reports/mod.rs:1000）——中文供应商名在 Excel 双击打开时按 GBK 解码乱码。
- 传递链条：触发（中文 Windows 用户双击打开用量 CSV）→ 根因（`providers/usage.rs:479` 表头无 \u{feff} 前缀，对比 `formats.rs:108`、`reports/mod.rs:1000` 均有 BOM）→ 传导（Excel 对无 BOM 的 UTF-8 按本地 ANSI/GBK 解码）→ 症状（中文供应商名等列乱码不可读）。
- 影响范围：功能面：供应商用量 CSV 导出；触发条件：默认配置即命中，中文 Windows + Excel 双击打开即触发；受损面：可读性——导出数据乱码。

### 8. OPML text 属性保留原始换行，被 XML 属性规范化吞掉
- `export/formats.rs:197-208`——多行正文进 text="..." 属性未替换换行；处理器按属性规范化折叠为空格（HTML 导出有 \n→&lt;br&gt;，OPML 无对应处理）。
- 传递链条：触发（多行段落/项目符号正文导出为 OPML）→ 根因（`export/formats.rs:197-208` text 属性经 `xml()`（`:52-54` 即 escape_html）仅转义 &<>"'，换行原样留在属性值；对比 `:66` HTML 导出有 `.replace('\n', "<br>")`）→ 传导（XML 处理器对属性值中的字面换行做规范化折叠为空格）→ 症状（大纲工具中多行内容连成一行，行结构丢失）。
- 影响范围：功能面：OPML 导出格式；触发条件：默认配置即命中，需正文含换行（多行笔记/摘要/卡片背面）；受损面：可读性/数据正确性——导出内容结构信息丢失。

## 材料解析器（materials/parse.rs）

### 9. txt/md 解析与笔记导入均不剥 UTF-8 BOM，U+FEFF 入库并连锁毁掉 PDF 导出
- `parse.rs:43-49`（:73 trim 不移除 U+FEFF）、`materials/mod.rs:470-475`、`notes/mod.rs:148-199` 同样保留——Windows 记事本旧默认保存的文本首字符 FEFF 入库进 Wiki 上下文/摘录，且 msyh 无该字形 → 叠加 01#23 使知识库 PDF 导出失败。
- 传递链条：触发（导入 Windows 记事本旧默认"UTF-8"保存的 txt/md，首字节 EF BB BF）→ 根因（`parse.rs:43-49` txt/md 分支 from_utf8 原样保留 U+FEFF，`:73` trim 不移除（U+FEFF 非空白字符）；`materials/mod.rs:470-475` 校验与 `notes/mod.rs:148-199` 导入同样不剥）→ 传导（FEFF 入库为文本首字符，进入 Wiki 上下文/摘录/笔记）→ 症状（叠加条目 1 机制：`pdf.rs:281-286` msyh 无该字形 → 知识库 PDF 导出整份失败）。
- 影响范围：功能面：txt/md 材料解析、笔记导入（单文件与 ZIP）及下游全部消费解析文本的功能；触发条件：默认配置即命中，需带 BOM 的文本文件；受损面：数据正确性+可用性——不可见字符污染上下文并连锁毁掉 PDF 导出。

### 10. PDF 单页提取失败即全量失败，无部分文本保留
- `parse.rs:102-112`——2000 页文档仅 1 页内容流损坏，整份解析失败、已累积文本全部丢弃（对比 5MB 截断有 warning）。
- 传递链条：触发（多页 PDF 中任一页内容流损坏/非标准）→ 根因（`parse.rs:102-112` 逐页 `document.extract_text(&[*page])` 失败经 `?` 直接返回 Err("PDF 文本层读取失败")）→ 传导（已累积的 text 局部变量随 Err 丢弃，无部分返回路径；对比 `:81-88` 超 5MB 时仅 warning 截断）→ 症状（2000 页文档仅 1 页异常即整份失败，零文本落库）。
- 影响范围：功能面：PDF 材料解析（知识库/Wiki 上下文的上游）；触发条件：默认配置即命中，需文件含至少一页 lopdf 无法提取的内容流；受损面：可用性——大文档全有全无，无法部分使用。

### 11. [待确认] 中文 PDF 编码覆盖依赖 ToUnicode/UniGB 两类，其余预定义 CMap 直接失败或乱码
- lopdf 0.35：Identity-H 仅走 ToUnicode，预定义 CMap 仅 UniGB-UCS2/UTF16 可解码（其余 CharacterEncoding 错误→整份失败）；流式 Encoding 无 ToUnicode 回退单字节 StandardEncoding 可能"已解析+乱码"落库。测试无中文 PDF 用例。
- 传递链条：触发（导入使用 Identity-H+ToUnicode、UniGB 系以外预定义 CMap，或流式 Encoding 无 ToUnicode 的 PDF）→ 根因（Cargo.lock 锁定 lopdf 0.35.0：其 `encodings/mod.rs:49` 仅处理 UniGB-UCS2-H/UniGB-UTF16-H，`:84` 其余 SimpleEncoding 返回 CharacterEncoding 错误；`object.rs:420-430` Identity-H 依赖 ToUnicode）→ 传导（`parse.rs:93/:106` 映射为"PDF 结构无法读取"/"PDF 文本层读取失败"整份 Err，或回退单字节 StandardEncoding 照常返回）→ 症状（整份解析失败，或"已解析+乱码"文本落库）。
- 影响范围：功能面：非简中/特殊编码 PDF 的解析路径；触发条件：需文件使用上述编码形态，现有测试无中文 PDF 用例未覆盖；受损面：可用性/数据正确性——待确认；判定倾向：lopdf 源码分支已证实存在，倾向成立，实际风险取决于真实语料中此类 PDF 占比。

### 12. EPUB href 仅解码 %20，其余百分号编码路径整体失败
- `parse.rs:349-377`——中文文件名 href（chapter-%E4%B8%AD.xhtml，规范允许且常见）by_name 找不到 → "压缩包缺少必需文档"，错误文案与真实原因（未解码）不符。
- 传递链条：触发（EPUB 的 OPF href 含 %20 以外的百分号编码，如中文文件名 chapter-%E4%B8%AD.xhtml）→ 根因（`parse.rs:349-354` zip_path 仅 `replace("%20", " ")`，其余编码不解码）→ 传导（拼接路径与 ZIP 内原始条目名不一致 → `:138-140` by_name 失败 → failure("压缩包缺少必需文档")）→ 症状（整份 EPUB 解析失败，错误文案指向"缺文档"而非"未解码"，误导排障）。
- 影响范围：功能面：EPUB 解析路径；触发条件：默认配置即命中，需制作工具对 href 做了百分号编码（规范允许且常见于中文书名）；受损面：可用性——合法 EPUB 无法导入且真实原因不可见。

### 13. EPUB 无 spine 时回退顺序随机（HashMap 无序），且仅认 application/xhtml+xml
- `parse.rs:408-415`——旧规范/残缺 EPUB 要么章节顺序不可预测，要么（OEBPS 1.x 常见 text/html）全被跳过 → 空文本失败。
- 传递链条：触发（导入无 spine itemref 或 manifest 仅 text/html 的旧规范/残缺 EPUB）→ 根因（`parse.rs:408-415` hrefs 为空时回退 `items.values()`，而 items 由 HashMap 收集（`:393-407`）迭代顺序随机；`:396-400` 过滤仅认 media-type=="application/xhtml+xml"）→ 传导（无 spine → 章节按 HashMap 任意序输出；全为 text/html → hrefs 空 → 循环零次返回空串）→ 症状（章节顺序不可预测，或 `:75-79` empty_content 空文本失败）。
- 影响范围：功能面：EPUB 解析的章节排序与旧规范兼容性；触发条件：默认配置即命中，需 OEBPS 1.x/残缺包；受损面：数据正确性/可用性——顺序错乱或整份失败。

### 14. 解析进度为固定里程碑 10/35/85/100，与真实工作量无关
- `materials/mod.rs:961/724/748/751`——大 PDF 实际提取期间恒停 35%；失败重置 0；前端按百分比展示，属装饰性进度。
- 传递链条：触发（用户导入大 PDF 并观察解析进度）→ 根因（`materials/mod.rs:961` 入队固定写 progress=10、`:724` 进入 parsing 固定 35、`:748` 解析完成后 85、`:750-752` UPDATE 100，数值与页数/字节数无关）→ 传导（parse_pdf 实际提取期间无中间上报，进度恒停 35%；失败按错误路径归零）→ 症状（前端按百分比展示的进度为装饰性，用户无法据此判断是否卡死）。
- 影响范围：功能面：材料解析进度展示（Library 页与材料详情弹窗）；触发条件：默认配置必命中，文件越大越明显；受损面：可读性/可用性感知——进度与真实工作量脱钩。

## 去重与暂存（materials/mod.rs）

### 15. sha256 去重短路不校验原件存在性，原件丢失后该内容永久无法重新导入恢复
- `mod.rs:492-505`——命中既有行直接返回 deduplicated:true，发生在原件写入之前，不检查 originals/{sha256}.{kind} 是否在盘——外部删除/杀毒隔离后重导永远得到坏记录；若被方案引用则删除也被 material_in_use 阻止（:1119-1128）。
- 传递链条：触发（originals/{sha256}.{kind} 被外部删除/杀毒隔离后，用户重新导入同一文件）→ 根因（`materials/mod.rs:492-505` stage_validated 查到既有 materials 行即直接返回 deduplicated:true，检查发生在 `:507+` 原件写入之前，全程不校验盘上文件）→ 传导（复用坏记录不重写原件；重新解析走到 `:733-734` fs::read 失败报 missing_original；被方案引用时 `:1119-1128` material_in_use 又阻止删除）→ 症状（该内容永久无法重导恢复，也难删除重建）。
- 影响范围：功能面：材料导入去重与原件生命周期管理；触发条件：默认配置即命中，需原件文件丢失而 DB 行仍在；受损面：数据正确性/可用性——坏记录不可自愈，无用户侧恢复路径。

## 笔记导入（notes/mod.rs）

### 16. 单文件 md/txt 路径缺 1MB 预检，且 1MB 上限含 JSON 转义膨胀，临界笔记使整批导入失败
- `notes/mod.rs:179-184` 单文件仅查 64MB；实际约束 store.rs:786-791 记录 ≤1MB（含转义，`\n`→`\\n` 每行膨胀）——接近 1MB 的合法笔记在落库前才失败，错误泛化，同 ZIP 其余笔记一并回滚。
- 传递链条：触发（导入一条接近 1MB 的单文件 md/txt 笔记）→ 根因（`notes/mod.rs:179-184` read_notes 对单文件仅查 64MB MAX_FILE_BYTES；真实上限在 `store.rs:786-791` 按 `store.rs:18` MAX_RECORD_BYTES=1MB 对序列化后记录校验，JSON 转义使每行 `\n` 膨胀为 `\\n`）→ 传导（读取/解析均通过，直到落库时 record_too_large 才失败）→ 症状（合法编辑的笔记在最后一步失败，同 ZIP 其余笔记一并回滚，错误未指明具体笔记）。
- 影响范围：功能面：笔记导入（单文件与 ZIP 批量）；触发条件：默认配置即命中，需笔记原文接近 1MB 或行数多导致转义膨胀越界；受损面：可用性——临界笔记无法导入且整批回滚。

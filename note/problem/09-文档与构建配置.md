## P-029 归档回退路径 tar size 偏移错误，.crate 中抽取的许可文件恒为 0 字节仍计为已收录

medium | 状态：已复核 | logic | scripts/collect-licenses.mjs:223（连带点 :233、:266-267）

### 详细说明

触发条件：某 Rust 依赖的本地 registry src 目录缺失，或 src 目录顶层不含匹配 `/^licen[cs]e|notice|^copying/i` 的许可文件名（许可证文件只存在于子目录时同样落入此路径）。collect-licenses.mjs:199-201 的项目注释自述「cargo metadata/fetch 都不解包 registry src（实测确认），冷缓存单独跑 make build 时源码目录为空」——全冷缓存或新机直接执行 `make build` 时全部 Rust 依赖走归档回退；平台专属 crate（如仅 macOS 使用的 objc2-foundation）在 Windows 构建中永不解包，恒触发该路径。

实际行为：`licenseFromCrateArchive` 解析 .crate（gzip tar）时，size 字段取 `header.subarray(248, 256)`。POSIX tar 的 size 字段位于偏移 124-136，248-256 落在 linkname 区，该区在标准 tar 头中恒为 NUL，`parseInt` 结果恒为 0。因此 `matches` 集合中每个条目的字节区间长度均为 0，`tar.subarray(offset, offset + size)` 存入的是 0 字节切片；266-267 行把它写入 `desktop/src-tauri/licenses/` 并照常 `copied.push` 计入「已收录」。脚本对同一个 size 同时用于 GNU 长名条目（typeflag 'L'）的读取长度，长名解析同样失效。

连带影响：233 行 `offset += Math.ceil(size / 512) * 512` 在 size 恒为 0 时不推进数据区，头部遍历失去同步，只能以 512 字节步长在归档内滑行并偶然对齐到许可条目。按脚本原逻辑复现：serde-1.0.228.crate 遍历 1132 个「头部」后命中 `LICENSE-APACHE` 与 `LICENSE-MIT`（字节长度均为 0）；objc2-foundation-0.3.2.crate 遍历 6150 个「头部」后命中 `copying.rs`（字节长度 0）——后者与现存构建产物的文件名 `cargo-objc2-foundation-0.3.2-copying.rs` 完全一致。

用户可见后果：安装包随附的第三方许可文件为 0 字节空文件。`tauri.conf.json:38-40` 声明 `"resources": ["licenses/*"]`，该目录随安装包分发，构建期的资源暂存目录 `desktop/src-tauri/target/release/licenses/` 中同样存在 0 字节文件。`COLLECTED.md` 的「已收录 N 个」把空文件计为已收录，收集脚本以成功状态退出，脚本自述的 MIT/Apache 分发义务被静默架空。

## P-078 单条 1 MB 预检的 512 字节固定预算在最坏字段组合下不足，特定窗口内错误退化为不含文件名的 record_too_large

low | 状态：已复核 | logic | desktop/src-tauri/src/backend/notes/mod.rs:129-142

### 详细说明

触发条件：单条笔记的 content 与 title 的 JSON 序列化长度、tag 原始字节长度之和落在特定窄区间内，且该笔记的 excerpt、updated、id 与 tag 形态同时取到最坏值。

实际行为：预检公式为 `content 序列化长度 + title 序列化长度 + tag 原始字节长度 + 512`（notes/mod.rs:130-136）。落库记录还含预检未计入的字段：excerpt（正文前 90 字符，notes/mod.rs:306，serde_json 不转义非 ASCII，最多 90×4=360 字节）、updated（RFC3339 UTC，notes/mod.rs:297，最多 30 字节）、id 数字、JSON 键名与标点（notes/mod.rs:303-310 的 6 字段对象共 56 字节），以及 tag 的 JSON 转义膨胀（tag 截断到 100 字节，notes/mod.rs:150；若 tag 全部为半角引号，序列化后膨胀到 200 字节，较预检计数多 100 字节）。上述未被计入的开销合计约 560 字节，超过预检预算 512 字节，净超出约 49 字节。

落库前的 `validate_collection` 按整条记录序列化长度判定（store.rs:1267-1271），在该窗口内拒绝，错误文案为「单条记录超过 1 MB 上限」，不含文件名；预检阶段的错误文案含文件名（notes/mod.rs:138-141「笔记「{file_title}」超过单条 1 MB 上限」）。

用户可见后果：整批 ZIP 导入在最后一步失败，且错误信息不含文件名，与 notes/mod.rs:128-129 注释所述「把具体文件名带进错误，避免整批 ZIP 导入到最后一步才失败」的目的相悖，用户在最多 1000 条的归档中无从定位问题条目。

窗口宽度校准：本次复核按落库记录的字段构成逐字节重算，最坏字段组合下的净超出量约 49 字节（excerpt 362 + updated 32 + id 9 + 键名标点 56 + tag 转义增量 100 − 预检预算 512 = 47-49，视 id 位数与 updated 亚秒位数浮动），对应触发区间为「content + title + tag 之和 ∈ (1 MiB − 561, 1 MiB − 512]」，即约 51 字节宽的窗口，占 1 MiB 上限的约 0.005%。原问题记录给出的「约 555 字节 / 1 MB（约 0.05%）」高估约一个数量级：缺陷本身成立，但触发概率远低于原估计。

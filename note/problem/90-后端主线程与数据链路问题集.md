## P3

### 90#1 export_content 同步命令在主线程做全量导出渲染、哈希与写盘

- 位置：`desktop/src-tauri/src/backend/export/commands.rs:6-16`（`pub fn export_content`，同步直调，无 spawn_blocking）；重活在 `export/mod.rs`：`:401-431` 全量读 notes collection（≤10000 条 × ≤1MB）、`:433` `material_text` 全量 JOIN 无 LIMIT、`:590-596` PDF 走 `pdf::render`（系统 TTF 字体解析嵌入）/ Apkg 走 `anki.rs:219` 内存 `zip::ZipWriter` + SQLite 临时库、`:618-619` `Sha256::digest(&bytes)` 对最高 64MB（`mod.rs:20` MAX_EXPORT_BYTES）整包哈希 + `atomic_export` 写盘。
- 传递链条：①用户在导出中心选 PDF/Apkg/全量 Markdown 并确认保存；②命令在主线程串行执行「全集合读库 → JSON 反序列化 → 渲染 → 内存打包 → 整包哈希 → 写盘」；③笔记/资料量大的库（数十 MB 文本）全程窗口无响应，事件循环停摆（动画、输入、其余 IPC 全部排队）。
- 影响范围：导出中心全部 8 种格式共用此命令；对照 73#8 已把 `export_material_original`（同为整读+哈希+写盘）移入 async，导出域三命令（本条与 90#2/90#3）是同族漏网。
- 修复方向：比照 73#8，`export_content` 改 `#[tauri::command(async)]` + `spawn_blocking`（principal 传播沿用 23#7 模式）。

### 90#2 export_notes_archive 同步命令在主线程全量读笔记并内存打 ZIP

- 位置：`desktop/src-tauri/src/backend/export/commands.rs:27-35`（同步直调）；`export/notes.rs:55-104` 全量 notes → `zip::ZipWriter::new(Cursor::new(&mut bytes))` 内存归档 → 逐条 `write_all`（Deflate CPU 密集）。
- 传递链条：①设置页「导出笔记归档」确认保存 → ②主线程全量读库 + 内存压缩 → ③笔记多时窗口冻结秒级，内存峰值 = 全部笔记文本之和。
- 影响范围：笔记归档导出单一入口；与 90#1 同族。
- 修复方向：同 90#1，移 spawn_blocking。

### 90#3 import_notes 同步命令在主线程整读 64MB + 解压 + 批量 INSERT + 全量状态重建

- 位置：`desktop/src-tauri/src/backend/notes/commands.rs:7-12`（同步直调）；`notes/mod.rs:17` MAX_FILE_BYTES = 64MB、`:259-260` `std::fs::read` 整读、`:155` `ZipArchive::new` 解析、`:292-304` 循环逐条 `validate_collection` + `insert_json`、尾部 `guard.app_state()`（全集合重读）。
- 传递链条：①用户选择笔记归档文件导入 → ②主线程读 64MB 上限文件 + ZIP 解压 + 单事务批量插入 + 全量 app_state 反序列化 → ③归档越大冻结越久（GB 级 HDD 上数秒起）。
- 影响范围：笔记导入唯一入口；对照 `import_material_archive`（200MB ZIP）已在 19 个 async 命令中，本条是导入族漏网。
- 修复方向：同 90#1，移 spawn_blocking。

### 90#4 get_usage_overview / export_usage_csv_file 同步命令做无 LIMIT 五表 JOIN + O(天数×行数) 内存过滤

- 位置：`desktop/src-tauri/src/backend/providers/commands.rs:231`（get_usage_overview）、`:259-268`（export_usage_csv_file，均为同步直调）；`providers/usage.rs:306-313` `entries()` 五表 LEFT JOIN **无 LIMIT** 全量物化（代码注释自认 provider_requests 为库中最大表；86#1 裁剪后上限仍为 2 万行 + 90 天）、`:335-358` 按天循环 × 全量 entries 逐条 `OffsetDateTime::parse`（RFC3339）过滤。
- 传递链条：①用户打开用量页或导出 CSV → ②主线程执行 2 万行 × 5 表 JOIN，全行 usage_json 反序列化 + 时间解析，再 O(天数×行数) 二次循环聚合 → ③行数多时秒级冻结；每次打开用量页重复全程。
- 影响范围：用量与成本页、CSV 导出两个入口；86#1 只解决了无界增长（裁剪），未解决查询线程位置与内存物化口径。
- 修复方向：两命令移 spawn_blocking；`entries()` 增加时间窗/LIMIT 参数按需拉取（页码与 86#1 的「ledger 只显示最近 200 条」口径对齐），聚合下推 SQL。

### 90#5 Agent 步骤中断后恢复会对同一步骤重新请求模型，中断步骤的部分用量与新请求双重计费

- 位置：`desktop/src-tauri/src/backend/agent/mod.rs:775-812`（`begin_step`：`reusable` 仅在 `providers::completed_chat(current)` 为真时复用 request_id；否则 `attempt+1` 生成新 id `agent-{run}-{attempt}-{step}` 重新请求）；`providers/mod.rs:1305-1319`（错误/中断路径把 `error.usage` 随终态一起落库）。
- 传递链条：①run 在某步骤流式中途被中断（断网/崩溃/强杀，非取消）→ ②错误路径已把该次请求已产生的部分 usage 写入 provider_requests 并计入预算 → ③用户恢复 run，`begin_step` 判定该步骤未完成且旧请求未 done → 生成新 request_id 重新整段请求 → ④同一逻辑步骤产生两笔计费（部分 + 全额），无「部分用量抵扣」机制。
- 影响范围：与 AGENTS.md「终态先落盘再发送，续接不重复执行或计费」的口径在「中断在流式中途」这一窄场景不符；已完成步骤跳过（`:786-791` completed 检查）与已完成请求复用（reusable）两道防线已在位，本条是两者之间的缝隙。
- 修复方向：`begin_step` 对 `current.is_some() && !completed` 且旧请求已有部分 usage 的场景，将旧请求 usage 记为该步骤已耗基线（新请求计费时扣减），或在恢复弹窗向用户明示「该步骤将重新请求并计费」。

### 90#9 每次写命令 commit 后全量重跑 app_state（四集合全读 + 反序列化）

- 位置：`store.rs:588-600`（`finish_write` 在 `tx.commit()` 后无条件 `self.app_state()?`）；`app_state()` 读全部 4 个集合（notes ≤10000 条 × ≤1MB content，`:543-571`）。
- 传递链条：①任意 kv 域写命令（save_draft/replace_collection 等）→ ②commit 后同步全量重读四集合并反序列化 → ③返回值随每条写命令膨胀，主线程写路径变慢；快照仅用于命令返回，前端多数调用方并不消费全量 state。
- 影响范围：所有 kv 写命令；数据量大时每次保存草稿都附带一次全库读。
- 修复方向：按 namespace 增量返回（写哪个集合只重读哪个），或懒快照（返回 revision + 按需拉取）。

### 90#11 锁中毒处理三种模式并存，语义不一致

- 位置：模式 1「中毒恢复继续用」`unwrap_or_else(|p| p.into_inner())`——`backup/commands.rs:36/65/91`、`backend/commands.rs:14/147`、`maintenance/commands.rs:23`、`reveal.rs:17`、`sync/scheduler.rs:64`（73#16 修复点）；模式 2「中毒报 store_unavailable」——`agent/mod.rs:596-599`、`providers/mod.rs:1205-1208`、`sync/mod.rs:913-915`、`notes/mod.rs:283-286`、`materials/mod.rs:932-935` 等；模式 3「中毒静默跳过」`if let Ok(...)`——`learning/actions.rs:181/191`、`practice/subjective.rs:245/250`、`providers/routing.rs:565`、`security/guard.rs:204`。
- 传递链条：①持锁线程 panic（unwind）→ ②不同域对同一把 `state.store`/域锁给出三种行为：继续用（73#16 语义：不永久拒绝）/ 报错 / 静默放弃该次清理或回滚 → ③模式 3 的调用点（actions 清理、subjective 记录、routing 维护、guard 回滚）失败无日志无事件，产生静默丢失。
- 影响范围：崩溃后的恢复路径行为不一致；模式 3 有静默丢操作机会（与 B-17「写路径静默=丢操作」口径相悖）。
- 修复方向：统一为 73#16 语义（恢复继续用）或至少把模式 3 改为「恢复 + 事件记录」；逐点评估 guard.rs:204 回滚路径是否可接受静默。

### 90#12 get_material / read_material_media_chunk 的 MB 级主线程 IO

- 位置：`materials/commands.rs:54`（get_material 同步，`mod.rs:414-425` 整篇 material_text.content 经 IPC 返回，MB 级 JSON 序列化在主线程）；`:136`（read_material_media_chunk 同步，`media.rs:177-189` seek + 读 ≤256KiB，有上限但视频拖动进度条时高频调用，每次数十 ms 主线程文件 IO）。

- 修复方向：get_material 返回摘要 + 按需分页取正文；media chunk 改 async（低改动，25#4 分块协议不变）。

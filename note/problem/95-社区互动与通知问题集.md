### 95#1 notifications 无保留策略无界增长，unreadCount 全表计数与列表 LIMIT 50 口径脱节

- 位置：`desktop/src-tauri/src/backend/engagement/mod.rs:558-568`（add_notification 只写不删；全仓唯一删除路径是 community 取消时删 `room-{id}`（community/mod.rs:925/963）与整库 reset 的 `clear_all`（engagement/mod.rs:153，仅 store.rs:785 重置链路调用））；产生源 5 处（`:599-607/635-643/659-667/679-689/709-716`——`review-due-{今天}`、`tasks-due-{今天}` 每天各一条、`weekly-report-{date}` 每周日、`plan-ready-{id}-{version}` 每版本一条）；`:719-723`（`SELECT COUNT(*) FROM notifications WHERE read_at IS NULL` 全表计数）与 `:726`（列表 `LIMIT 50`）。
- 传递链条：①每日 2-4 条新行、无 retention → ②约 2-3 周未读数即可超过 50：角标显示 63，列表只展示最新 50 条 → ③更早的未读在 UI 中不可见、无法单条标记已读，只能「全部已读」一刀切；一年量级约 800 行沉淀且全部进备份（backup/archive.rs:92 含 notifications 表）。53#11 注释自认「表只增不减」但只加了索引未加保留策略。
- 影响范围：通知中心徽标与列表的数字打架（同 89#9「同一数字两处打架」类体验问题）；存储与备份体积随使用年限线性增长。
- 修复方向：写入侧加保留窗口（如删除 created_at < now-30 天 且 read_at IS NOT NULL 的行）；或 unreadCount 收敛为「可见 50 条内的未读数」并在列表尾部提示「还有 N 条较早未读」。

### 95#2 reserve() 房间状态检查在写事务之外——取消房间的窗口期内仍可建立预约与提醒

- 位置：`desktop/src-tauri/src/backend/community/mod.rs:843-851`（status/start_at 读取发生在 `store.conn` 自动提交读，非事务内）；`:860`（之后才开 IMMEDIATE 事务，事务内不再复查 rooms.status）；对向操作 cancel_room 在 `:944-949`。
- 传递链条：①reserve 在 t0 快照读判定 status='scheduled' → ②cancel_room 在 t1 提交 status='cancelled'（同时删除提醒与通知） → ③reserve 在 t2 取得 IMMEDIATE 锁后直接 INSERT 预约与提醒（`:896-897`），不再复查房间状态 → ④已取消房间残留 active 预约与 reminder 行：room_row 显示 reserved=true、stats.active_reservations 虚增。提醒投递本身被 claim_due 的 `rooms.status='scheduled'` 联查兜住（95#3 的 SQL 已见）不会误触发，但与项目自己在 31#35/34#11 修过的 TOCTOU 模式同型——34#11 注释还自认「预约的重叠检查」曾是同类问题。
- 影响范围：并发点击预约+取消的窄窗口；统计口径失真与用户困惑（「取消了还能约上」）。
- 修复方向：把 status/start_at 读取移入 IMMEDIATE 事务内，或 INSERT 前加 `SELECT status FROM community_rooms WHERE id = ? AND status = 'scheduled'` 复查；附带：`:849` 毒行 start_at（34#19 场景）使 reserve 整体报错，与 create_room 跳毒行的策略不一致，宜对齐。

### 95#3 claim_due_reminders 用 DEFERRED 事务 + UPDATE 无 delivered_at 守卫——并发领取可重复投递

- 位置：`desktop/src-tauri/src/backend/community/mod.rs:978`（`store.conn.unchecked_transaction()` = DEFERRED）；`:979-987`（快照读 `WHERE … delivered_at IS NULL`）；`:995-998`（`UPDATE … SET delivered_at = ?1 WHERE id = ?2` 无 `AND delivered_at IS NULL` 守卫）；前端并发触发点 `desktop/src/App.tsx:186-203`（60s setInterval 与 visibilitychange 立即 claim 互不等待，上一轮未返回即再发 invoke）。
- 传递链条：①两个 claim 并发进入 → ②双方 DEFERRED 快照都读到同一批 delivered_at IS NULL 的行 → ③双方都执行无守卫 UPDATE（盲写，无 BUSY_SNAPSHOT 拦截）并各自 emit `community.reminder_due` 事件 → ④前端 notify() 重复弹层、events 流多出重复事件（插件/集成消费方受污染）。
- 影响范围：提醒重复弹层；与项目已建立的「写路径一律 IMMEDIATE + 条件守卫」模式（25#18/31#35/34#11）不一致；单窗口下概率低，切换窗口可见性时可达。
- 修复方向：改 `store.write_transaction()`（IMMEDIATE），UPDATE 加 `AND delivered_at IS NULL` 并以 changed==0 跳过该行的事件发送。

- 位置：`desktop/src-tauri/src/backend/community/mod.rs:825`（创建即 'scheduled'）、`:947`（唯一状态迁移是改 'cancelled'）、`:1046-1051`（`active_reservations: count(… "cancelled_at IS NULL")`——不看结束时间）。

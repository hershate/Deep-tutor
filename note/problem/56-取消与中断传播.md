# 56 · 取消与中断传播（第二十三轮）

> 审计方式：七条取消链路（agent/provider/materials/focus·logout/sync/插件/
> 进程退出）逐阶段推演「取消信号到达时该阶段在做什么」。主审对三条最强
> 发现逐行亲验（materials UPDATE 无状态条件、stop_all `?` 链、tools 无取消点）。
> 「中」按本仓口径记 P3。已有测试覆盖点见文末注记，不重复。

## P3

### 56#1 materials 取消的 UPDATE 无状态条件——与解析完成竞态可致永挂 'cancelling'、重启后被错标 'cancelled'

- 位置：`desktop/src-tauri/src/backend/materials/mod.rs:1139-1143`（主审亲验）；守卫仅靠 :1118-1125 的先验 SELECT。
- **传递链条（构造时序）**：① 用户点「取消解析」→ ② 取消命令先 SELECT 校验 job 活跃，随后 `UPDATE material_jobs/materials SET status='cancelling' WHERE id=?`（无状态条件）→ ③ 同一毫秒窗内 worker 的 run_job Ok 事务（:870-898）提交 parsed/done → ④ 晚到的 UPDATE 把已完成的 job+material 覆写为 'cancelling'，而 Ok 路径再无后续写、schedule_next 已摘除 active → ⑤ **永久 cancelling**：该资料再点解析报 job_active（active_job 含 cancelling），直到重启 recover 按 cancel_requested=1 翻 'cancelled'——但 material_text 实际已在库，重启后标签错为「已取消」。
- **影响范围**：恰在解析完成瞬间点取消的用户（毫秒窗）；后果为该资料解析功能被锁死至重启 + 状态错标（文本其实在，界面说取消）。无数据损坏。对照：其余七域（agent/practice/knowledge/learning/lecture/projects/subjective）全部有 `AND status='running'`+changed==0 守卫，materials 是唯一漏网。修复：UPDATE 加状态条件 + changed==0 转竞态码。

### 56#2 stop_all 的 `?` 链短路 + focus 不在停机集合——登出吞错后旧用户任务全量续跑

- 位置：`desktop/src-tauri/src/backend/security/guard.rs:21-29`（主审亲验）；maintenance/commands.rs:20-28 与 reset :86-91 同款。
- **传递链条（根因组合）**：① 登出/切换用户/清理触发 stop_all → ② 七域串行 `?`：agent::stop 只等 15s → ③ agent 工具执行无取消点（tools.rs:413-699 全程无 flag 检查，主审 grep 亲验；web.fetch/search 阻塞 reqwest 单次可 >60s）→ ④ 15s 超时 Err(run_active) → ⑤ `?` 短路：practice/knowledge/learning/providers/sync/materials 全部不停 → ⑥ 后果分三种可见性：**logout**（security/mod.rs:1005-1008 `let _ =` 吞错）——登出显示成功但旧用户的解析/同步/流式继续跑（worker 继承旧 principal 写旧用户库，无跨用户污染但用户以为已停）；login 切换（guard.rs:91-96）reject 可重试；清理/vacuum 报错。另 stop_all 列表无 reports 域——focus_sessions 停留 running 按墙钟计时（reports/mod.rs:230-260），该用户再登录见「进行中且秒数疯涨」，仅重启收口。
- **影响范围**：登出/切换时恰有 agent 运行且卡在无取消点工具的用户（web 工具慢时可复现）——旧用户后台任务全量续跑 + focus 计时疯涨；无数据损坏、无跨用户写入。修复：stop_all 逐域独立停并汇总错误 + 补 reports + 工具循环加取消点。

### 56#3 sync 取消的同族竞态——cancel 与 finish(done) 交错时永挂 'cancelling' 至重启

- 位置：`desktop/src-tauri/src/backend/sync/mod.rs:848-851`。
- **传递链条**：① 用户点取消同步任务 → ② cancel 先 job() 读状态 + active 查找（active 在 finish() 之后才移除）→ ③ 同窗内 worker finish() 提交 done → ④ 晚到的 `UPDATE sync_jobs SET status='cancelling' WHERE id=?`（无状态条件）覆写 done → ⑤ 无人再翻——列表永挂「取消中」直到重启 recover 翻 'cancelled'，且文案谎称「按已取消收尾」而远端实际已确认上传完成。
- **影响范围**：恰在任务完成瞬间点取消的用户（毫秒窗）；后果为任务列表状态错误+重启前不可再取消（已非 active，cancel 报 no_active_request）。新任务不受阻（sync_busy 只查 active map）。修复同 56#1（状态条件+changed==0）。

### 56#4 finish_focus 不封顶 min(planned)——挂机后点完成把膨胀秒数计入报告

- 位置：`desktop/src-tauri/src/backend/reports/mod.rs:354-384` vs `:396-423`。
- **传递链条**：① 用户开启 25 分钟专注后离开电脑数小时（会话保持 running、按墙钟累计）→ ② 回来点「完成」→ ③ finish_focus 落库 `actual_seconds = now - started_at`（未封顶的墙钟秒，如 4 小时）→ ④ status=completed 且秒数进入 focus_minutes 报告与日历——远超 planned；对照崩溃恢复路径（:396-423）会封顶 `min(actual, planned)`。cancel 路径的膨胀只影响展示（focus_minutes 只统计 completed）。
- **影响范围**：挂机后点「完成」（而非取消）的用户——专注统计虚高污染周报/日历/热力图；一次性错误，事后可手动打卡修正。修复：finish 对齐 recover 的 min(planned) 封顶（或超时自动收卷）。

## 信息性

- **56#5** agent_tool_calls 崩溃残留。链条：① 工具执行中进程崩溃（非取消）→ ② 重启 agent::recover 只翻 agent_runs 状态 → ③ agent_tool_calls 行永留 status='running'。影响：表不进 UI（纯 DB 残留）；同 id 重放报 tool_active 需换 id——低危。
- **56#6** 路由取消双向小竞态。链条：① cancel 读到 running、finish 先提交 done → ② cancel 仍发 route_cancel_requested 且 Ok(true)——事件序 cancel_requested→completed（终态如实）；反向：cancel 先落 cancelling、流已读完 [DONE] 不再查 flag → finish 覆写 done（输出完整）。影响：仅事件序/反馈层矛盾，终态与数据均如实。
- **56#7** 审批跨 run 存活。链条：① run 等待审批时被取消 → ② pending 审批不清理 → ③ 用户仍可 approve（memory 照写）。影响：审批语义与 run 生命周期脱钩（产品可辩：用户明确批准仍有效）；UI 悬空调用卡片为 31#41 已知项。
- **56#8** sync 远端半态（有明示）。链条：① 取消检查只在阶段边界 → ② 历史 PUT 完成后取消→远端孤儿版本（retention 下次清理）；主 PUT 完成后取消→远端已更新而本地未导入、任务标 cancelled → ③ 取消文案已明示「远端请求可能已执行，请核对任务与远端状态」。影响：需用户人工核对一次；S3/WebDAV 单次 PUT 无分片残留。
- **56#9** 进程退出无钩子。链条：① 关窗/restart → ② 进程直接杀线程（无 stop_all/RunEvent）→ ③ 在途任务靠 outbox 事务内落库 + 重启 recover 续接（测试在案）。影响：设计内边界；import 中途被杀的 staged 资料不自动续解析（界面可见「已暂存」，需手动开始）。
- **56#10** 取消的计费口径。链条：① 上游 usage 在末 chunk → ② 中途取消时几乎恒 NULL → ③ 会话预算回退 LENGTH(output)/2 估算计入、实费 0（cancelled_cost 单列）。影响：预算为保守近似、不虚报；口径有注释自认（08#7/25#17）。

## 正向结论（状态如实、已闭环）

- **七域取消守卫在位**：agent/practice/knowledge/learning/lecture/projects/subjective 的 cancel 全带 `WHERE status='running'` + changed==0 + 终态 guard 写；无双终态、无覆盖已落终态。
- **流式中途取消**：100ms 粒度检查、partial 文本/推理/工具/usage 全保留、provider.chat_cancelled 事件、取消不触发 failover、熔断对 cancelled 中性（07#5）；取消后迟到 delta 物理不可能落库（同线程）。
- **failover 与取消**：循环头 route_cancelled 检查保证 attempt#1 取消后 #2 不发出。
- **materials 解析线程**：逐页/逐 zip 条目/逐 XML 事件有取消点；34#12 阻止迟到进度覆写终态；recover（cancel_requested→cancelled / 否则回 queued）正确。
- **插件 dispatch vs reload**：同一写事务内快照订阅+投递，与 reload/uninstall 的另一连接写事务经 SQLite 写锁串行化，FK CASCADE 兜底——无撕裂/双投递；dispatch 失败连带回滚业务事件（fail-closed）。
- **崩溃续读**：流式中途被杀的 provider_requests output 列空但 delta 事件在库，chat() 重建兜底（mod.rs:945-966）。

# 56 · 取消与中断传播（第二十三轮）

> 审计方式：七条取消链路（agent/provider/materials/focus·logout/sync/插件/
> 进程退出）逐阶段推演「取消信号到达时该阶段在做什么」。主审对三条最强
> 发现逐行亲验（materials UPDATE 无状态条件、stop_all `?` 链、tools 无取消点）。
> 「中」按本仓口径记 P3。已有测试覆盖点见文末注记，不重复。

## P3

### 56#1 materials 取消的 UPDATE 无状态条件——与解析完成竞态可致永挂 'cancelling'、重启后被错标 'cancelled'

- 位置：`desktop/src-tauri/src/backend/materials/mod.rs:1139-1143`（主审亲验：`UPDATE material_jobs SET …status='cancelling' WHERE id=?` 与 materials 同款，均无 `AND status IN(...)`；守卫仅靠 :1118-1125 的先验 SELECT）
- **构造时序**：worker 的 run_job Ok 事务（:870-898 提交 parsed/done）恰落在取消命令的 SELECT 与 UPDATE 提交之间 → job+material 被覆写 'cancelling'，而 Ok 路径再无后续写、schedule_next 摘除 active → **永久 cancelling**；enqueue 因 active_job 含 cancelling 永报 job_active，直到重启 recover（cancel_requested=1）翻 'cancelled'——但该资料实际已解析完（material_text 在库），重启后标签错为「已取消」。
- **对照**：同族守卫在其余七域全部在位（agent mod.rs:1097、practice :1386、knowledge :746、learning :828-837、lecture.rs:781、projects :508、subjective :594-597 均 `AND status='running'` + changed==0）——materials 是唯一漏网。修复：UPDATE 加状态条件 + changed==0 转竞态码。

### 56#2 stop_all 的 `?` 链短路 + focus 不在停机集合——登出吞错后旧用户任务全量续跑

- 位置：`desktop/src-tauri/src/backend/security/guard.rs:21-29`（主审亲验：agent→practice→knowledge→learning→providers→sync→materials 串行 `?`，任一步失败后续全不停）；maintenance/commands.rs:20-28 与 reset :86-91 同款。
- **根因组合**：`agent::stop` 只等 15s，而 agent 工具执行**无取消点**（tools.rs:413-699 全程无 flag 检查，主审 grep 亲验；web.fetch/search 阻塞 reqwest 单次可 >60s）→ 15s 超时 Err → 整链中断。
- **三种可见性**：① **logout**（security/mod.rs:1005-1008 `let _ =` 吞错）——登出「成功」但旧用户的解析/同步/流式全部继续跑（worker 继承旧 principal 继续写旧用户库，无跨用户污染但用户以为已停）；② login 切换（guard.rs:91-96）reject 可重试——可见；③ 清理/vacuum 命令报错——可见。
- **focus 缺席**：stop_all 列表无 reports 域——登出/切换后 focus_sessions 停留 running、按墙钟持续计时（reports/mod.rs:230-260），下次登录该用户见「进行中且秒数疯涨」，仅下次重启 recover 收口。修复：stop_all 改为逐域独立停并汇总错误；补 reports/focus；工具执行循环加取消点。

### 56#3 sync 取消的同族竞态——cancel 与 finish(done) 交错时永挂 'cancelling' 至重启

- 位置：`desktop/src-tauri/src/backend/sync/mod.rs:848-851`（UPDATE 无状态条件，前置仅 job() 读 + active 查找，active 在 finish() 后才移除）。构造：worker finish() 提交 done 落在读与 UPDATE 之间 → 行被覆写 'cancelling' 无人再翻 → 列表永挂「取消中」直到重启 recover 翻 'cancelled'（文案谎称按已取消收尾，实际远端已确认上传完成）。新任务不受阻（sync_busy 只查 active map）。修复同 56#1。

### 56#4 finish_focus 不封顶 min(planned)——挂机后点完成把膨胀秒数计入报告

- 位置：`desktop/src-tauri/src/backend/reports/mod.rs:354-384`（complete/cancel 共用，落库墙钟秒）vs `:396-423`（recover 封顶 min(planned)）。长时间挂机后 complete_focus 把膨胀秒记为 completed 并进 focus_minutes 报告（cancel 的膨胀仅展示层）。两处结算口径应统一为 recover 的封顶语义。

## 信息性

- **56#5** agent 工具执行中崩溃（非取消）→ `agent_tool_calls` 永留 status='running'（agent::recover 只翻 agent_runs，无回收；表不进 UI，纯 DB 残留；同 id 重放报 tool_active）。
- **56#6** 路由取消双向小竞态：cancel-vs-done 交错时事件序矛盾（cancel_requested→completed，终态如实）或取消反馈被 done 覆写（输出完整，终态如实）——终态均如实，仅反馈层。
- **56#7** run 取消不清理 pending 审批——审批跨 run 存活仍可 approve（memory 照写）；UI 显示悬空调用卡片（31#41 自认）。
- **56#8** sync 远端半态有明示（取消文案「远端请求可能已执行，请核对」）：历史 PUT 后取消→远端孤儿版本待 retention 清理；主 PUT 后取消→远端已更新而本地未导入。S3/WebDAV 均单次 PUT 无分片残留。
- **56#9** 进程退出无钩子：restart 立即重启、关窗杀线程，无 stop_all——outbox 事务内落库 + events_since 续接兜底（测试在案）；import_material_* 中途被杀的 staged 资料不自动续解析（可见半态）。
- **56#10** 取消时 usage 几乎恒 NULL（上游 usage 在末 chunk）→ 预算回退 LENGTH/2 估算计入、实费记 0——一致但近似口径（08#7/25#17 注释自认）。

## 正向结论（状态如实、已闭环）

- **七域取消守卫在位**：agent/practice/knowledge/learning/lecture/projects/subjective 的 cancel 全带 `WHERE status='running'` + changed==0 + 终态 guard 写；无双终态、无覆盖已落终态。
- **流式中途取消**：100ms 粒度检查、partial 文本/推理/工具/usage 全保留、provider.chat_cancelled 事件、取消不触发 failover、熔断对 cancelled 中性（07#5）；取消后迟到 delta 物理不可能落库（同线程）。
- **failover 与取消**：循环头 route_cancelled 检查保证 attempt#1 取消后 #2 不发出。
- **materials 解析线程**：逐页/逐 zip 条目/逐 XML 事件有取消点；34#12 阻止迟到进度覆写终态；recover（cancel_requested→cancelled / 否则回 queued）正确。
- **插件 dispatch vs reload**：同一写事务内快照订阅+投递，与 reload/uninstall 的另一连接写事务经 SQLite 写锁串行化，FK CASCADE 兜底——无撕裂/双投递；dispatch 失败连带回滚业务事件（fail-closed）。
- **崩溃续读**：流式中途被杀的 provider_requests output 列空但 delta 事件在库，chat() 重建兜底（mod.rs:945-966）。

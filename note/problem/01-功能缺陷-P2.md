## 1. 同步"清除已保存凭据"开关在 S3 与 WebDAV Basic/Bearer 下必然失败，旧凭据被原样回写

- 前端：`desktop/src/components/SyncPanel.tsx:52`——勾选 `clearCredentials` 后把
  `password/accessKey/secretKey` 置空字符串提交；`SyncPanel.tsx:144` 开关文案
  "保存后删除系统密钥库中对应的同步凭据"。
- 后端：`desktop/src-tauri/src/backend/sync/mod.rs:350-367`——S3 分支先按空串删除
  access/secret 两把 key，随后第 367 行 `credentials(service, &config)?` 立即强制要求
  两把 key 均存在（缺失返回 `sync_credentials_missing`）；
  `sync/mod.rs:369-379`——WebDAV 非 `none` 认证同样在删除后强制校验；
  `sync/mod.rs:394-397`——失败路径 `restore_credentials` 把刚删除的旧凭据恢复回密钥库。
- 影响：S3 档案勾选"清除凭据"后保存必报"S3 Access Key 未配置"，WebDAV Basic/Bearer
  报"WebDAV 凭据未配置"，且密钥库旧凭据被恢复、配置未保存——清除功能完全不可用，
  与开关文案相反。仅 WebDAV + 无认证组合不受影响。
- 传递链条：用户在同步配置弹层勾选"清除此服务的已保存凭据"后点"保存配置" → 根因 `sync/mod.rs:367/378` 在按空串删除密钥后仍无条件调用 `credentials()` 强制要求密钥存在 → `SyncPanel.tsx:52` 把空串作为 accessKey/secretKey/password 提交，`save_config` 先 `backend.delete`（`sync/mod.rs:353/361/371`）再校验得 `sync_credentials_missing` → 失败分支 `sync/mod.rs:394-395` `restore_credentials` 把旧凭据写回密钥库 → 用户看到"未配置"报错、配置未保存、密钥库里旧凭据原样保留。
- 影响范围：功能面为 saveConfig 命令与 sync-s3-access/sync-s3-secret/sync-webdav 密钥库条目；触发条件为用户主动勾选清除开关且认证方式非 none（S3 或 WebDAV Basic/Bearer）才命中，默认不勾选、全新安装主流程不触发；受损面为可用性——清除功能完全不可用且报错文案与真实意图相反。

## 2. 路由 failover 第二次切换起前端丢失上游请求 id，Agent 直播输出冻结

- 后端：`desktop/src-tauri/src/backend/providers/routing.rs:994-1010`——候选循环中

  `providers/mod.rs:1107-1115`——`provider.chat_delta` 携带的是上游 id，

  route_attempt→upstreamRequestId 映射外，`PlanGenerator.tsx:111-118`、`Practice.tsx:58-61`、

- 影响范围：功能面为同步配置弹层表单与 saveConfig 命令；触发条件为凡从 S3 切到 WebDAV 保存的用户必命中（含加载过已存 S3 配置的场景），全新安装直接选 WebDAV 不命中、主流程 S3 使用不受影响；受损面为可用性——WebDAV 保存被阻断且错误文案误导排障方向。

- 传递链条：用户首次配置 WebDAV 同步并触发上传（含自动同步首跑） → 根因 `sync/versions.rs:179-190` upload 的第一个远端操作就是对 `{base}/versions/{timestamp}-{id}-{sha256}.json` 直接 PUT，全 src-tauri 无任何 MKCOL（grep 实证） → RFC 4918 下父集合不存在时服务器返回 409（Apache/Nextcloud/Synology/IIS 等主流实现均如此） → 首次上传必失败，报"HTTP 409"且无建目录指引，用户须离开应用手工预建 versions/ 目录；测试桩 `versions_tests.rs:21-35` 把任意路径直接插内存 map 返回 201，隐式"创建"父目录掩盖了该行为 → 缺陷直到真实服务器才暴露。
- 影响范围：功能面为 WebDAV 同步的上传/自动同步/历史版本链路；触发条件为凡在符合 RFC 4918 的 WebDAV 服务器上从零首次上传即命中（默认主流程首跑必现，服务器端已预建 versions/ 或 S3 模式不触发）；受损面为可用性——WebDAV 同步开箱不可用且报错无指引。

## 31. KaTeX 样式仅由懒加载的 Library 页引入，学习空间讲义公式首次访问前渲染为双份乱码 DOM
- 前端：`pages/Library.tsx:7` 引入 katex.min.css（懒块）；`pages/StudyRoom.tsx:3-6` 用 rehype-katex 渲染讲义公式却不引样式（构建产物实证：katex 规则仅在 Library CSS 块，主包仅 1 处不覆盖 StudyRoom 的规则）。
- 影响：无 katex CSS 时 `.katex-mathml` 不被隐藏——每个公式同时渲染 MathML 与未加样式 HTML 两份呈重复乱码，直到用户某次访问"笔记与 Wiki"页后全局生效；主流程（学习空间阅读）视觉功能缺陷。
- 传递链条：用户首次打开学习空间阅读含公式的讲义 → 根因 katex 样式唯一入口是懒加载块内的 `Library.tsx:7`（App.tsx:32 经 lazy 动态 import），而渲染讲义公式的 `StudyRoom.tsx:3-6` 用 rehype-katex 却不引入该 CSS（构建产物实证 katex 规则仅落在 Library 的 CSS 块） → StudyRoom 首访时样式块尚未加载 → `.katex-mathml` 不被隐藏，每个公式同时渲染 MathML 与未加样式 HTML 两份 → 用户看到重复乱码，直到某次访问"笔记与 Wiki"页把 Library 块加载后全局生效。

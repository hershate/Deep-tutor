## P3

### 112#1 stop_all 失败的回滚路径上，recover 无「仍活跃」守卫覆写仍在执行的任务终态——状态被活线程二次覆写、事件乱序

- 位置：`desktop/src-tauri/src/backend/learning/mod.rs:1008`（recover 路径 `UPDATE learning_plans SET status=?… WHERE id=?` **无 status 条件**；对照 :1007 steps UPDATE 有 `AND status='running'`）；同型：`agent/mod.rs:1310`、`knowledge/mod.rs:914`、`practice/mod.rs`（recover 路径 UPDATE 均无活跃态守卫；对照各自 fail 路径 :884/:732/:693 都有 `AND status IN (…)` 守卫）。触发面：`guard.rs:228-231`（stop_all Err → resume(previous) → 十域 recover）。
- 传递链条：①switch 时某域 stop 超时（agent/practice 15s deadline 等，stop_all 返回 stop_failed）→ ②回滚路径 resume(previous) 无差别跑十域 recover → ③learning::recover 把 running 计划行翻 interrupted 并发 plan.interrupted 事件——但内存中的生成线程还活着（stop 失败即意味着没停干净），稍后写自己的终态 → ④「done 覆盖 interrupted」或「interrupted 覆盖 done」的状态二次覆写、事件乱序/重复；用户看到的方案状态与真实执行结果不符（如已完成被标「可从已保存步骤恢复」）。
- 影响范围：切换用户时恰有长任务在跑且停机超时的组合（窄但后果是状态失真）；stop_all 成功的常规路径（线程已 join）不受影响。
- 修复方向：recover 的 plan/run/session 行 UPDATE 补 `AND status IN ('running','cancelling')` 守卫（与各自 fail 路径、materials 的 transition 守卫 34#12 对齐）——活线程终态写入仍在，被翻行不再发生。

### 112#2 materials::recover 的 spawn_job 错误经 `?` 短路——同域其余 queued 任务不被重排，仅靠后续完成回调自愈

- 位置：`desktop/src-tauri/src/backend/materials/mod.rs:1269`（`spawn_job(app.clone(), state, id, job_id, false)?`）；spawn_job 对 active 命中返回 Err（:942-944 job_active）。
- 传递链条：①stop_all 失败（或 cancel 竞态）后仍有一个活跃解析 → ②recover 循环先遇到该 id → spawn_job 返回 job_active → ③`?` 上抛中断整个 recover 循环，排在后面的其余 queued 任务不被 transition/spawn → ④闸门已复位（accepting=true），但重排停在该行——直到活跃解析结束后 schedule_next（:1203-1236）逐个补起；若活跃解析挂死则后续 queued 永远排队（同 107#1 的表象，触发面更窄）。
- 影响范围：stop 失败/取消竞态后的批量重排；常规路径（stop 成功、无活跃）不触发。
- 修复方向：spawn 失败（job_active）时 continue 而非 `?`；其余错误可收集为警告。

## 信息

### 112#3 resume(actual) 在 WORKSPACE_SWITCH 写锁内串行跑十域 recover——僵尸行多时切换尾部全 UI 停顿

- 位置：`desktop/src-tauri/src/backend/security/guard.rs:273`（`resume(actual)` 在 :207 `_write` 守卫作用域内执行）；guard.rs:326（其余命令排队在读锁后）。
- 传递链条：①login/切换成功 → ②handler 返回响应后，switch 尾部持写锁跑十域 recover（每行一个小事务+事件插入+可能的解析线程 spawn）→ ③期间进程内全部其他 invoke 排队 → ④崩溃残留行多时（例如导入后首次登录）切换「完成」后仍有可感的全 UI 停顿。锁序经全量核对无反向获取路径（WORKSPACE_SWITCH 全部使用点仅 guard.rs 4 处），无死锁，纯吞吐面。
- 影响范围：僵尸行多的库的登录/切换尾部延迟；常规库为毫秒级。
- 修复方向：recover 段挪出写锁（换库提交完成后释放再恢复），或 resume_background 放后台线程执行（recover 幂等可承受并发窗口）。

### 112#4 maintenance 失败路径也恢复后台——「操作失败=后台仍停机」的直觉被打破

- 位置：`desktop/src-tauri/src/backend/maintenance/commands.rs:72/106`（`resume_background(&app)` 在 result Err 时照跑）。
- 传递链条：①vacuum/cleanup 中途失败（操作 Err）→ ②收尾仍复位 accepting + 重启调度器 + recover 重排 → ③用户以为失败后任务仍停着，实际解析已重新开跑 → ④重试 maintenance 会再 stop_all（实害有限）；但「失败后无后台活动」的心智模型不再成立，排障时误判。
- 影响范围：maintenance 失败场景的语义清晰度；无数据损坏。
- 修复方向：失败时只复位 accepting 闸门（防 107#1 停摆）不重排任务；或文档化「失败即恢复」语义。

### 112#5 vacuum/cleanup/切换把在途解析打回零进度重启——107#1 修复的既定代价记录

- 位置：`desktop/src-tauri/src/backend/materials/mod.rs:1268`（recover 把 parsing 任务回 queued 且 progress=10，从头重解析）。
- 传递链条：①大 PDF 解析到 80% → ②用户跑一次「数据库整理」或切换用户 → stop_all 取消解析 → ③resume_background 的 recover 回 queued → ④重解析从零开始，大文件用户可感（分钟级重做）。与冷启动同口径，属 107#1 消除「静默停摆」的权衡，非缺陷——记录供未来断点续解析排期。
- 影响范围：维护操作与在途大文件解析的交集场景。
- 修复方向：解析断点化（进度持久化）后排期消除。

## 核实通过项（免后续复查）

- **孤儿清理与 queued 任务文件面交集**：scan_orphans 期望集来自 `materials` 表全量 sha256（maintenance/mod.rs:262-293，不查 job 状态）——queued/parsing 任务必有带 sha256 的 materials 行，原图恒在期望集不被删；24h 宽限只作用于临时名；delete() 删 materials 行时 material_jobs 经 FK CASCADE 连带（无反向悬挂）。
- **reset 空库安全**：十域 recover 对 reset 后空库全部 SELECT 空/UPDATE 0 行，materials 只复位闸门无 spawn；start_scheduler 起后 run_due 因无 sync 配置直接返回——无 panic 无错误。
- **switch 回滚语义**：stop_all 成功后的回滚路径对 previous 跑 recover 家族语义正确（恢复到切换前状态，与 logout 同口径）；stop_all 失败路径见 112#1。
- **锁序**：WORKSPACE_SWITCH 使用点全量枚举（guard.rs:13/207/280/326），十域 recover 与调度器线程无任何反向获取路径，无死锁（含 std RwLock 非重入检查）。
- **principal 传播**：resume_background 四条调用点均在 with_user/with_principal 内（guard.rs:223、security/mod.rs:1356、maintenance/commands.rs、backend/commands.rs）；解析/调度线程经 security::thread_builder/spawn 继承 principal；无 principal 时十域仅 eprintln 不中断调用方。
- **reports::recover 与 stop 的关系**：stop_all 的 reports::stop 已做同样行翻转（无事件），四条 resume 语境中 recover 对 focus 域是幂等空转——正确无副作用。

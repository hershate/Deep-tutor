### 94#1 同步调度锚点按 TEXT 主键字典序取「最新」行——81#6 修复未按注释实现，可致每分钟上传风暴并摧毁版本历史

- 位置：`desktop/src-tauri/src/backend/sync/scheduler.rs:32-35`（`SELECT finished_at, status FROM sync_jobs WHERE kind = 'upload' ORDER BY id DESC LIMIT 1`——注释 28-31 行声称「锚点按 rowid 取最新一行……rowid 单调递增即真实写入顺序」，排序键实际是 `id` 列而非 rowid）；`sync/mod.rs:153-157`（`sync_jobs.id TEXT PRIMARY KEY`）；`mod.rs:711-714`（id 生成 `format!("sync-{}-{}", std::process::id(), NEXT_JOB.fetch_add(1, …))`——NEXT_JOB 为全进程共享计数器，check/upload/download/import/restore 每种任务都消耗）。
- 传递链条：①TEXT 主键字典序 ≠ 时间序：`"sync-1234-9" > "sync-1234-12"`（'9'>'1'，计数器跨过 10 即乱序）；pid 每次重启变化，重启到更小 pid 后所有新行字典序低于旧行（如旧 `sync-9800-3` 恒为最大）→ ②`ORDER BY id DESC LIMIT 1` 选中的是「字典序最大」而非「最近」的 upload 行 → ③`run_due`（scheduler.rs:52-54）用该错误行的 finished_at 判 `anchor + 24h > now`：锚点停在重启前的旧行上，条件恒假 → ④调度线程每 60 秒 tick 一次（scheduler.rs:75 `tick % 60 != 59` 跳过），每个 tick 都判定到期并启动一次 upload——每次 upload 对远端 PUT 两个对象（当前+历史）+ 双 GET 回读 + retention 清理（versions.rs:213-248，保留 10 个版本：`versions.iter().skip(10)` 之外全删）→ ⑤约 10 分钟内风暴版本把 retention 窗口填满，**真实的版本历史被挤出保留窗口不可逆销毁**；sync_jobs 表每分钟 +1 行无限增长；若错选行恰为 failed，1h 退避也被误判为到期，变成每分钟重试。git 证据：commit 3d1f58b4（81+85 修复）把 `MAX(finished_at)` 换成 `ORDER BY id DESC`，从未真正使用 rowid。
- 影响范围：开启自动同步（auto_sync）的用户；触发条件常见——进程内任务计数跨过 10、或重启后 pid 变小（每次重启 pid 随机，约半数概率变小），二者任一即锚点失准。远端为用户自配置的 WebDAV/S3：写放大、流量/存储费用、版本历史丢失。
- 修复方向：排序键改 `ORDER BY rowid DESC LIMIT 1`（或 `ORDER BY created_at DESC, rowid DESC`）；补回归测试：构造 `sync-9999-1`（字典序最大、时间最旧）与更新的 `sync-1000-5`，断言锚点取后者；风暴场景（错锚点+auto_sync）断言 60s 内不重复启动。

## P3

### 94#2 恢复/导入供应商配置逐档案 upsert 无总事务——中断留下半套配置且无回滚

- 位置：`desktop/src-tauri/src/backend/providers/sync_config.rs:184-248`（`for profile in config.providers { … super::upsert(app, state, input).map_err(|e| …("已导入 {applied} 个档案后中断…"))? }`，upsert 各自提交，整批 + routing::save_settings + set_active 三段均无总事务；E-2 注释自认「逐档案 upsert 会中途失败留下部分提交」）；调用链 `sync/mod.rs:560-573, 618-623`（restore 分支 destination 为空 → import）。
- 传递链条：①用户从远端版本恢复供应商配置 → ②import 循环进行到第 N 个档案时进程被杀/断电/单档案校验失败 → ③本地 provider 档案部分覆盖为新版本、路由与 active 仍是旧的；`recover()`（mod.rs:872）只把 job 标 interrupted，无回滚入口 → ④用户面对与所选远端版本不一致的混合配置，仅错误消息里的「已导入 N 个」可作线索。
- 影响范围：供应商配置恢复/导入（从 .json 文件导入与从同步版本恢复两条路径）；中断概率低但后果是静默混合状态。
- 修复方向：整批包进单事务（upsert/routing/set_active 同事务提交）；或导入前把本地 providers 快照到备份表、失败/中断时一键回滚。

### 94#3 网页导入只认 UTF-8 且不探测 meta charset——中文常见 GBK/GB18030 站点导入必败

- 位置：`desktop/src-tauri/src/backend/web/mod.rs:222-230`（Content-Type 带 charset 且非 utf-8 即拒）、`:251-252`（`String::from_utf8(bytes)` 失败报 `web_encoding_unsupported "网页必须使用 UTF-8 编码"`）；无 meta charset/BOM 探测与转码层。
- 传递链条：①用户导入 GBK/GB18030 编码的中文页面（中文互联网大量存在，且多数响应头不带 charset、编码声明写在 HTML meta 里） → ②`from_utf8` 校验失败 → ③导入必败；错误文案「网页必须使用 UTF-8 编码」未给出「另存转码后再导入」的自救指引。
- 影响范围：URL 抓取与网页文本导入功能对目标用户群（中文学习者）的可用性；安全面正确（拒绝而非乱码入库）。
- 修复方向：引入 `encoding_rs`/`chardetng`（检查 F 盘现有缓存后再定）：响应头 charset → meta charset → 探测三级，统一转 UTF-8 后再解析；至少在错误信息中说明原因与替代做法。

### 94#4 24h 调度全程墙钟、无时钟回拨钳制——回拨后自动同步长期停摆

- 位置：`desktop/src-tauri/src/backend/sync/scheduler.rs:52-54`（`if anchor + hours(interval) > OffsetDateTime::now_utc()`——anchor 来自库内 RFC3339 墙钟，无 `min(anchor, now)` 钳制，无单调时钟水位）。
- 传递链条：①系统时间被回拨（NTP 纠偏/手动改拨）→ ②库内 upload 行 finished_at 落在「未来」，`anchor+24h > now` 恒真 → ③自动同步停摆直至真实时间追过 anchor+24h（可达数月），无任何告警；前拨则一次性立即触发（影响小）。
- 影响范围：仅时钟异常场景；与 94#1 独立（修复排序键后本条仍存在）。
- 修复方向：`anchor = anchor.min(now_utc())` 钳制，或调度器内存维护 `Instant` 单调水位、墙钟仅作跨重启兜底。

### 94#5 S3 aws4 签名两处当前未触发的隐患：查询串未按 RFC3986 重排重编码、默认端口进 canonical host

- 位置：`desktop/src-tauri/src/backend/sync/transport.rs:68-70`（canonical query 直接取 `url.query()` 原串——由 `form_urlencoded` 序列化，空格→`+`、`~`→`%7E`，与 AWS 要求的 RFC3986 canonical（`%20`、`~` 原样）不同，且未按键排序）；`:61-63`（endpoint 显式写 `https://host:443` 时 canonical host 变 `host:443`，若底层按惯例发不带端口的 Host 头则签名不匹配）。
- 传递链条：①当前仅有 `list-type=2&prefix=<受限字符集>` 查询（恰已有序、无空格/波浪号），签名碰巧正确（HMAC 实现经 FIPS 向量测试 transport tests.rs:269-275） → ②未来加 continuation-token 等含特殊字符参数即 403；用户 endpoint 写默认端口即得误导性「HTTP 403」。
- 影响范围：纯前瞻性；现有功能不受影响。
- 修复方向：构造 canonical query 时按键排序并按 RFC3986 重编码；host 仅在非默认端口时带端口。

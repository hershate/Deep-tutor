### 133#1 普通文件批量导入无逐批容错——一批失败丢失全部已导入结果并跳过剩余

- 位置：`desktop/src/backend/materialImport.ts:16-18`（`for (...) { outcomes.push(...await backend.importMaterialFiles(regular.slice(index, index + 32))) }` 无 try/catch）。
- 传递链条：①用户拖入/选择大量资料（如 200 个文件=7 批）或拖放混合普通文件与 ZIP；②第 N 批 `importMaterialFiles` reject（后端瞬时错误、配额、连接异常——任一非预期错误）；③整个 `importMaterialPaths` promise reject：前 N-1 批**已真实导入**的结果被丢弃——调用方（App.tsx:269-271 拖放、资料库文件选择）catch 只报 `reportBackendError`，用户看到「失败」却无从得知前几批已入库；④剩余批次与全部 ZIP 被跳过。ZIP 循环（同文件 :20-31）有 42#3 逐包 try/catch 降级为逐文件 outcome——同一函数内两种通道容错口径不对称。
- 影响范围：受影响=大批量导入中途出错的用户（已导入部分零反馈，只能去资料库自查；失败原因只有一个笼统错误）；不受影响=全部成功的导入与单个 ZIP 失败场景；损害性质=反馈丢失与误导，无数据损坏（已入库不受影响）。
- 修复方向：批循环加 try/catch——失败批降级为整批 error outcome（或批内重试一次）后继续后续批次；摘要文案已有 errors 通道可直接呈现。

### 133#2 测试 HTTP 桩在请求头未一次收齐时把连接当作「无请求」丢弃

- 位置：`desktop/src-tauri/src/backend/providers/test_support.rs:85-87`（`let header_end = request.windows(4).position(|bytes| bytes == b"\r\n\r\n")?;` 位于 `loop { stream.read(...) }` 内）。
- 传递链条：①`read_request` 每次 `read` 最多 4096 字节入缓冲；②若 `\r\n\r\n` 尚未到达（TCP 分段把头拆到第二个 read、或头部+首块超过 4096 字节被分段），当前缓冲里 `position` 返回 None；③`?` 直接让 `read_request` 返回 None——本应「继续 read 等剩余字节」，实现成了「放弃整个请求」；④worker（:54-59）把 None 视作无请求，`continue` 接下一连接——被测客户端的这次请求在桩侧「凭空消失」，测试得到空请求列表/意外响应，以难定位的方式 flaky 或误报。「已收到部分字节但头未完整」与「对端关闭」（:78-80 count==0）是两种语义，被合并成同一 None。
- 影响范围：受影响=所有用 TestServer 的 providers 测试（请求恰好分段时误判，概率低但真实存在——reqwest 分块发送大体量头/慢回环时）；不受影响=头一次到达的常规请求；损害性质=测试基建可靠性，非产品缺陷。
- 修复方向：`position` 返回 None 时 `continue` 继续 read（保留已收缓冲），仅 EOF（count==0）与超 1MB 上限返回 None；补一条分段投递的回归测试（先写半个头 flush 再写剩余）。

### 133#3 单实例互斥体重试窗内每轮泄漏一个句柄

- 位置：`desktop/src-tauri/src/main.rs:160-177`（restart 退避窗每 100ms `CreateMutexW` 一次、最多 20 轮，每轮新句柄未 CloseHandle；注释 :170 自述「句柄随第二实例退出由 OS 回收」）。
- 传递链条：①重启子进程（DEEPTUTOR_RESTARTING 标记）在 2s 退避窗内每 100ms 重试 acquire；②每轮 CreateMutexW 分配一个新内核句柄——命中 ALREADY_EXISTS 后 continue 前不 CloseHandle；③窗口内最多累积 20 个句柄；④第二实例随后 return false 退出、OS 全量回收——无跨进程累积；正常单实例只持 1 个句柄到进程结束（:149 注明有意设计）。
- 影响范围：受影响=重启退避窗内的瞬时句柄计数（≤20，有界且进程退出即回收）；不受影响=稳态运行、双开判定正确性；损害性质=资源卫生注记，无泄漏放大。
- 修复方向：`continue` 前 `CloseHandle(handle)`，只保留最终判定用的句柄。

### 133#4 verify 通道的 catch_unwind 只包 initialize——后续自检段 panic 仍以 101 破坏 exit(2) 契约

- 位置：`desktop/src-tauri/src/main.rs:58-74`（127#9 的 catch_unwind 范围仅 `startup::initialize`）vs `:84-102`（verify 分支其后的 `ensure_ready` / `.lock()` / `.bootstrap()` / snapshot 断言段在 catch 之外）及其余 setup/事件循环。
- 传递链条：①verify-native 进程进入 setup，assemble 内 initialize 被 catch_unwind 包住（panic→exit 2）；②其后 ensure_ready/bootstrap/snapshot 断言段及 setup 外围、事件循环不在保护内；③这些位置若 panic（内部断言崩坏、意外状态）——unwind 穿到 `builder.run().expect`（:439-441）以 101 退出；④50#1「verify 校验不过 → exit(2)」契约对残余面不成立——CI 又会把断言崩坏误读为运行崩溃（127#9 要修的原状只修了一半）。
- 影响范围：受影响=verify 通道残余 panic 面（概率低——该段以 Result 交付为主）；不受影响=GUI 通道与 initialize 本身（已受保护）；损害性质=CI 契约判定失真（退出码语义）。
- 修复方向：把 :84-102 段并入 catch_unwind（或该段全部改 Result → exit(2) 交付）；至少给 expect 加 verify_native 判定转 exit(2)。

### 133#5 事件循环失败走 `.expect` 无声硬崩——GUI 子系统下用户零反馈

- 位置：`desktop/src-tauri/src/main.rs:439-441`（`builder.run(context).expect("error while running the Deep Tutor application")`）。
- 传递链条：①GUI 模式事件循环 run() 返回 Err（WebView2 初始化失败等）；②expect 直接 panic——错误消息只写 stderr；③Windows GUI 子系统（main.rs:1 windows_subsystem="windows"）无控制台——stderr 无人可见、无对话框；④用户双击后窗口不出现、无任何提示与日志落点，只能盲猜原因。
- 影响范围：受影响=事件循环失败的启动场景（罕见——WebView2 缺损/损坏环境）；不受影响=正常启动与 assemble 失败路径（present_startup_failure 有用户呈现）；损害性质=启动失败零反馈。
- 修复方向：expect 改 match——Err 时写数据根 diagnostics.log（store.rs 已有 append_diagnostic 通道）并可选原生消息框后 exit(1)。

### 133#6 Ctrl+K 只判专注层——其它弹层打开时顶替/叠开搜索

- 位置：`desktop/src/App.tsx:283-287`（`if ((metaKey||ctrlKey) && key==='k') { if (!focusOpen) { preventDefault(); setModal('search') } }`；modal 为单值状态 :73）。
- 传递链条：①任一 App 级弹层（快速记录/通知/任务中心，均走 Modal 组件）或页面级弹层打开时用户按 Ctrl+K；②handler 只判 focusOpen（14#4 只论证了 z90 专注层遮挡一种情形）——放行 setModal('search')；③modal 是单值状态：App 级弹窗被直接顶替（快速记录半填内容丢失）、页面级弹层上叠开搜索弹层；④用户视角——弹窗意外切换或搜索凭空叠出。
- 影响范围：受影响=弹层打开时使用 Ctrl+K 快捷键的用户（输入丢失/意外切换）；不受影响=无弹层时的正常打开；损害性质=状态顶替与输入丢失。
- 修复方向：`if (!focusOpen && !modal)` 才响应（页面级弹层可经 `.overlay` 判定，与 133#7 同源）。

### 133#7 Esc 全局仲裁依赖 `.overlay` 类名查询——与弹层栈真源脱钩

- 位置：`desktop/src/App.tsx:291`（`if (document.querySelector('.overlay')) return`）vs `desktop/src/components/UI.tsx:174-184`（弹层真源是模块级 `MODAL_STACK`，按 modalSequence 仲裁最顶层）。
- 传递链条：①App 级 Esc handler 用 DOM 类名查询判断「是否有弹层打开」；②该判定与弹层栈真源 MODAL_STACK 完全脱钩——只认 `.overlay` 类名的存在；③任何不走 Modal 组件的自绘弹层、或未来类名重构，都会让仲裁静默失效；④Esc 穿透弹层直接关掉底层抽屉/移动导航/共享页——一次按键关错层。
- 影响范围：受影响=未来自绘 overlay 或类名改动后的一切弹层场景（当前全部弹层经 Modal 渲染、暂无实害）；不受影响=当前 Esc 行为；损害性质=结构性耦合的脆弱性。
- 修复方向：UI.tsx 导出 `MODAL_STACK.length > 0` 判定（或 `hasOpenModal()`），App.tsx 改用该 API，删类名查询。

### 133#8 大批量导入全程无中间进度——数百文件分钟级静默

- 位置：`desktop/src/backend/materialImport.ts:13-33`（顺序批/逐包 await）+ `desktop/src/App.tsx:269-271`（拖放调用方仅在终态 notify 一次）。
- 传递链条：①用户拖入/选择数百个文件——普通文件按 32/批顺序 await、ZIP 逐包 await；②全程无中间反馈通道——调用方只在全部完成后 notify 一次摘要；③导入持续数十秒至分钟级，期间 UI 无「进行到第几批/共几批」任何口径（页面数据虽由 material.* 事件刷新，但那是数据变化而非进度反馈）；④用户不知是否在工作、能否中断或关闭页面。
- 影响范围：受影响=大批量导入场景（数百文件/多 ZIP）；不受影响=小批量导入（秒级完成，终态 toast 足够）；损害性质=长任务反馈缺失，无数据风险（后端逐条入库）。
- 修复方向：importMaterialPaths 接收可选 onProgress 回调（已处理数/总数），调用方挂轻量进度条（ProgressBar 已有 srLabel 通道）。

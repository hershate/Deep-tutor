## P3

### 133#1 普通文件批量导入无逐批容错——一批失败丢失全部已导入结果并跳过剩余

- 位置：`desktop/src/backend/materialImport.ts:16-18`（`for (...) { outcomes.push(...await backend.importMaterialFiles(regular.slice(index, index + 32))) }` 无 try/catch）。
- 传递链条：①用户拖入/选择大量资料（如 200 个文件=7 批）或拖放混合普通文件与 ZIP；②第 N 批 `importMaterialFiles` reject（后端瞬时错误、配额、连接异常——任一非预期错误）；③整个 `importMaterialPaths` promise reject：前 N-1 批**已真实导入**的结果被丢弃——调用方（App.tsx:269-271 拖放、资料库文件选择）catch 只报 `reportBackendError`，用户看到「失败」却无从得知前几批已入库；④剩余批次与全部 ZIP 被跳过。ZIP 循环（同文件 :20-31）有 42#3 逐包 try/catch 降级为逐文件 outcome——同一函数内两种通道容错口径不对称。
- 影响范围：受影响=大批量导入中途出错的用户（已导入部分零反馈，只能去资料库自查；失败原因只有一个笼统错误）；不受影响=全部成功的导入与单个 ZIP 失败场景；损害性质=反馈丢失与误导，无数据损坏（已入库不受影响）。
- 修复方向：批循环加 try/catch——失败批降级为整批 error outcome（或批内重试一次）后继续后续批次；摘要文案已有 errors 通道可直接呈现。

### 133#2 测试 HTTP 桩在请求头未一次收齐时把连接当作「无请求」丢弃

- 位置：`desktop/src-tauri/src/backend/providers/test_support.rs:85-87`（`let header_end = request.windows(4).position(|bytes| bytes == b"\r\n\r\n")?;` 位于 `loop { stream.read(...) }` 内）。
- 传递链条：①`read_request` 每次 `read` 最多 4096 字节入缓冲；②若 `\r\n\r\n` 尚未到达（TCP 分段把头拆到第二个 read、或头部+首块超过 4096 字节被分段），当前缓冲里 `position` 返回 None；③`?` 直接让 `read_request` 返回 None——本应「继续 read 等剩余字节」，实现成了「放弃整个请求」；④worker（:54-59）把 None 视作无请求，`continue` 接下一连接——被测客户端的这次请求在桩侧「凭空消失」，测试得到空请求列表/意外响应，以难定位的方式 flaky 或误报。「已收到部分字节但头未完整」与「对端关闭」（:78-80 count==0）是两种语义，被合并成同一 None。
- 影响范围：受影响=所有用 TestServer 的 providers 测试（请求恰好分段时误判，概率低但真实存在——reqwest 分块发送大体量头/慢回环时）；不受影响=头一次到达的常规请求；损害性质=测试基建可靠性，非产品缺陷。
- 修复方向：`position` 返回 None 时 `continue` 继续 read（保留已收缓冲），仅 EOF（count==0）与超 1MB 上限返回 None；补一条分段投递的回归测试（先写半个头 flush 再写剩余）。

## 信息

### 133#3 单实例互斥体重试窗内每轮泄漏一个句柄

- 位置：`desktop/src-tauri/src/main.rs:160-177`（restart 退避窗每 100ms `CreateMutexW` 一次、最多 20 轮，每轮新句柄未 CloseHandle；注释 :170 自述「句柄随第二实例退出由 OS 回收」）。有界（≤20 个）、进程退出即回收，正常单实例持有 1 个句柄到进程结束是 :149 注明的有意设计。
- 修复方向：`continue` 前 `CloseHandle(handle)`，只保留最终判定用的句柄。

### 133#4 verify 通道的 catch_unwind 只包 initialize——后续自检段 panic 仍以 101 破坏 exit(2) 契约

- 位置：`desktop/src-tauri/src/main.rs:58-74`（127#9 的 catch_unwind 范围仅 `startup::initialize`）vs `:84-102`（verify 分支其后的 `ensure_ready` / `.lock()` / `.bootstrap()` / snapshot 断言段在 catch 之外）及其余 setup/事件循环。这些位置若 panic（内部断言、锁中毒之外的意外），unwind 仍穿到 `builder.run().expect`（:439-441）以 101 退出——50#1「verify 校验不过 → exit(2)」契约对残余 panic 面不成立，CI 又会把断言崩坏误读为运行崩溃（127#9 要修的原状残留一半）。
- 修复方向：把 :84-102 段并入 catch_unwind（或该段全部改 Result → exit(2) 交付）；至少给 expect 加 verify_native 判定转 exit(2)。

### 133#5 事件循环失败走 `.expect` 无声硬崩——GUI 子系统下用户零反馈

- 位置：`desktop/src-tauri/src/main.rs:439-441`（`builder.run(context).expect("error while running the Deep Tutor application")`）。run 返回 Err（WebView2 初始化失败等）时 panic 输出只到 stderr——Windows GUI 子系统无控制台，双击启动的用户看到的是「点了没反应」，无对话框、无日志落点。
- 修复方向：expect 改 match——Err 时写数据根 diagnostics.log（store.rs 已有 append_diagnostic 通道）并可选原生消息框后 exit(1)。

### 133#6 Ctrl+K 只判专注层——其它弹层打开时顶替/叠开搜索

- 位置：`desktop/src/App.tsx:283-287`（`if ((metaKey||ctrlKey) && key==='k') { if (!focusOpen) { preventDefault(); setModal('search') } }`）。modal 是单值状态（:73 `'search'|'quick'|'notifications'|'tasks'|null`）：快速记录/通知/任务中心任一打开时按 Ctrl+K 直接切到搜索——原弹窗（可能含半填的快速记录内容）被顶替；页面级 Modal（供应商中心等）打开时则在 其上叠开搜索（z70 层级关系与 14#4 注释只论证了 z90 专注层一种遮挡情形）。
- 修复方向：`if (!focusOpen && !modal)` 才响应（页面级弹层可经 `.overlay` 判定，与 133#7 同源）。

### 133#7 Esc 全局仲裁依赖 `.overlay` 类名查询——与弹层栈真源脱钩

- 位置：`desktop/src/App.tsx:291`（`if (document.querySelector('.overlay')) return`）vs `desktop/src/components/UI.tsx:174-184`（弹层真源是模块级 `MODAL_STACK`，按 modalSequence 仲裁最顶层）。全局分层仲裁把「是否有弹层」外包给 DOM 类名——任何不走 Modal 组件/改了类名的弹层都会让仲裁静默失效（Esc 穿透去关抽屉或移动导航）。
- 修复方向：UI.tsx 导出 `MODAL_STACK.length > 0` 判定（或 `hasOpenModal()`），App.tsx 改用该 API，删类名查询。

### 133#8 大批量导入全程无中间进度——数百文件分钟级静默

- 位置：`desktop/src/backend/materialImport.ts:13-33`（顺序批/逐包 await）+ `desktop/src/App.tsx:269-271`（拖放调用方仅在终态 notify 一次）。几百个文件分十几批顺序导入期间 UI 无任何进度反馈（页面数据倒是由 material.* 事件刷新，但无「进行到第几批/共几批」通道）；与 130#4 的 ZIP 逐包同病。
- 修复方向：importMaterialPaths 接收可选 onProgress 回调（已处理数/总数），调用方挂轻量进度条（ProgressBar 已有 srLabel 通道）。

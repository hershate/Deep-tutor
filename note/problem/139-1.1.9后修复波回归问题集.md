### 139#1 133#5/135#3 新增的 eprintln 在 release + windows_subsystem 双击场景可能先于诊断落盘 panic

- 位置：`desktop/src-tauri/src/main.rs:464`（事件循环失败分支：`eprintln!` 先于
  `append_diagnostic` 与 `exit(1)`）；`desktop/src-tauri/src/backend/sharing/mod.rs:339`
  （分享创建失败后清理失败的 `eprintln!`，位于 tauri 命令内）。
- 传递链条：①release 构建 `windows_subsystem = "windows"`（main.rs:1），双击启动的
  进程无控制台、stderr 句柄无效；②事件循环失败（133#5 场景）或分享清理双失败
  （135#3 场景）触发 `eprintln!`；③Rust std 对 stderr 写失败的行为是 panic
  （"failed printing to stderr"）；④133#5 场景：panic 使其后同分支内的
  `append_diagnostic` 与 `exit(1)` 均不可达，进程以 101 退出——「用户可诊断」的修复
  目标在真实双击场景未达成（不劣于修复前 `.expect` 的 panic，但也没达成改善）；
  135#3 场景：panic 发生在同步命令内，主线程 panic 使进程崩溃——劣于修复前
  `let _ =` 的完全静默（静默仅丢诊断线索，崩溃则中断整个应用）。
- 影响范围：受影响=release 安装包双击启动且命中事件循环失败 / 分享创建失败后清理
  再失败的用户；不受影响=控制台或 CI 启动（verify 通道 stderr 有效，eprintln 正常
  工作）、一切正常路径。既有生产代码十余处 eprintln（guard.rs、sync/scheduler.rs
  等）同样暴露，本波两处是延续既有口径而非独创。损害性质=诊断落盘失效（133#5）
  或进程崩溃（135#3）。
- 修复方向：改用 `append_diagnostic`（已有基础设施）或显式吞错的写入封装替代
  eprintln。需 release 安装包实机验证双击启动下 stderr 写入是否真实失败后定级——
  Windows GUI 子系统进程 stderr 有效性取决于父进程是否提供句柄，explorer 双击启动
  通常不提供。

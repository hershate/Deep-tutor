# 65 · 数据目录文件区三方对齐（第二十五轮）

> 审计范围：实际写入面（全部 fs 写调用推导）↔ 备份收集面 ↔ 运维清理面
> 三方对照；磁盘生命周期（去重原件/多用户隔离/删除语义）；导出目的地遏制
> 一致性。主审抽验 J-1 属实（agent_artifacts 全库无 DELETE）。

## 数据目录结构（代码推导）

```
<data_root>/deep-tutor.db(±wal/shm)              账户库
<data_root>/users/<uid>/deep-tutor.db(±wal/shm)  每用户工作区库
  ├─ materials/originals/{sha256}.{kind}          原件（.upload-/.restore- 临时件）
  ├─ materials.reset-{n}/                         reset 中间态
  ├─ plugins/{id}/manifest.json
  ├─ agent-workspaces/{session}/scratch/**        agent 产物（.tmp/.previous 点文件）
  ├─ backup-work/{pid}-{n}/                       备份工作目录（RAII）
  ├─ exports/anki-{pid}-{n}.db                    Anki 瞬态
  └─ sync/sync-{pid}-{n}.json（±.download-*/.previous-*）
app_local_data/storage-location.json（配置目录）   verification-storage.json（verify）
```

原件/插件/scratch 全部在用户目录内，无跨用户共享——删除/重置/备份/清理天然按用户切面。

## P3

### 65#1（=J-1）agent_artifacts 的 expires_at 从不清理——scratch 无限累积并膨胀备份

- 位置：写入 `agent/tools.rs:301-315`（+24h）；唯一消费 `tools.rs:815-836` 仅在用户尝试提升时惰性置 status='expired'；全库**无任何按 expires_at 的 DELETE**。maintenance 期望集（mod.rs:300-311）与备份收集（archive.rs:326-334）均取全表无状态过滤。
- 链条：每次 workspace.write 落盘+落行 → 过期后行与文件永存 → 运维视为「期望存在」不报孤儿 → 备份原样打包 expired 文件 → 磁盘与备份体积随 Agent 使用单调增长。唯一出口是手动删会话或 reset 后手动清孤儿。sessions=200 配额限会话数，不限每会话文件数。

### 65#2（=J-2）reset 不清 agent-workspaces 与 sync 目录——「数据已清空」后文件证据仍在盘上

- 位置：reset_application（backend/commands.rs:82-110）只搬 materials 与 plugins；agent/sync 的 clear_all 只删表行。scratch 沦为无主文件需事后手动清孤儿；sync/*.json 完全不在任何清理面（见 65#3）。与用户对「清除本地学习数据」的预期不符。

### 65#3（=J-3）`users/<uid>/sync/` 是清理盲区

- 位置：写入 `sync/mod.rs:557-602`；自剪枝只保留最近 10 份 `.json` 且仅在新下载任务时触发；原子写临时件经 with_extension 变为 `sync-{pid}-{n}.download-{m}`（**丢失 .json 扩展名**），不满足自剪枝过滤。maintenance 只枚举五处目录不含 sync。下载中途崩溃的临时件与 reset 后存量永久滞留。这是 atomic_export 唯一落在数据目录内的调用点（其余被 reject_data_root_destination 遏制到数据根外）。

### 65#4（=J-4）`materials.reset-{n}` 备份目录可永久残留

- finish_reset 提交成功路径 remove_dir_all 失败仅报 cleanup_failed，或进程在 rename 与 finish 间崩溃 → 残留目录在用户目录根层，scan_orphans 只走 materials/originals 看不见它——全部原件（各 ≤50MB）长期占盘且对运维 UI 不可见。

### 65#5（=K-5/J-6）`reject_data_root_destination` 只拦当前 data_root，不拦旧默认目录

- 数据目录迁移后旧默认目录仍含历史库与原件；导出/备份目的地选在旧默认数据目录内会被放行，可能覆盖旧数据。边角场景（需用户主动迁移后再主动选旧目录导出同名文件）。

### 65#6（=J-7）delete_material 引用保护不含 projects——ON DELETE SET NULL 静默断链

- materials/mod.rs:1274-1284 只检查 learning/knowledge 两处 RESTRICT 外键；project_versions.material_id 是 SET NULL——被项目版本引用的资料删除时无提示断开关联，与另两域「友好拒绝」口径不一致（不丢数据）。

## 信息性

### 65#7（=J-5/J-8）两处清理面小缺口

- migration-tmp 残留：① 首次迁移旧根库（copy → `deep-tutor.db.migration-tmp` → rename 两步）→ ② 进程在两步间崩溃 → ③ staging 库文件残留于数据根，任何清理面不扫描 → ④ 占盘且不可见（一次性路径，含全部账户数据副本）。位置 store.rs:180-189。
- restore 临时件误报：① 去重命中但原件丢失时补写走 `.restore-{pid}-{n}` 临时名 → ② 运维宽限白名单只匹配 `.upload-` → ③ 该文件被报为孤儿（报告噪声）→ ④ 但 cleanup 前统一 mtime 复查（24h 内不删）兜底，**不会误删**。位置 maintenance/mod.rs:293、materials/mod.rs:570-574。
- 影响范围：migration-tmp 为崩溃窗口残留（概率极低、后果为数据目录多一个完整库副本）；restore 误报仅为维护报告多一行噪声。均无用户可见功能影响。

## 正向结论

- **备份收集与写入面精确对齐**：全部持久用户文件类别（originals/插件清单/agent scratch）均进备份，缺失/漂移显式随档（57#2/3）；DB 55+ 表全量、凭据脱敏；「不进备份」项（sync 下载副本可重下、exports/backup-work 瞬态）均合理。
- **sha256 去重不产生共享原件**：同库同内容单行，删除即删原件正确，失败报 cleanup_failed 后孤儿清理兜底（自愈闭环）；命中去重但原件丢失会补写（11#15）。
- **多用户隔离完整**：reset 全程当前 principal 下执行，用户 A 重置不影响用户 B 库与原件。
- **导出原子写三处实现一致**（materials/agent/plugins），正式路径不留截断文件；备份导出与 sync 下载共用同一道二道遏制（fail-closed）。
- 运维清理对已识别临时类别设计周到：24h 宽限、500 项批次、失败不占配额、symlink/深度/越界防护、删除前 mtime 复查。

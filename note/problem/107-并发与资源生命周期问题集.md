## P2

### 107#1 materials 的 accepting 闸门在 logout→login / 数据库整理 / 清理孤儿 / 重置之后永不复位——同进程会话内资料解析静默停摆

- 位置：`desktop/src-tauri/src/backend/materials/mod.rs:107`（stop_all 首行 `accepting.store(false)`——唯一置 false 点）、`:927-929` 与 `:1201-1203`（spawn_job/schedule_next 开头 `if !accepting { return Ok(()) }`——静默跳过，无错误无事件）、`:1229`（`accepting.store(true)` 全仓唯一复位点，在 `pub fn recover` 内）。recover 的调用方全仓仅两处：`startup.rs:407`（进程冷启动）、`backup/mod.rs:158`（备份导入收尾）。而置 false 的 stop_all 调用方（guard.rs:41）：logout（security/mod.rs:1037）、login 切换（guard.rs:170，resume 只重启同步调度器 :161-167）、maintenance 清理/整理（maintenance/commands.rs:67/:100，收尾同样只 start_scheduler :71/:104）、reset（commands.rs:140，两者皆无）——三组路径均不调 materials::recover。
- 传递链条：①用户执行任一停机操作（登出后再登录 / 跑一次「数据库整理」/「清理孤儿文件」/「重置应用」，均不重启进程）→ accepting 置 false 且后续路径不复位 → ②导入新资料点解析 → enqueue（materials/mod.rs:1048）正常插入 queued 行、status='queued'、发 material.queued 事件 → ③随后 spawn_job 命中闸门静默 return——不启动解析线程、不报错；schedule_next 只在其他任务完成时被触发且同样被挡 → ④该资料永远停留「排队中」：无进度、无错误、无事件；停止前已排队的任务同样无人捡起；资料解析功能域在同会话内整体失效，直到重启应用（冷启动 recover 复位并重排）。确定性触发（非竞态）。
- 影响范围：每次 vacuum/cleanup/logout+login/reset 后必现；数据不丢（重启恢复），但功能损坏是静默的——UI 永远显示排队，无任何自救提示。备份导入是唯一自带恢复的路径。
- 修复方向：把 accepting 复位并入停机后的统一恢复点——login switch 的 resume、maintenance 两命令收尾、reset 成功路径各补一次 materials::recover（或最小改动：仅置 accepting=true 的轻量函数）；备选：spawn_job 被闸门挡住时把 job 落回 queued 并在 UI 呈现「解析暂停」而非静默。

### 107#4 sync 调度器线程 panic 后 JoinHandle 残留使 start_scheduler 永不再启——纯防御缺口

- 位置：`sync/scheduler.rs:87-89`（`if scheduler.is_some() && !STOP { return }`）与 `:106-109`（spawn 成功即覆盖句柄，永不探活）。调度线程体当前无可达 panic 路径（run_due 错误均走 ? 返回后 eprintln）。
- 传递链条：①调度线程因栈溢出/OOM 等极端情形死亡 → ②句柄仍存、STOP 仍 false → ③此后全部 8 个 start_scheduler 入口恒 early-return → ④auto_sync 静默停摆至进程重启。
- 影响范围：无已证 panic 源的纵深缺口；无用户可见影响。
- 修复方向：spawn 前对旧句柄 `is_finished()` 探活，死句柄即替换重启；或线程体包 catch_unwind 记录失败态。

### 107#5 user1 首次工作区迁移整库复制期间 STORE_OPEN_LOCK 全局串行——每命令新开连接模式放大阻塞面

- 位置：`store.rs:187-213`（Store::open 全程持全局锁；owner==Some(1) 且 root 存在且 user1 缺失时，锁内 checkpoint+BEGIN IMMEDIATE+fs::copy 整库，GB 级可达数十秒）。
- 传递链条：①旧版单库升级/迁移目录后首条触发 user1 的命令在锁内整库复制 → ②期间进程内所有其他 Store::new（域 store() 每命令打开一次）排队 → ③同步命令在主线程等锁 → ④一次性窗口内全局命令排队。与 103#9（同段代码的 WAL 帧丢失数据面）不同后果，本条是锁阻塞体验面。
- 影响范围：一次性首迁移窗口（启动后首批命令）。
- 修复方向：迁移完成后将就绪状态记入进程内 OnceLock，稳态 Store::open 跳过全局锁；或复制段降级为显式迁移入口。

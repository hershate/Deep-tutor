### 81#1 同一备份第三次导入时 agent_memory 必撞主键，整单回滚

- 位置：`desktop/src-tauri/src/backend/backup/transfer.rs:1184-1197`（agent_memory 键改写）与 `:1149-1157`（`global_conflict` 键表未含 agent_memory）、`:1029` 附近（`insert_row` 主键冲突返回 `backup_constraint_failed`）。
- 传递链条：①导入含 agent_memory 键 K 的 .dtbackup，第 1 次导入插入原键 K；②第 2 次导入时 `exists(tx, "agent_memory", "key", K)` 为真，改写为 `"{K} · 导入 {N+1}"`（N 为备份内 agent_memory 行数，取自 `transfer.maps.get("agent_memory").len()`，**同一备份恒定**）；③第 3 次导入时 K 仍冲突，再次改写出与第 2 次完全相同的 `"K · 导入 N+1"`，与库中已有行撞 TEXT 主键 → `backup_constraint_failed` → 事务整体回滚。
- 影响范围：31#43/31#44 建立的追加导入幂等承诺对 agent_memory 域失效——同一备份第 3 次起永久无法导入；数据无损，但报错文案（「备份 Agent 会话数据未通过当前数据库约束」）与真实原因（键改写碰撞）不符，用户无从自救。
- 修复方向：改写前对**新键**再做 `exists` 判定，被占则递增序号（`· 导入 {N+2}`…直到空闲）；或后缀序号改为「目标库中 ` · 导入 ` 前缀行数 + 1」。

### 81#2 Deep Link 供应商类型判定对 https 端点恒为「本地模型」

- 位置：`desktop/src-tauri/src/backend/providers/mod.rs:743-747`（`kind = if openai::endpoint(&base_url, "本地模型", "models").is_ok()`）→ `openai.rs:169-177`（`endpoint_scope`：kind=本地模型 + https → `LocalHttps`）→ `openai.rs:193-201`（`socket_addresses` 仅对 `LocalHttp` 拒绝公网、对 `LocalHttps` 无任何检查）。
- 传递链条：①用户点击 `deeptutor://provider?baseUrl=https://api.example.com/v1`；②`endpoint()` 落入 LocalHttps 分支，`socket_addresses` 对该 scope 全放行 → 恒 Ok → kind 判定为「本地模型」；③任何 https 云端兼容服务（包括 api.openai.com）的档案 kind 都记为「本地模型」，且本地模型的宽松网络语义（免「远程必须 HTTPS+公网」校验）经 deep link 自动生效——正常 UI 路径需用户手动选「本地模型」才能引入 `https://内网IP` 端点，此处被静默放行。
- 影响范围：档案 kind 字段错误（供应商列表/导出配置显示「本地模型」实为云服务）；SSRF 面扩大：恶意网页诱导点击 deep link 即可注册指向内网 https 地址的供应商档案，后续「测试/聊天」将对内网发请求。http 地址判定正确（公网 http 被拒 → 兼容服务），仅 https 侧失效。
- 修复方向：https 地址解析后按 IP 分类——回环/私网 → 「本地模型」，公网 → 「兼容服务」；仅 http 保留现判定。补回归测试覆盖 https 公网/私网两分支。

### 81#4 begin_chat 持 chat_cancels 锁跨 SQLite 查询与事务提交，取消请求可被延迟

- 位置：`desktop/src-tauri/src/backend/providers/mod.rs:1030-1073`。
- 传递链条：①`begin_chat` 取 `chat_cancels` 互斥锁后执行 `chat(state, request_id)`（新开连接 + 可能全量 delta 重建）与 `unchecked_transaction`（INSERT + 事件落盘）；②`tx.commit()` 在 busy_timeout 内最长等待 10s（恰逢备份导入等长写事务时）；③此窗口内 `cancel_provider_chat`/`cancel_direct_chat`（:1332-1342）、`ChatGuard::drop`、`stop_direct_chats`（:1376-1401）全部阻塞在同一把锁上——用户点「取消」无响应直至锁释放。
- 影响范围：无死锁（锁依赖单向），但取消与停机（stop_all 15s deadline）最坏被拉长数秒；正常负载无感。
- 修复方向：锁内只做 `contains_key` 幂等检查 + insert 登记，随即放锁执行查询与落库，commit 失败时补偿 remove（现 :1066 附近已有 remove 补偿分支，仅需调整顺序）。

### 81#5 events_since 跳过坏 payload 行后 hasMore 按「跳过后」计数，可能漏页

- 位置：`desktop/src-tauri/src/backend/store.rs:869-913`。查询 `LIMIT 201`，75#3 修复使坏 JSON 行被 `continue` 跳过；若 201 行中恰有 ≥1 行损坏，返回 200 行且 `events.len() > 200` 判为无更多——实际仍有未读事件。
- 传递链条：①`events_since` 以 `LIMIT 201` 分页读取事件 → ②75#3 修复使坏 JSON 行被 `continue` 跳过（降级路径本身正确）→ ③若 201 行中恰有 ≥1 行损坏：返回的有效行 < 200 且 `has_more = events.len() > 200` 判 false——调用方以全局 MAX 推进游标后，剩余未读事件被跳过。
- 影响范围：前端已按 38#2 改为全量快照，`eventsSince` 零调用（另见 83#2 死命令条目）——当前无实际触发方；仅未来/第三方分页消费方会漏页。
- 修复方向：`has_more` 改按原始查询行数（> 200）判定，而非跳过后计数。

### 81#6 sync 调度器 MAX(finished_at) 字符串比较在混合亚秒精度下可能取错锚点

- 位置：`desktop/src-tauri/src/backend/sync/scheduler.rs:28-57`。`SELECT COALESCE(MAX(finished_at), '')` 按字典序比较 RFC3339 字符串，time crate 输出的亚秒位数不定（0/3/6/9 位），`.123Z` 与 `.123456Z` 的字典序与时间序不一致；后续 `WHERE finished_at = ?1` 取 status 决定 1h/24h 间隔时可能读到空/错行。
- 传递链条：①调度器取 `MAX(finished_at)` 字符串作锚点、后续 `WHERE finished_at = ?1` 取 status 决定间隔 → ②RFC3339 亚秒位数不定（0/3/6/9 位），字典序比较在混合精度下与时间序不一致（`.123Z` > `.123456Z` 但时间更早）→ ③锚点可能取错行或匹配空，失败后的 1 小时短退避被当作 24 小时长退避——下一次自动同步延后近一天。
- 影响范围：仅同步失败后的自动重试节奏（偶发延后）；不损数据、成功路径不受影响。
- 修复方向：锚点行改按 `rowid` 取最新 upload 行，或改存整数时间戳列。

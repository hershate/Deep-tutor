# 162 · 恢复竞态

## 162#1 多个 recover 实现可覆写仍存活任务的真实终态

- 严重度：P2。
- 传递链：`stop_all` 失败后的回滚路径会调用 `resume_background`，此时旧工作线程仍可能存活并完成。学习方案、Agent、练习生成、主观评分和 Wiki 主行已有活跃态守卫，但下列路径没有完整守卫：
  - `providers::recover_chats` 对 running 请求无条件改 interrupted 并发事件；
  - `providers::routing::recover` 对 route run 无条件覆写，再改 attempt 并发事件；
  - `lecture::recover` 先改单元再无条件改讲义主行并发事件；
  - `projects::recover` 的普通收尾与重放失败收尾均无条件 UPDATE；
  - `sync::recover` 对任务无条件 UPDATE 并发终态事件；
  - `reports::recover` 的 UPDATE 虽有活跃条件，但不检查 changed，仍对已完成会话发 `focus.interrupted`；
  - `materials::recover` 经通用 `transition` 无条件写 queued/cancelled，可覆盖已落盘终态。
- 影响范围：停机失败回滚、登录/切换、维护与重置后的恢复；真实完成结果被改为 interrupted/cancelled，前端收到与数据库原终态矛盾的事件，恢复和计费记录随之失真。

## 162#2 方案与讲义的子行在主流失守卫前被改写

- 严重度：P3。
- 传递链：`learning::recover` 先更新 running 步骤，再检查主行 changed；`lecture::recover` 同样先更新单元再写主行且无 changed 判定。主行若已被存活线程置为 done/degraded，子行仍可能被补写成 interrupted/cancelled。
- 影响范围：方案步骤与讲义单元的持久状态、结果重放和后续恢复；主从状态可在同一库内分叉。

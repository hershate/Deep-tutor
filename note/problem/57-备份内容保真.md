## P3

### 57#1 `agent_messages.tool_calls_json` 与 `provider_requests.tool_calls_json` 内嵌 call id 不随 agent_tool_calls 重映射改写——跨工作区撞键时工具配对挂错行

- 位置：`desktop/src-tauri/src/backend/backup/transfer.rs:743`（`continue` 只挡键名递归，主审亲验）+ `:897`（两列仍进 rewrite_json）；载荷是 `[{"id","name","arguments"}]` 数组，元素键 `"id"` 不在键表（只认 toolCallId/toolCalls），34#14 特判匹配不上。
- **机理（传递链条）**：① 跨工作区导入备份 → ② `agent_tool_calls.id`（TEXT PK）与目标库撞键 → ③ 重映射把该行 id 改写为 imported-N，`agent_messages.tool_call_id` 列同步改写 → ④ 但消息内嵌 `tool_calls_json` 数组的 `"id"` 元素键不在键表（只认 toolCallId/toolCalls），34#14 特判也匹配不上——保持源值 → ⑤ agent 会话视图的工具调用声明（34#5 配对场景）按源 id 查表 → 指向目标库同 id 的**无关**工具调用行。
- **影响范围**：跨工作区导入且 call id 恰好撞键的用户（provider 生成的 call_XXX 撞键概率低）；后果为历史会话的工具调用详情挂错行（展示层错配，工具结果本体在 agent_tool_calls 表中仍正确）。同备份重复导入时源 id 行仍在、配对仍命中旧行（症状最轻）。

### 57#2 原件「内容漂移」档案——导出成功、导入永久拒绝

- 位置：`desktop/src-tauri/src/backend/backup/archive.rs:249-262`（主审亲验：collect_files 用 DB 的 sha256 列拼路径、用文件**实际内容**算 entry.sha256，导出端无一致性比对）。
- **机理（传递链条）**：① 原件入库后被外部改动（文件内容 ≠ DB 记录的 sha256）→ ② 导出时 collect_files 用 DB sha 拼路径、用文件实际内容算 entry.sha256——无一致性比对，导出照常成功（missing_files 只报缺失不报不一致）→ ③ 导入侧 `target_relative`（:1199-1208）强制「文件名 stem == entry.sha256」→ stem(DB sha) ≠ entry.sha(实际) → `invalid_backup_path` **整单拒入**。
- **影响范围**：原件目录被外部工具改过（同步盘/杀毒/手动）的用户——拿到一份导出成功却永远导不回来的备份，且失败信息（路径非法）与真实原因（内容漂移）无关。正常未动原件的用户不受影响。修复：导出时发现 stem≠实际哈希即计入告警（或按缺失处理）。

### 57#3 missingFiles 只落导出端不随档案传递；导入不校验 materials 行有对应原件

- 位置：`archive.rs:105-114`（Manifest 结构无 missingFiles 字段，主审亲验）；transfer.rs 无对应校验。
- **传递链条**：① 导出时部分原件已缺失 → ② `BackupResult.missing_files` 只写进导出回执/事件（BackupPanel 当场明示）→ ③ 备份 zip 的 Manifest 没有该字段——缺失信息不随档案走 → ④ 恢复方导入：拿到 materials 行但 zip 里没有原件，也无从得知导出时已缺 → ⑤ 打开该资料预览/导出报错；导入回执无任何提示 → ⑥ 只能靠 maintenance 孤儿扫描事后发现。
- **影响范围**：导出时存在缺失原件、且在另一台机器/目录恢复的用户——静默拿到不完整备份（数据行在、文件缺），排障需自己想到孤儿扫描。修复：Manifest 增加 missingFiles（或导入时校验每行 materials 有对应 FileEntry 并计入 backupImportWarnings）。

### 57#4 「缺列走默认值」注释与实现不符——NOT NULL 缺列显式插 NULL 必撞约束（前瞻风险）

- 位置：`transfer.rs:100`（注释）vs `:950`（主审亲验）。
- **传递链条**：① 旧版本备份的某表缺新列（源库 schema 旧）→ ② insert_row 对缺列 `row.get(&column.name).unwrap_or(&Value::Null)` **显式插 NULL** → ③ SQLite 显式 NULL 不触发列 DEFAULT → ④ 若该列为 NOT NULL → 约束失败 `backup_constraint_failed` → ⑤ 整单事务回滚（loud 失败，非静默丢数据）——与 :100 注释「缺列走默认值」不符。
- **影响范围**：当前零受损面（git 时间线核实：全部 NOT NULL 迁移列均早于备份功能上线，不存在缺列的旧 v3 备份）；风险是前瞻性的——未来加 NOT NULL 列不升清单版本时，旧备份整体导入失败且错误码指向不明。修复：缺列时改用列默认值表达式（或按 schema DEFAULT 补值）。

## 正向结论（核对过、无问题）

- **表覆盖零遗漏**：TABLES 与全库 67 张用户表逐名 diff 完全一致；auth_sessions/access_tokens/share_index 为「收录后清空」（secure_delete=ON+VACUUM，导出）/「导入置空」+ sharing::reindex 重建——密钥/令牌不泄漏进备份（测试断言 zip 二进制无令牌）。
- **动态列映射**：`SELECT *` 按源列名装 BTreeMap + 按目标 PRAGMA table_info 生成列集——无静态清单可漂移；源多列=更新版本备份明确报错（08#9）；paused_at 有专门 shim。
- **ID 重映射**：INTEGER 主键事务内 MAX+1 线性探测（25#14 IMMEDIATE 关竞态）；`free_text_id` 的 GLOB 组合语义经内存 SQLite 实测正确；JSON 内嵌 ID 键族（materialId/planId/providerId/requestId 系/setId/questionId/answerId/cardId/projectId/taskId/noteId/userId/sessionId 按事件域路由/runId/community 系/shareId/pluginId）与 special-case（snapshot lenient、evidence_key 前缀、provider_meta）齐全——除 57#1 外无断链。
- **原件哈希链**：导出写 zip 前逐文件重哈希防 TOCTOU、导入逐文件哈希、强制 stem==sha、canonicalize+symlink 检查+hard_link、目标已存在内容不同则 backup_file_conflict 不覆盖。
- **事务与回滚**：单 IMMEDIATE 事务包住 prepare_ids→stage_files→order→import_rows→install_files；第 N 表失败全部回滚 + 已 hard_link 文件逐个删除（测试断言零残留）；dry_run 与导入共用代码路径（13#19 成立，仅安装期失败预演不可见——注释已声明）。
- **恢复后应用层**：9 个 recover 失败只进 backupImportWarnings（13#20 不阻断不重复追加）；导入的 plan 能被 adopt（round-trip 断言）；running 任务置 interrupted 不重跑/不重传；导入的 queued/parsing 资料真正 respawn 解析。

### 99#1 备份导入的资料镜像重建先于 materials 表导入——导入完成后资料库缺条目直到下次资料操作

- 位置：`desktop/src-tauri/src/backend/backup/transfer.rs:1189-1191`（`import_kv(transfer, tx)?` 在 `for table in ordered` 循环之前执行——materials 行在循环中才插入）；`transfer.rs:1126-1127`（import_kv 尾部 `materials::sync_resources(tx)?` + next_revision）；sync_resources（materials/mod.rs:359-364）`DELETE FROM kv WHERE namespace='resources'` 后按 **materials 表当前内容**重建镜像——此刻只看到目标库旧资料。
- 传递链条：①import_full_backup → import_rows → import_kv → sync_resources（镜像=旧库资料） → ②ordered 循环随后才插入备份的 materials 行（镜像不含它们） → ③前端资料库页（Library.tsx:45 的 resources prop ← app_state ← store.rs:546-548 读 kv）不显示导入资料，直到任意资料增删/解析触发全量重建才自愈。round-trip 测试只断言 plan JSON 的 materialId（tests.rs:254），镜像无覆盖。
- 影响范围：导入回执显示资料计数，但界面资料库缺条目——用户感知「导入丢了资料」，与「真实持久化」的产品承诺相悖；触发自愈前持续误导。
- 修复方向：把 sync_resources + next_revision("resources") 从 import_kv 移到 import_rows 的 ordered 循环之后；补镜像内容断言的 round-trip 测试。

### 99#2 Gemini 拦截类 finishReason（RECITATION/BLOCKLIST/PROPHIBITED_CONTENT/SPII/OTHER）静默按成功收尾或退化成 empty_completion

- 位置：`desktop/src-tauri/src/backend/providers/gemini.rs:255-261`（只对 `reason == "SAFETY"` 报 content_blocked；其余拦截类 done=true、无 error；promptFeedback.blockReason 有处理 :189-195）。
- 传递链条：①Gemini 因复读/违禁词/敏感内容截断 → finishReason=RECITATION 等 → ②a 有部分文本：status="done" 落库，用户拿到**无提示的截断答案** → ②b 无文本：finish() 报泛化 `empty_completion`（「模型没有返回文本内容或工具调用」） → ③真实拦截原因对用户完全丢失。对照 SAFETY 路径用户可见 content_blocked + 中文原因。
- 影响范围：Gemini 用户的安全/合规拦截被误呈现为成功截断或莫名其妙的空响应——讲义/答案静默缺尾不可察觉。
- 修复方向：RECITATION/BLOCKLIST/PROHIBITED_CONTENT/SPII 并入 content_blocked（带 reason 文案），OTHER 归 incomplete_stream。

### 99#3 熔断与 failover 仅在 routing 模式生效，但失败计数在所有模式照写——跨模式语义不对称且聚合冗余形同虚设

- 位置：`desktop/src-tauri/src/backend/providers/routing.rs:989`（failover 候选仅 `mode == "routing"` 构建）、`:1027`（circuit_permit 闸门仅 routing 检查）、`:1099/1123`（record_circuit 无模式门槛，Err/Ok 均调用）。
- 传递链条：①用户长期用 direct/aggregate 模式，某供应商持续 5xx → ②record_circuit 无模式判断，失败计数照常累计开闸 → ③切到 routing 模式后该供应商直接 circuit_open 被跳过（「从没配过路由却熔断」的困惑）；反向：aggregate 模式选中供应商失败后**不会**沿聚合内其他成员替补（select 只选一个 profile，无替补循环）——聚合的多供应商冗余在故障时不起作用。
- 影响范围：三模式语义不对称且无注释说明是否有意；aggregate 用户的故障可用性预期落空。
- 修复方向：明确语义——要么熔断/故障转移三模式一致（aggregate 失败沿 aggregate_provider_ids 替补），要么 record_circuit 按模式收窄并在 circuits() 快照标注计数来源模式。

### 99#4 备份导出盘满：atomic_export write_all 失败残留数 GB 临时文件 + 错误码泛化不能指明盘满

- 位置：`desktop/src-tauri/src/backend/backup/archive.rs:406`（VACUUM INTO 的 SQLITE_FULL 经 From<rusqlite::Error> → storage_failed，error.rs:51；86#3 注释自认「磁盘满与目录只读共用文案」）；`materials/mod.rs:1352-1357`（atomic_export 的 write_all 失败 `?` 直接返回，temporary（download-{n}）不清理；59#2/70#3 只治理 rename 失败路径）。
- 传递链条：①目标盘满 → ②a VACUUM INTO 阶段：错误传播、Workspace Drop RAII 清理、目标 .dtbackup 不受影响（正确） → ②b 内存 zip 已建成、write_all 写 temporary 中途盘满 → `?` 提前返回 → ③download-{n} 部分文件（可能数 GB）残留 + 用户只看到「无法读写本地数据」。

### 99#5 熔断失败计数无时间窗口、仅成功清零——跨天偶发失败可凑满开闸

- 位置：`desktop/src-tauri/src/backend/providers/routing.rs:730-743`（`failures.saturating_add(1)` 无时间戳无衰减；仅 `success` 分支清零）。
- 传递链条：①供应商周一失败 1 次、周四失败 1 次、次周二失败 1 次（期间无成功请求） → ②计数累计到 3 → ③熔断打开 60s+，用户视角「这周才错三次就熔断」。
- 影响范围：低频使用供应商的熔断语义失真（滑动窗口缺失）。
- 修复方向：记录 last_failure_at，超窗口（cooldown 的数倍）清零计数；或改滚动窗口。

### 99#6 三域保留窗口异构（route_runs 1000 / provider_requests 20000 / events 90d+20000）——异常库态下跨表悬挂引用使备份导入整单拒绝

- 位置：`maintenance/mod.rs:864-880`（三处裁剪口径各异）；`backup/transfer.rs:999-1008`（导入 transform 双查失败即整单 `invalid_backup_reference`——仅 provider_requests→provider_route_runs 一个 lenient 分支，其余引用无降级）。
- 传递链条：①维护裁剪按各自窗口删行（正常运行下引用关系保持自洽——已推演核实） → ②但手工裁剪/外部工具改动/历史版本库升级等异常态下，runs/attempts/requests 之间的引用可能出现单侧悬挂 → ③该库的全量备份在导入时 transform 双查失败，**整单**拒绝且无 lenient 降级——用户无法用备份恢复，只能手改库。
- 影响范围：仅异常库态触发（正常使用不触发）；一旦触发备份完全不可用，恢复路径阻断。
- 修复方向：统一三域保留口径（同一时间窗+计数兜底）；或导入 transform 对悬挂引用提供 lenient 降级（跳过该行并计入 backupImportWarnings，复用 AppSnapshot.backupImportWarnings 通道）。

### 99#7 半开探测被取消回 open 但 opened_at 不刷新——冷却判定立即失效，可形成探测-取消振荡

- 位置：`desktop/src-tauri/src/backend/providers/routing.rs:717-729`（cancelled 分支保留旧 opened_at；对照失败分支 :733 重新起算）。
- 传递链条：①冷却期满探测发起（opened_at 已老） → ②用户取消 → ③状态回 open 但 opened_at 仍是旧值 → 冷却判定 `now < opened + cooldown`（:676）恒假 → 下一个请求立刻再探测；反复取消可振荡。
- 影响范围：取消高频场景才有感；探测请求本身有成本。
- 修复方向：cancelled 分支在 half_open→open 时同步 opened_at=now()，或维持 half_open 等待下次探测结果。

### 99#8 SSE EOF 零行判定先于尾行处理——无终止符单事件流被误分类为 endpoint_unreachable

- 位置：`desktop/src-tauri/src/backend/providers/protocol.rs:379-391`（openai.rs:1262-1275 同构：`processed_lines == 0` 判定在 `process(&pending)` 之前）。
- 传递链条：①非标网关整流只发一条**无终止符**的最终 data 行后关连接 → ②该行滞留 pending、processed_lines==0 → ③误报 `endpoint_unreachable`（「未收到任何事件」），尾行被丢弃；四次重试后用户看到的错误与事实不符。
- 影响范围：低（需规格违反型服务端）；有终止符的尾行处理正确。
- 修复方向：EOF 分支先 process(&pending) 再按「是否收到过任何事件（含尾行）」分类。

### 99#9 Responses API 未覆盖事件静默丢弃（`_ => {}`）——output_text.done-only 流退化为 empty_completion；refusal 无区分标记

- 位置：`desktop/src-tauri/src/backend/providers/responses.rs:315`（`_ => {}` 无日志无诊断）；`:132-135`（response.refusal.delta 当普通正文 emit）。
- 传递链条：①个别代理只发 `response.output_text.done`（携带全文）不发 delta → ②事件被丢弃、output.text 为空 → ③finish 报泛化 empty_completion，真实全文丢失；拒答内容与正常输出混排无标记。
- 影响范围：低——官方流 delta 齐全时无损；1MB/64KB 上限兜底。丢弃本身 fail-open。
- 修复方向：output_text.done 在 text 为空时作兜底全文接收（至少记诊断事件）；refusal 单独标记。

### 99#11 record_circuit 每次成功请求都 UPSERT + 发 circuit_changed 事件——events 表每请求多一行噪音

- 位置：`desktop/src-tauri/src/backend/providers/routing.rs:744-754`（状态无变化也写库发事件）。

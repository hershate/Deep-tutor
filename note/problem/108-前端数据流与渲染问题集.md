# 108 号：前端数据流与渲染问题集（第三十六轮·专项审计）

审计基线：`32d95533`（代码 = 1.1.5 `b57f260a`）。审计面：useBackendState 快照/去抖/迟到
防护链、事件驱动刷新（useAgent/useProviderChat 族）、大列表渲染与封顶、React 正确性横切、
状态一致性、样式渲染性能。历史 51/80/32#18 之后的增量与未覆盖面。本轮正面结论：迟到快照
防护三件套、sync 去重排队、登录切换隔离、监听器零泄漏、序号守卫全仓覆盖（除 108#4）、列表
封顶（除笔记）全部有效（见文末）。共 4 P3 + 3 信息。

## P3

### 108#1 Library 笔记网格：每卡片对 overview 做两次线性 find（O(N²)/渲染）且无渲染封顶——大库下搜索击键与每次快照同步都可感卡顿直至冻结

- 位置：`desktop/src/pages/Library.tsx:368`（卡片 JSX 同一表达式内 `libraryOverview?.notes.find(item => item.noteId === note.id)?.links.length` 调用两次）；后端 `notes/library.rs:72-97` 对每条笔记都产出一行——find 的被查表长度 = 笔记总数 N，卡片数也 = N；notes-grid 是全仓唯一无渲染封顶的大列表（对照 Dashboard 100、Community 100、Review 200、错题 500、AgentTaskCenter 40、UsagePanel 200、Plan 50/500）。
- 传递链条：①Library 任意重渲染（搜索击键、openingNoteId 切换、父组件下传新 props）→ ②filteredNotes.map 重新执行全部卡片 JSX（useMemo 只缓存数组不缓存渲染）→ ③每卡两次 O(N) 线性扫描 → ④N=1000（单次 ZIP 导入即达，决策文档允许 1000 条/次、无总量上限）≈ 每击键 2×10⁶ 次比较，输入开始变顿；N=10000（口径上限）≈ 2×10⁸ 次，每次击键秒级冻结 + N 张卡 ≈10N 个 DOM 节点全量驻留。
- 影响范围：Library 笔记页的搜索/滚动/开关编辑器/快照同步期间的整页响应性；纯性能，数据无错误。
- 修复方向：渲染前一次 useMemo 把 overview.notes 建成 Map<noteId, links>（每卡 O(1)、只查一次）；notes-grid 加渲染封顶（如前 200 条+超限提示）。

### 108#2 笔记过滤 memo 随 notes 数组身份变化全量重算——每次窗口聚焦/事件簇同步都对全部笔记正文做拼接+小写化 O(总字节)

- 位置：`desktop/src/pages/Library.tsx:94`（`useMemo(() => notes.filter(… `${n.title}${n.excerpt}${n.content}`.toLowerCase().includes(…)), [notes, debouncedQuery, filter])`）；`useBackendState.ts:43`（每次 applySnapshot setSnapshot(next) 产生全新对象，notes 身份必变）；快照触发面：每 120ms 去抖事件簇、窗口 focus/visibilitychange（:201-202）、写后兜底同步、笔记保存。
- 传递链条：①80#5 只把击键频率降下来（query 250ms 去抖），memo 依赖含 notes 身份 → ②每次快照刷新 → ③对全部笔记的 title+excerpt+**content（单条上限 1MB）** 重新拼接并 toLowerCase——1000 条×50KB ≈ 50MB 字符串分配/次同步，主线程秒级 → ④与 108#1 叠加（重算后紧跟全网格重渲染）。
- 影响范围：驻留 Library 页期间的一切后台快照刷新/窗口聚焦/笔记写入。
- 修复方向：过滤基元化——memo 依赖 query/filter + 预建的 `id→小写语料` 索引（仅随内容版本重建），或以 versions.notes 游标作 memo key。附带：:95 filteredResources 用未去抖 query 与笔记口径不一，可顺手统一。

### 108#3 草稿自动保存事件驱动全局全量快照循环——笔记编辑期每次停顿触发一轮 MB 级 getAppState + 整树重渲染，快照对草稿路径完全无用

- 位置：`useBackendState.ts:195`（全局订阅无过滤 `onBackendEvent(requestSyncCoalesced)`）；`store.rs:806`（每次 save_draft 落 draft.saved 事件）；触发端 `Library.tsx:111-117`（编辑器 350ms 停顿自动保存）。
- 传递链条：①打字每次 ≥350ms 停顿触发 save_draft → ②同事务写 draft.saved 并 emit → ③该事件无专项监听（:192-194 注释自认全局快照是唯一消费路径）→ 120ms 尾沿去抖后 getAppState **全量**拉取（含全部集合与全部笔记正文，叠加 108#2 重算 + 108#1 网格重渲染）→ ④而草稿域在快照中只有 versions.drafts 计数，编辑器已从写回执拿到 revision——这轮全量拉取对草稿路径是纯浪费；写作期间每次停顿重复一轮；关闭笔记的 draft.deleted 同样触发一轮。
- 影响范围：笔记编辑体验（停顿即整树重渲染，随库规模放大）；与 103#6（后端重建成本）同一链条的前端半边，不重复。
- 修复方向：requestSyncCoalesced 对 draft.saved/deleted 跳过全量同步（单窗口下写回执已是权威）；或后端把草稿事件改轻量（不带集合版本推进，lastEventId 不动则快照守卫自然跳过）。

### 108#4 useAgent.refreshSession 无序号守卫、无节流——每个 agent.* 事件都全量拉会话，并发响应乱序可把已完成的 run 拉回「运行中」滞留

- 位置：`useAgent.ts:62-71`（refreshSession 直接 setSessions 覆写，无票据）；事件分发 :156-169（活动会话每个 agent.* 事件独立发起全量 getAgentSession）；后端每步 step_started + 每 tool_completed + message_saved + 终态事件（每步 3~10 个）。
- 传递链条：①25 步带工具的 run 期间每个事件一次全量拉取（会话载荷随 run 推进单调增长）→ ②两次 refreshSession 并发时 invoke 完成顺序无保证（全仓 51#1/51#2/76#8 等正因此到处加序号守卫，本函数是唯一漏网）→ ③窄窗口下旧快照后到覆写新状态——若覆盖的是 run_completed 之后的状态，UI 滞留「运行中」：发送框被禁用、步骤数停更 → ④无后续事件自愈，需手动取消或切换会话才恢复。
- 影响范围：AgentCenter 与全局导师抽屉（同用 useAgent）；正常顺序下仅多耗 IPC，乱序窗口窄但命中即「假运行中」。
- 修复方向：refreshSession 加 51#2 同型序号守卫；顺带对 agent.* 刷新做 150-300ms 合并（deltaThrottle 现成设施），把每步 3~10 次拉取压到每簇 1 次。

## 信息

### 108#5 窗口 focus 与 visibilitychange 双路径各拉一次全量快照，隐藏时也照拉

- 位置：`useBackendState.ts:201-202`（两个监听都调 refresh/sync）。
- 传递链条：①窗口激活 focus 先触发 requestSync（在途）→ ②紧随的 visibilitychange 再 sync()，命中 syncing 走 queued，第一轮完成后 do-while 再跑一轮——每次激活窗口 = 2 次全量快照 + 2 次整树渲染 → ③窗口隐藏时 visibilitychange 同样发起全量快照，结果无人消费（80#7e 在通知轮询修了同型，此处未覆盖）。
- 影响范围：每次窗口切换多 1-2 轮全量快照（随库规模放大 108#2 的重算与 108#1 的重渲染成本）；隐藏期拉取纯浪费；无正确性影响。
- 修复方向：visibilitychange 内判 document.hidden 直接 return；或只保留单路径。

### 108#6 Agent 流式输出期间每条 delta 重渲染整个 AgentCenter/TutorPanel，滚动跟随每 delta 强制读布局

- 位置：`useAgent.ts:150-152`（每条 chat_delta 一次 setStream）→ `AgentCenter.tsx:122-123`（消息列表与流式气泡同页内联无 memo 分层）、`:80-87`（滚动跟随 effect 依赖 stream.text，每 delta 读 scrollHeight/clientHeight 强制 reflow）。80#2 只 memo 了 StudyRoom 讲义区块。
- 传递链条：①高频分块供应商（数十 Hz）下每条事件一次 setState → 整页函数每 delta 重执行 → ②三栏全部 JSX 重建 reconcile → ③82#7 贴底跟随每 delta 一次强制 reflow。无状态错误（拼接与游标正确），CPU 峰值级开销。
- 影响范围：长会话（消息多）+ 高频流式期间 AgentCenter 与导师抽屉的 CPU 峰值（风扇噪音级）；无状态错误，流文本拼接与游标均正确。
- 修复方向：消息列表/流式气泡抽组件 memo 化；滚动跟随节流 ~150ms。

### 108#7 styles.css：sticky 顶栏常驻 backdrop-filter blur(16px)——滚动期间每帧对下层内容重模糊

- 位置：`desktop/src/styles.css:144`（.topbar sticky + backdrop-filter: blur(16px)）。
- 传递链条：①主内容滚动时顶栏下持续有新内容掠过 → ②WebView2 对全宽 backdrop 每帧重新采样模糊 → ③与大 DOM（108#1 万级卡片）叠加挤压滚动帧预算。初始集成即存在，历轮性能审计（80/103 号）均未覆盖 CSS 合成层。弹层类 blur(3-6px) 仅打开期存在，成本可接受；reduce-motion 双通道全覆盖无其他问题。
- 影响范围：全应用滚动流畅度的常驻税（每帧全宽重模糊）；与大 DOM 列表叠加时滚动掉帧最明显；量级未实测，方向性判断；弹层类与动画无其他问题。
- 修复方向：顶栏改不透明/半透明纯色，或降 blur(8px) 并验证帧率。

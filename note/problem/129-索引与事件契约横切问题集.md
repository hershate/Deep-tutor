## P3

### 129#1 learning_node_evidence 缺 plan_id 索引——无上限增长表的最高频过滤列全表扫，知识总览与全局搜索逐节点放大

- 位置：`desktop/src-tauri/src/backend/learning/mod.rs:188-197`（DDL 仅 id PK + plan_id FK，无任何以 plan_id 为首列的索引；唯一索引是 reports/mod.rs:197 的 created_at）。
- 传递链条：①表每次作答/复习/考试 UPSERT 且无上限增长（reports/mod.rs:196 注释自认——配 created_at 索引时已意识到膨胀却漏了 plan_id 面）；②全部业务查询按 plan_id 过滤：知识总览 `WHERE plan_id=? GROUP BY node_id`（learning/knowledge.rs:50，页面每次打开）；③全局搜索结果循环内**逐节点** `WHERE plan_id=? AND node_id=?`（engagement/mod.rs:486）——无索引时每次全表扫；④证据行积累到数万行后知识地图打开与搜索逐条放大为数十次全表扫。
- 影响范围：长期使用（证据行多）的知识地图打开与全局搜索节点结果（查询耗时随表线性放大）；新建用户与小库不受影响；纯性能，无数据错误。
- 修复方向：补 `CREATE INDEX learning_node_evidence_plan ON learning_node_evidence(plan_id, node_id)`（同时服务两类查询）。

### 129#2 plugin_deliveries 缺 event_id 前导索引——插件页热路径（overview 恒全量分支）全表扫+临时排序

- 位置：`desktop/src-tauri/src/backend/plugins/mod.rs:241-246`（PK(plugin_id,event_id) 无其他索引）；列表查询 `ORDER BY d.event_id DESC LIMIT 100`（:788）在 `plugin_id IS NULL` 分支无法用 PK（首列 plugin_id）。
- 传递链条：①overview() 恒以 events(state, None, None) 调用（:833）——全量分支是常态路径非冷路径；②前端 Integrations 页 loadEarlier 也传 undefined，且对 plugin./material./practice./knowledge. 四族事件 250ms 节流重拉 overview（Integrations.tsx:52-56）；③表行数 = 事件×插件，事件尾保留上限 2 万（maintenance :913），多插件时可观；④每次重拉都是全表扫+临时排序取前 100。
- 影响范围：安装多个事件插件且事件活跃时的插件页浏览（列表查询随表增长变慢）；单插件/无插件用户不受影响；纯性能。
- 修复方向：补 `CREATE INDEX plugin_deliveries_event ON plugin_deliveries(event_id DESC)`。

### 129#3 learning_plan_schedule_tasks 无 date 索引——通知概览的 30 秒轮询查询全表扫

- 位置：`desktop/src-tauri/src/backend/engagement/mod.rs:634`（`SELECT task_id … WHERE date <= ?1 AND date >= ?2` 无 plan 过滤的跨方案窗口查询）；表 PK 为 (plan_id, task_id)（learning/mod.rs:176）。
- 传递链条：①notification_overview 由 get_notifications 调用（engagement:785-787）；②前端 App.tsx:196-197 可见状态下每 30 秒轮询 get_notifications；③每次轮询对全部方案的全部排期任务全表扫；④表规模 = 各方案任务累计（单方案 500-10000），多方案数年使用后可观。
- 影响范围：长期多方案使用下的通知轮询常数开销（30s 一次全表扫）；新用户不受影响；纯性能。
- 修复方向：补 `CREATE INDEX learning_plan_schedule_tasks_date ON learning_plan_schedule_tasks(date)`。

### 129#4 死索引 ×3 + 重复索引 ×1——写放大清理族

- 位置与证据（均全仓正反 grep 复核）：`sync_jobs_created(created_at)`（`desktop/src-tauri/src/backend/sync/mod.rs:161`——全部查询走 rowid/PK/status/kind）；`project_versions_requests(request_id)`（projects/mod.rs:142——request_id 只写入（:349/:596）无过滤查询，含 backup/transfer 侧）；`learning_plan_steps_requests(request_id)`（learning/mod.rs:163——steps 查询全按 plan_id(+step_index/status)，:557-559 的 request_id 是子查询取值非过滤键）；`project_versions_project(project_id, version_number DESC)`（projects/mod.rs:141——与 UNIQUE(project_id,version_number) 隐式索引重复服务 MAX 查询 :338）。
- 传递链条：①每次对四张表的 INSERT/UPDATE 都要维护对应索引（B-tree 写放大）；②三个死索引无任何查询消费——纯写开销；③重复索引使 project_versions 每次版本写入维护两棵等价 B-tree；④长期使用中这些开销累积而查询侧零收益（agent_tool_calls_run 初判死索引经复核 :1318 有消费，不立案——佐证复核方法在案）。
- 影响范围：全部安装的对应表写入路径（每次写多维护 1-2 棵无用 B-tree）；读路径与查询正确性不受影响；纯资源浪费，无行为损害。
- 修复方向：迁移 DROP 三个死索引与一个重复索引（backup 侧已核实无 request_id 消费）。

### 129#5 低危索引观察两条——agent_messages 前导 LIKE 与 agent_sessions 排序

- 位置：`desktop/src-tauri/src/backend/agent/tools.rs:720`（history.search 的 `%query%` 前导通配 LIKE）；`agent/mod.rs:467`（`ORDER BY updated_at DESC LIMIT 50` 无索引）。
- 传递链条：①模型调用 history.search 工具 → 前导 % 通配使 B-tree 失效 → agent_messages 全表扫描（每次工具调用一次）；②agent_sessions 列表每次排序无索引支撑——表为用户手建会话（通常 <50 行）排序成本可忽略；③两者表规模都受配额/使用习惯约束——实际可感阈值未到。
- 影响范围：大会话量下模型高频使用 history.search 的场景（全表扫叠加）；常规会话量与其余 agent 查询（五索引全消费）不受影响；设计限制观察项（前导 LIKE 需 FTS5 才可优化），无行为错误。
- 修复方向：暂不修（记录在案）；若未来 search 工具高频使用再评估 FTS5。

### 129#6 agent 事件归属键缺口族——122#8 复核仍在 + approval_cancelled/memory_changed 同缺 + answer_submitted 载荷形状漂移

- 位置：`agent.run_completed/cancelled/degraded/failed` 载荷仍无 sessionId（`desktop/src-tauri/src/backend/agent/mod.rs:885-893`；122#8 已立案——前端 runOwners 内存映射补偿在位，发布形态不可触发错误归属）；**新增**：`agent.approval_cancelled {approvalId,kind}`（唯一既无 sessionId 又无 runId 的 agent 事件）与 `agent.memory_changed {approvalId,key,action}`（tools.rs:832-852）同样无归属键；`practice.answer_submitted` 双发射点载荷不同（subjective.rs:519-527 含 requestId、practice/mod.rs:1331-1341 不含）。
- 传递链条：①未来任何按事件驱动的消费者（声明式插件/新页面）订阅 agent.*；②审批取消与记忆变更事件到达——载荷只有 approvalId/key，无会话/运行归属键；③消费者无法把事件关联到具体会话（需另查 approvals 表反查）；④answer_submitted 形状漂移：两发射点载荷键集不同——按 requestId 分支的消费者在主观题路径拿到 undefined；当前前端均不读这些键，实害为零。
- 影响范围：未来事件驱动消费者对这三个 kind 的归属判定与形状假设（契约坑）；当前零消费方与 run_* 的补偿机制（runOwners）不受影响；契约完备性，无现行行为错误。
- 修复方向：载荷统一补归属键（sessionId 或 runId）；两发射点 answer_submitted 载荷对齐（随 122#8 修复一并）。

### 129#7 step_completed 是否应入 isCancelRace 白名单——恢复按钮与步骤自行完成的竞态边角

- 位置：`desktop/src-tauri/src/backend/learning/mod.rs:689`、`lecture.rs:480`（「该步骤已经完成，不会重复执行」）。
- 传递链条：①用户点「从已保存步骤恢复」；②与该步骤自行完成（事件在途/UI 未刷新）毫秒交叠；③resume 命中 step_completed → 前端不在 isCancelRace 白名单 → 弹出「该步骤已经完成…」toast；④语义与已白名单的 plan_active/run_active 同族（操作与状态迁移的良性交叠）——其他交叠静默、这个弹提示，口径不一；toast 文案自释，无误导。
- 影响范围：恢复操作与步骤完成交叠的窄窗口（多一条自释 toast）；其余 race 家族（tool_call_conflict/grading_in_progress/answer_already_*——需用户行动或自释双击场景）维持现状合理；恢复操作的正常路径与其余已白名单 race 码（静默语义不变）不受影响；体验一致性边角，无功能损害。
- 修复方向：产品定夺是否入白名单静默；不入则维持现状（文案已自释）。

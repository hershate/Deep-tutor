## P3

### 129#1 learning_node_evidence 缺 plan_id 索引——无上限增长表的最高频过滤列全表扫，知识总览与全局搜索逐节点放大

- 位置：`desktop/src-tauri/src/backend/learning/mod.rs:188-197`（DDL 仅 id PK + plan_id FK，无任何以 plan_id 为首列的索引；唯一索引是 reports/mod.rs:197 的 created_at）。
- 传递链条：①表每次作答/复习/考试 UPSERT 且无上限增长（reports/mod.rs:196 注释自认——配 created_at 索引时已意识到膨胀却漏了 plan_id 面）；②全部业务查询按 plan_id 过滤：知识总览 `WHERE plan_id=? GROUP BY node_id`（learning/knowledge.rs:50，页面每次打开）；③全局搜索结果循环内**逐节点** `WHERE plan_id=? AND node_id=?`（engagement/mod.rs:486）——无索引时每次全表扫；④证据行积累到数万行后知识地图打开与搜索逐条放大为数十次全表扫。
- 影响范围：长期使用（证据行多）的知识地图打开与全局搜索节点结果（查询耗时随表线性放大）；新建用户与小库不受影响；纯性能，无数据错误。
- 修复方向：补 `CREATE INDEX learning_node_evidence_plan ON learning_node_evidence(plan_id, node_id)`（同时服务两类查询）。

### 129#2 plugin_deliveries 缺 event_id 前导索引——插件页热路径（overview 恒全量分支）全表扫+临时排序

- 位置：`desktop/src-tauri/src/backend/plugins/mod.rs:241-246`（PK(plugin_id,event_id) 无其他索引）；列表查询 `ORDER BY d.event_id DESC LIMIT 100`（:788）在 `plugin_id IS NULL` 分支无法用 PK（首列 plugin_id）。
- 传递链条：①overview() 恒以 events(state, None, None) 调用（:833）——全量分支是常态路径非冷路径；②前端 Integrations 页 loadEarlier 也传 undefined，且对 plugin./material./practice./knowledge. 四族事件 250ms 节流重拉 overview（Integrations.tsx:52-56）；③表行数 = 事件×插件，事件尾保留上限 2 万（maintenance :913），多插件时可观；④每次重拉都是全表扫+临时排序取前 100。
- 影响范围：安装多个事件插件且事件活跃时的插件页浏览（列表查询随表增长变慢）；单插件/无插件用户不受影响；纯性能。
- 修复方向：补 `CREATE INDEX plugin_deliveries_event ON plugin_deliveries(event_id DESC)`。

### 129#3 learning_plan_schedule_tasks 无 date 索引——通知概览的 30 秒轮询查询全表扫

- 位置：`desktop/src-tauri/src/backend/engagement/mod.rs:634`（`SELECT task_id … WHERE date <= ?1 AND date >= ?2` 无 plan 过滤的跨方案窗口查询）；表 PK 为 (plan_id, task_id)（learning/mod.rs:176）。
- 传递链条：①notification_overview 由 get_notifications 调用（engagement:785-787）；②前端 App.tsx:196-197 可见状态下每 30 秒轮询 get_notifications；③每次轮询对全部方案的全部排期任务全表扫；④表规模 = 各方案任务累计（单方案 500-10000），多方案数年使用后可观。
- 影响范围：长期多方案使用下的通知轮询常数开销（30s 一次全表扫）；新用户不受影响；纯性能。
- 修复方向：补 `CREATE INDEX learning_plan_schedule_tasks_date ON learning_plan_schedule_tasks(date)`。

### 129#6 agent 事件归属键缺口族——122#8 复核仍在 + approval_cancelled/memory_changed 同缺 + answer_submitted 载荷形状漂移

- 位置：agent.run_* 终态仍无 sessionId（mod.rs:885-893，前端 runOwners 内存映射补偿——122#8 已立案，本轮复核确认补偿机制在位、发布形态不可触发错误归属）；**新增**：`agent.approval_cancelled {approvalId,kind}`（唯一既无 sessionId 又无 runId 的 agent 事件）与 `agent.memory_changed {approvalId,key,action}`（tools.rs:832-852）同样无归属键——当前前端零消费（走命令返回值），属未来消费者的契约坑；`practice.answer_submitted` 双发射点载荷不同（subjective.rs:519-527 含 requestId、mod.rs:1331-1341 不含——前端不读键无实害，形状不稳定）。

- 修复方向：载荷统一补归属键（sessionId 或 runId）；发射点载荷形状对齐。

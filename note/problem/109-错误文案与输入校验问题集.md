## P3

### 109#1 流式模型请求非 200 时错误 body 整体丢弃——检测入口有 55#4 细节提取，主生成路径没有，同一故障两种信息量误导排障

- 位置：`providers/protocol.rs:282-285`（`if status != 200 { return Err(http_error(status)) }`——Anthropic/Gemini/Responses 三协议流式共用）、`openai.rs:1179-1182`（OpenAI Chat 内联流式同款）；对照 `openai.rs:341-380`（read_json 的 55#4 修复：读 body 前 4KB 提取 /error/message 或剥 HTML 拼「（服务返回：…）」）；`protocol.rs:493-505`（chat_once 对非 OpenAI Chat 协议也走流式）。
- 传递链条：①兼容/官方供应商在**真实生成请求**上返回非 200+body 说明（欠费 402、模型名错 400、配额/权限，兼容服务高频）→ ②流式路径只按状态码映射 http_error（`_ =>` 兜底「供应商返回了不可用的响应」），body 未读一字节 → ③错误经 request.error → run/plan/lecture/practice 的 .error → ④方案生成页/学习空间/导师抽屉只显示「provider_error：供应商返回了不可用的响应」；而**同一供应商同一故障**在「检测→读取模型列表」（read_json）却显示「（服务返回：Insufficient Balance）」——用户据此误判「检测通过=配置无误，是应用坏了」。
- 影响范围：全部真实生成路径的非 200 上游错误；SSE 200 内嵌 error 已由 99#2/55#3 覆盖，缺口仅在非 200。
- 修复方向：把 read_json 的 4KB body 提取抽成共享 helper，两处流式 non-200 分支同口径拼接；顺带 http_error 的 408/429 补「请稍后重试」。

### 109#2 同步域 HTTP 状态码到文案映射缺失——401/403/429 一律「远端同步服务返回 HTTP {n}」，三域映射深度不一致

- 位置：`sync/transport.rs:150-155、174-178、189-193`（三处同款裸状态码文案）；对照供应商域 `openai.rs:398`（401/403→「请检查 API Key」）与网页域 `web/mod.rs:192-199`（403/429→「请等待一段时间后再试」）。transport.rs:37 注释自认 S3 签名问题「即 403 且排障方向被误导到凭据」。
- 传递链条：①用户配置 WebDAV/S3（凭据错误、权限不足、时钟偏移致 SigV4 403、限流——同步最高频失败族）→ ②远端返回 401/403/429 → ③统一裸状态码 → ④SyncPanel 显示「sync_http_error：远端同步服务返回 HTTP 403」——无从区分凭据/权限/时钟/限流四个方向，无自救指引；同一数字在供应商域却有明确指引。
- 影响范围：所有同步配置失败与任务失败的排障面。
- 修复方向：按状态码分桶映射（401/403→核对凭据与系统时钟、429→稍后重试、5xx→服务暂不可用），保留数字附注。

### 109#3 invalid_persisted_plan 族 30 处文案只陈述内部数据缺失事实，无一条自救指引——最大的无指引错误家族

- 位置：`learning/pipeline.rs:395-468`（29 种事实陈述）、`agent/tools.rs:144`、`practice/mod.rs:344`；UI 直出面 `Plan.tsx:189`、`PlanGenerator.tsx:321`（`{code}：{message}` 仅附「查看真实生成步骤」跳转，非恢复路径）。
- 传递链条：①方案行存在但 artifacts 断链（102#1 的导入裁剪、外部改库、写中断）→ ②get/resume/adopt/generate 返回「invalid_persisted_plan：已保存的知识图谱缺失」→ ③前端原样直出 → ④用户面对「缺 X」的技术陈述没有任何下一步动作；对照 database_corrupt（「换空目录+全量备份导入恢复」）、disk_full（「清理空间」）均有自救路径。
- 影响范围：持久化断链方案的全部操作入口（详情/恢复/采用/练习/讲义）。
- 修复方向：族文案统一追加「该方案数据不完整，请重新生成或新建方案」；或 get_learning_plan 对断链方案返回可重建的降级状态而非裸错误。

### 109#4 笔记正文是全库唯一「后端 1MB 硬限、前端零钳制」的高频用户输入——粘贴超限文本后保存必败且草稿自动暂存逐次报错

- 位置：前端缺口 `Library.tsx`（正文 textarea `onChange={e => { setNoteContent(e.target.value); setDirty(true) }}` 无 clampToBytes；同文件标题 500/标签 100 均已钳制，全文件仅 2 处 clampToBytes）；footer 计数按 UTF-16 码元显示与后端字节口径不一致（纯中文 33 万字即达 1MB，用户无从预判）。后端限制 `store.rs:1132`（notes 集合 content MAX_RECORD_BYTES=1MB）与 :1056-1060（record_too_large 整单拒绝）；草稿同限（store.rs:1301-1305）。放大器 `Library.tsx:112-117`（350ms 去抖草稿自动保存 catch(reportBackendError)，draftBlocked 只对 revision_conflict 置位，record_too_large 不停循环）。
- 传递链条：①用户粘贴大段参考材料（>1MB 常见）→ ②350ms 后自动暂存失败报「草稿超过 1MB 上限」，此后每次编辑停顿再报一次 → ③点「保存笔记」撞 record_too_large 整单拒绝（弹窗保留、输入不丢，有中文文案）→ ④footer 始终显示「N 字 · 草稿自动暂存中」与实际（持续失败）不符；用户只能自行猜出是正文超限。
- 影响范围：笔记编辑主路径（新建/编辑共用）；标题/标签/摘录均对称，唯正文不对称。
- 修复方向：正文与草稿链路补 clampToBytes（建议 1,000,000 给整条 JSON 预留头部）；至少对 record_too_large 同置 draftBlocked 消除重复报错；footer 改 utf8Bytes 口径。

### 109#5 复习卡 create/update 后端对 front/back/tag 零校验——与全部同族域不一致，备份导入路径可把超长/空卡带入渲染与 Anki 导出

- 位置：`review/mod.rs:275-286`（create 直接 `params![…, input.front.trim(), input.back.trim(), …]` INSERT）、`:288-310`（update 同款；整个函数除 validate_scope 外无长度上限、无非空校验——front="" trim 后空串照样入库，tag 空串有「手动创建」兜底唯独 front/back 无）；前端 `Review.tsx:174`（front 8000/back 20000/tag 100 + 必填守卫）；旁路 `backup/transfer.rs:1215`（import_rows 按列逐字复制，不做字段校验）+ 编辑回流 `Review.tsx:106`（库值载入表单不过 onChange 不重新 clamp）。
- 传递链条：①正常 UI 用户被前端约束；但注入脚本直接 invoke，或导入字段异常的备份包 → ②空 front 或任意长度 front/back 直接入库 → ③next_review_card 把该卡推上复习界面全文渲染（无 XSS，纯布局破坏）；管理列表同样全文渲染 → ④export_content(scope=Review, format=Apkg) 把全文写入 flds/sfld，超长卡使 apkg 体积与 Anki 导入耗时同步膨胀；空卡造成「正面空白」的卡进入到期队列。对照 community/practice/notes/tasks/projects/learning/providers/security/sync 全部有后端校验——review 是唯一「用户内容字段后端零校验」的域。
- 影响范围：review 域读写与 Anki 导出；条件触发（异常备份导入或脚本注入），无数据损坏无 XSS。
- 修复方向：create/update 补齐与前端同界校验（front 非空 ≤8000、back 非空 ≤20000、tag ≤100，invalid_card 类型化）；备份导入侧可选复用同一校验。

### 109#7 同一「复习卡」概念在错误文案中三名混用：记忆卡/卡片/复习卡

### 109#8 前端契约守卫的开发者术语报错直达用户（「后端 JSON 键变更？」）

### 109#9 对话框插件原始错误未映射——91#1 只修了 opener 一处，plugin:dialog|* 九处直通

- 位置：`client.ts:385/393`、`notes.ts:9`、`backup.ts:22-23`、`storage.ts:19`、`sharing.ts:30-31`、`reports.ts:72` 共 9 处；各调用点 catch → String(error) 分支英文原文。取消路径返回 null 不走此通道，触发概率低（shell COM 故障）。
- 传递链条：①对话框子系统异常（shell COM 故障等罕见情形；用户取消返回 null 不走此通道）→ ②plugin:dialog 以英文原始串 reject → ③九处调用点的 catch 经 backendErrorMessage 落入 String(error) 分支 → ④toast 显示英文原文——正是 91#1 在 opener 消灭的形态在 dialog 族残留。
- 影响范围：9 个文件选择/保存入口（资料导入/备份选择/导出落盘/分享包/报告）；触发概率低，触发后仅文案不友好，重试即可，无数据影响。
- 修复方向：封装层统一映射「无法打开系统对话框，请重试」。

### 109#10 API Key 前端钳制 4096 与后端 1200 不符——54#1 收紧后端时前端未同步

- 位置：`ProviderHub.tsx:410`（clamp 4096）vs `providers/mod.rs:480-483`（>1200 即 invalid_credential）。
- 传递链条：①用户粘贴 1200-4096 字节的 Key（个别自建网关长 JWT）→ ②前端 clampToBytes(4096) 放行 → ③保存时后端 >1200 即 `invalid_credential` 拒绝 → ④错误文案带长度指向（「不超过 1200 字节」）可自救，但输入期无预兆、前端先放行后端再拒的两段式体验。
- 影响范围：仅超长 Key 场景（主流 Key 远短于 1200）；54#1 收紧后端时前端未同步的单点不对称，无数据影响。
- 修复方向：前端 clamp 降为 1200。

### 109#11 表单直连路径未复用 deep_link 的 display_safe——控制字符/RTL 覆写可经 upsert 写入供应商档案名

- 位置：`providers/mod.rs:429-433`（name 只查非空+≤100）对照 `:743-751`（deep_link 有 display_safe 滤 is_control 与 bidi 区段，85#2）。
- 传递链条：①注入脚本或异常配置导入对 upsert_provider_profile 传含 U+202E 等 bidi 覆写/控制字符的 name → ②validate_input 只查非空+≤100，通过入库 → ③ProviderHub 列表以 React 文本渲染（自动转义无 XSS），bidi 使条目文字视觉反排/伪装 → ④与 85#2 已堵死的 deep_link 入口口径不一致，同一伪装面在表单路径敞开。
- 影响范围：供应商档案列表的文案伪装面（钓鱼/误导）；本地单用户威胁模型下可利用性低（需注入或异常导入）；无 XSS、无数据损坏。
- 修复方向：validate_input 对 name/default_model/note 复用 display_safe；或在 85#2 注释说明表单路径的有意取舍。

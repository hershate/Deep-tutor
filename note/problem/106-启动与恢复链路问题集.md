# 106 号：启动与恢复链路问题集（第三十六轮·专项审计）

审计基线：`32d95533`（代码 = 1.1.5 `b57f260a`）。审计面：main.rs 装配/verify/panic/退出/
单实例，startup.rs 目录决策/pointer/initialize/ensure_ready/重试，12 域 recover 家族语义
与覆盖，启动时序竞态，退出与崩溃窗口，数据目录决策链。本轮正面结论：recover 覆盖完整
（15 张含 running 态的表全部有翻转者）、崩溃一致性模型（WAL+终态先落盘+下次启动 recover）
成立、pointer 决策链分支齐备（见文末）。问题集中在启动/重试的前端-后端时序、跳过 recover
的会话边界、restart 与单实例互斥体的竞态。共 5 P3 + 4 信息。

## P3

### 106#1 前端 bootstrap 硬超时 20s 撞上 >20s 的后端初始化——错误页常驻无自动回正，「重试初始化」不重跑 bootstrap

- 位置：`desktop/src/backend/useBackendState.ts:129-137`（20s deadline，仅 `startup_not_ready` 250ms 轮询，超时 throw）、`:83-110`（fail() 对非 database_busy/非认证错误 `settled=true` 落错误页）、`:111-120`（armTimeout 同 20s）；`desktop/src/components/DataDirectoryPanel.tsx:59-71`（错误页「重试初始化」仅调 retry_storage_initialization，成功且 ready 时只显示「初始化状态正常，无需处理」，注释 A-6 明确不 reload）；唯一回正通道 `useBackendState.ts:201-202`（窗口 focus/visibilitychange → sync → getAppState 成功 → setReady(true)）。后端慢初始化源：`store.rs:190-213`（user1 首迁整库 fs::copy，GB 级+慢盘/杀软扫描可超 20s）。
- 传递链条：①旧版单库用户首升启动或慢盘大库，initialize_background >20s，期间 guard 对每条 invoke 回 `startup_not_ready` → ②前端 20s 轮询窗口耗尽抛出 → fail() → 错误页 → ③后端在 25s/40s 处初始化成功（BackendState 就绪），但 useBackendState 已 settled，不再有任何轮询或事件触发重试 → ④用户面对「本地数据或实时连接打开失败」页；点「重试初始化」得到「初始化状态正常，无需处理。」却仍停在错误页；知情者切走再切回窗口可触发 focus 恢复，但该自救完全不可发现。
- 影响范围：初始化 >20s 的启动（大库首迁/慢盘/杀软）；错误页与实际状态自相矛盾（面板徽章「当前使用」+顶部报错「打开失败」）。
- 修复方向：fail() 对 startup_not_ready 单独放宽（持续轮询 getStorageOverview.initializing，就绪后自动重跑 start()）；或 DataDirectoryPanel 重试成功且 ready 时通知 useBackendState 重新 bootstrap。

### 106#2 reauthentication_required 启动跳过全部 recover，登录换库不补偿——僵尸 running 行在会话内不可取消/恢复/删除

- 位置：`desktop/src-tauri/src/startup.rs:393-398`（`reauthentication_required` → principal=None）、`:400-422`（`if let Some(principal)` 才执行 store 换库 + 12 域 recover + 调度器）；`security/guard.rs:128-217`（switch()：login/PAT 换库只做 stop_all + store swap + resume 重启调度器，无任何 recover）；全仓 recover 调用点仅 startup.rs:407-416 与 backup/mod.rs:107-162。
- 传递链条：①用户工作中有任务在跑，应用崩溃行停留 running，随后会话过期（或凭据失效，或 103#8 场景成员 keyring 槽丢失时启动自动签发管理员、recover 跑在管理员工作区）→ ②下次启动 current() 返回 session_expired → principal=None → 整段 recover 跳过 → ③用户登录 switch 换到自己的库，仍无 recover → ④僵尸行后果（逐一核实）：Agent 会话 send 撞 `run_active`、cancel 撞 `no_active_run`、resume 要求终态、delete 被运行检查拦——四路全堵；方案/练习/讲义同型（no_active_plan/no_active_generation 均要求内存 flag）。唯一自愈是再重启一次。
- 影响范围：多用户库 + 会话过期/凭据丢失的崩溃残留；单管理员默认路径不触发。数据不丢，但会话内死状态且报错文案误导。
- 修复方向：switch() 换库成功后对该用户工作区执行一次 recover 家族（与 startup 同序）；或 login 命令体内补偿。

### 106#3 app.restart() 先启后退与单实例命名互斥体竞态——「保存并立即重启」可能变成「直接退出不回来」

- 位置：`desktop/src-tauri/src/startup.rs:509-512`（restart_application → app.restart()）；tauri 2.12.5 process.rs（`Command::new(path).spawn()` **先启动新进程**，旧进程随后才 exit(0)——互斥体句柄要到旧进程完全终止才释放）；`main.rs:113-124`（新进程 acquire() 撞 ERROR_ALREADY_EXISTS 即判「已有实例」→ focus_existing（聚焦的正是垂死的旧窗口）→ 第二实例退出）。
- 传递链条：①用户改数据目录点「保存并立即重启」→ ②app.restart() spawn 新进程后旧进程开始退出，退出前仍持有互斥体 → ③若新进程跑到 CreateMutexW 时旧进程尚未完全终止（DLL detach 被杀软/负载拖慢、新进程热启动快）→ ④新进程判「已运行」→ 聚焦旧窗口后自杀，旧进程随即退出——应用整体关闭不再自动启动；用户手动重开才生效（pointer 已保存，无数据丢失）。
- 影响范围：所有「保存并立即重启」操作的小概率竞态窗口；46#1 单实例机制与 tauri restart 的组合盲区。
- 修复方向：重启路径给新进程传参使其对 ALREADY_EXISTS 做短重试窗口（如 2s 内重试 acquire）；或改先 exit 再由外部拉起。

### 106#4 retry_storage_initialization / set_storage_location 同步命令在主线程跑全量 assemble（含整库复制迁移）——重试期间整窗冻结，且无 catch_unwind

- 位置：`desktop/src-tauri/src/startup.rs:466-487`（retry_storage_initialization 为同步 `#[tauri::command]`，直调 initialize → assemble：可能执行整库 fs::copy + 15 域 migrate + 12 域 recover）；`:489-498`（set_storage_location 同步执行 save_location → Store::root 打开校验）；对照 initialize_background（:328-350）用后台线程 + catch_unwind，retry 直调无 panic 捕获——panic 沿主线程杀进程。90 号移后台家族的漏网成员（103#7 清单未含启动域命令）。
- 传递链条：①首次初始化失败 → ②用户点「重试初始化」→ 同步命令主线程执行全量 assemble → ③大库首迁/慢盘下主线程阻塞数秒到数十秒——窗口冻结、Windows 标记「未响应」→ ④期间 assemble 若 panic（无 catch_unwind），进程直接崩溃退出而非展示类型化错误，与 initialize_background 的失败恢复 UI 承诺分叉。
- 影响范围：初始化失败后的重试与目录保存；条件为慢初始化（同 106#1 触发面）。
- 修复方向：按 90 号范式移 spawn_blocking（StartupState 自带原子/互斥量可跨线程），补 catch_unwind 与 initialize_background 同口径。

### 106#5 单实例命名互斥体无 Global\ 前缀——同一 Windows 账号的两个交互会话（快速用户切换/RDP+本地）可双开

- 位置：`desktop/src-tauri/src/main.rs:114`（`wide("DeepTutor-SingleInstance-7f3a9c2e")`——无 `Global\` 前缀，命名内核对象创建于会话本地命名空间）、`:142-156`（acquire/focus 路径）。
- 传递链条：①用户在会话 1 运行知舟，不注销切到会话 2（快速用户切换或本地+RDP 同账号）→ ②会话 2 启动：同名互斥体在会话 2 命名空间是另一个对象，CreateMutexW 不返回 ALREADY_EXISTS → 判定可启动 → ③两进程同时打开同一数据目录的同一 SQLite 库——busy_timeout 内互相拖慢，两个 sync 调度器并发上传，远端最后写者胜 + 空耗版本保留额度——正是 46#1 要消灭的后果 → ④revision_conflict/数据库占用类报错间歇出现，用户无从归因。
- 影响范围：需要同账号双交互会话的部署形态；常规单会话桌面不受影响。
- 修复方向：互斥体名加 `Global\` 前缀（跨会话唯一）；或显式 `Local\` 并在 46#1 注释中记录接受该边界。

## 信息

### 106#6 verify 通道断言/打印失败以 panic（退出码 101）交付，违背 50#1 声明的 exit(2) 契约

- 位置：`main.rs:67-72`（`assert!(snapshot["tasks"].is_array() && …)` panic 上穿 → 101；println! 在 stdout 管道关闭时同路径）。50#1 只保证 outcome Err → eprintln + exit(2)。
- 传递链条：①verify 断言失败 → ②panic → 101 → ③CI 按退出码区分时把内部断言崩坏误读为运行崩溃。
- 影响范围：仅 `--verify-native` 无界面验收通道；GUI 用户不可达；CI/脚本按退出码分类时误判失败类别（崩坏 vs 校验不过）。
- 修复方向：断言改 `if !… { eprintln; exit(2) }`，打印改 writeln! 忽略错误。

### 106#7 providers 域 spawn_blocking 内 panic 后 provider_requests 行僵尸 running——域内无 catch_unwind，仅下次启动 recover_chats 翻转

- 位置：`providers/commands.rs:128-143/208-227`（spawn_blocking JoinError 仅映射 task_join_failed，行不落终态）；对照其余 9 域 worker 均有 catch_unwind + task_panicked 落终态。
- 传递链条：①流式请求闭包 panic → ②行停留 running，本会话内 get_provider_chat 永远显示「运行中」→ ③与 102#2（half_open 悬挂）同族的「进程存活但任务丢失」缺口，重启才翻转。
- 影响范围：流式请求 panic 后的本会话；该请求在用量页/任务中心永显「运行中」视图失真，预算计数停留在中途值；重启后 recover_chats 翻 interrupted 自愈。
- 修复方向：stream_chat 闭包内包 catch_unwind，Err 路径落 interrupted/task_panicked 终态。

### 106#8 GUI 装配前的路径解析失败绕过失败恢复 UI——builder.run().expect 无声闪退

- 位置：`main.rs:25-29`（app_data_dir()/app_local_data_dir()? 上抛）、`:382-384`（run(context).expect panic；release 无控制台——用户只见双击后闪退无任何界面）。该窗口在 StartupState 建立之前，失败恢复 UI 覆盖不到。触发面极窄（已知文件夹 API 解析失败）。
- 传递链条：①已知文件夹 API 解析失败（系统策略/注册表损坏等极端环境）→ ②setup 内 `?` 上抛越过 StartupState 建立点，失败恢复 UI 无从接管 → ③builder.run().expect panic，release 为 windows_subsystem 无控制台 → ④用户只见双击后进程闪退，无错误页、无任何界面与诊断信息。
- 影响范围：触发面极窄（路径解析失败的极端环境）；一旦发生即无诊断信息的无声闪退，用户与技术支持均无从入手；常规环境不可达。
- 修复方向：setup 内把路径解析失败也转入 StartupState.failure 走错误页。

### 106#9 pointer 指向「父目录存在、叶子已删」的路径时静默重建空工作区

- 位置：`startup.rs:170`（inspect_location 对 NotFound 返回 Ok）、`:181-188`（create_dir_all 重建）。
- 传递链条：①用户把数据目录移走/误删叶子后启动 → ②不报错不提示，直接原路径建空库呈现空工作区 → ③「目录即真相」语义下可辩护，但与「数据似乎全没了」的用户感受之间无桥接提示。盘符不存在/网络路径场景则正确落错误页。
- 影响范围：手动迁移/误删数据目录叶子后启动的用户；原数据仍在原处未损毁，但应用呈现空工作区且无提示，易被误判为「数据丢失」并可能引发二次误操作（如在空库重建覆盖 pointer）。
- 修复方向：configured 命中但目录缺失时在 overview/通知中给出「目录不存在，已新建空工作区」提示。

## 核实通过项（免后续复查）

- **recover 覆盖完整性**：15 张含 running 态的表全部有翻转者——agent_runs+tool_calls、learning_plans+steps、lectures+units、practice_sets+answers、knowledge_sessions、provider_requests、route_runs+attempts+circuits half_open、project_versions、material_jobs、sync_jobs、focus_sessions（实际时长墙钟计算 min(planned) 封顶）。review/community/plugins/notes/engagement/export 无长任务态；agent_approvals pending 跨重启为设计（97#8 交互收口）。
- **cancelling→cancelled / running→interrupted 语义 12 域一致**（practice/materials 用自身词汇自洽）；恢复顺序正确——recover_chats 先翻 provider_requests 再由 routing/projects 用 completed_chat 回放。
- **启动时序**：setup 先管理 StartupState 再建窗口；guard ensure_ready 以 startup_not_ready 拒绝 + 前端 250ms 轮询；BackendState 在 running 期间 manage 无早访问窗口；failure/running 三态次序无假就绪；initialize_background catch_unwind 兜底。
- **verify/GUI 分叉**：for_verification 先 manage、verify 全程独立凭据服务不碰日常 JWT；窗口清空、错误 eprintln+exit(2)、互斥体按设计跳过且目录隔离。
- **退出/崩溃一致性**：WAL(synchronous=NORMAL)+终态先落盘+下次启动 recover 模型成立；互斥体句柄进程级持有、OS 终止时释放无残留；事件 outbox 与数据同事务，emit 丢失由全量快照兜底（38#2）；重试路径二次 recover 幂等。
- **数据目录决策链**：pointer NotFound→默认、损坏/超 4096/版本不符→storage_config_invalid、读失败→storage_config_unavailable（GUI 回退默认根+configuration_error 走失败恢复 UI，测试覆盖）；半写由 tmp+rename 防住；save_location 先验证后写、失败不动旧配置；自定义目录校验（相对/根/../UNC/系统目录黑名单含 25#18）齐备。
- **多工作区顺序**：SecurityState 惰性建根库（不误触发迁移）；recover 在 with_user(principal) 内对实际登录用户执行；域 worker 经 thread_builder 传播 principal（23#7）；retry 被 pending 守卫拦住。

# 44 · 主线程阻塞专项（第二十轮）

> 审计起点：本轮排查「点击按钮时应用是否卡死/未响应」时，沿 Tauri 2 源码
> （tauri-macros 2.7.4 / tauri 2.12.5 / tauri-runtime-wry 2.12.3 / wry 0.57.1，
> 均为本机 cargo 缓存的实际锁定的版本）逐层验证了命令执行线程模型。
> 结论：**非 async 命令的函数体在主线程执行**（逐跳证据见 44#1），本项目
> 187 个命令中仅 4 个 providers 命令为 async，其余全部同步——其中包括多个
> 一次性重 IO 命令。历轮（第六/七轮）只录入过「重复 IPC/N+1 放大」族并已修复，
> 「一次性重命令阻塞主线程」族从未单独录入。本文件补录该族并给出证据链。

## 执行线程模型（四层证据，版本为 Cargo.lock 实际锁定）

1. **wry 0.57.1**（`src/webview2/mod.rs:1050-1113`）：自定义协议（含 tauri 的
   `ipc://`）经 `add_WebResourceRequested` COM 事件分发，`custom_protocol_handler(...)`
   在事件回调内**直接调用**——WebView2 的该事件在 **UI 主线程**触发；`main_thread_id`
   判断只作用于应答回调，不作用于命令执行。
2. **tauri-runtime-wry 2.12.3**（`src/lib.rs:5114` 起）：把 uri_scheme_protocols
   注册进 wry，未做线程迁移。
3. **tauri 2.12.5**（`src/webview/mod.rs:2005` `on_message`）：收到请求后同步调用
   invoke_handler，无派生。
4. **tauri-macros 2.7.4**（`src/command/wrapper.rs:50` 默认 `ExecutionContext::Blocking`；
   `:116/:159` 仅 `async fn` 签名或 `#[tauri::command(async)]` 才转 Async；
   `:398-428` `body_blocking` 为 `let result = $path(args)` **原地执行**）。
   应用侧 `security/guard.rs:142` `guard_handler` 为纯同步包装（无 spawn）。

即：`#[tauri::command] pub fn ...`（无 async）→ 主线程执行；阻塞期间窗口消息泵
停转。WebView 渲染器是独立进程，页面内 CSS 动画/转圈仍会动——症状是**窗口拖不动/
改不了大小、后续全部 invoke 无响应排队**，超过约 5 秒 Windows 给窗口挂「未响应」。

## P2

### 44#1 备份三命令与 ZIP/批量导入在主线程执行——大数据量时整窗冻结、无进度反馈

- 位置（全部为同步命令，函数体在主线程跑完才返回）：
  - `desktop/src-tauri/src/backend/backup/commands.rs:21`（`export_full_backup`：停调度器 → `archive::export` 全量导出+打包 → 重启调度器）
  - `desktop/src-tauri/src/backend/backup/commands.rs:41`（`preview_full_backup`：`archive::open` + `transfer::dry_run`——**13#19 的预演是完整导入一遍再回滚**，量级等同导入）
  - `desktop/src-tauri/src/backend/backup/commands.rs:49`（`import_full_backup`：停五类任务 → `archive::open` + `transfer::import` 全量导入）
  - `desktop/src-tauri/src/backend/materials/commands.rs`（`import_material_archive`：≤200MB ZIP 预检+逐项解压落盘，决策:150；`import_material_files`：≤32×50MB 逐文件读+校验+哈希+写盘）
- **传递链条**（以导入完整备份为例）：① 设置页「导入完整备份」选择备份文件（BackupPanel.tsx 选定后 invoke）→ ② `import_full_backup` 在主线程执行 `archive::open`（解包整个备份）与 `transfer::import`（整库写入）→ ③ 期间主线程不回消息泵：窗口不能拖动/缩放、点击无反馈（WebView 内动画仍在）、所有后续 invoke（含取消、读取）排队 → ④ 若超过 ~5 秒，Windows 标记窗口「未响应」并可能白化 → ⑤ 命令返回后一切恢复，无数据损害。
- **影响范围**：触发条件=备份/归档体量 × 磁盘速度。ZIP 导入有 200MB 上限（决策:150），SSD 上约 1–3 秒（可感但未挂未响应）；备份导入无体量上限（用户自选文件），大媒体库的备份在慢盘上可达 5–15 秒——恰在「未响应」判定线上。预览（dry_run）与导入同量级，即用户只是「看看里面有什么」也会冻结。历史对照：第六/七轮已把「重复 IPC 放大」族（每事件双份 dashboard、每击键全库 LIKE、每 delta 全量回放）作为 P3 录入并修复，但一次性重命令族从未录入；`import_full_backup` 全程无进度事件（单一 invoke 到终态），前端也无法显示真实进度。
- **修复方向**（供决策，非必须本轮）：把这五个命令改为 `#[tauri::command(async)]`（tauri 会投到线程池执行，UI 不冻结）；注意各命令内部持有 `State<'_>` 的借用需改为 `AppHandle` 获取（异步命令不能借用 State 跨 await，但这些函数体本身是纯同步代码，迁移成本低）；或维持现状并在文档中记录「大备份导入期间窗口短暂无响应为已知边界」。
- **实机验收建议**：造一个 ≥100MB 原件的备份执行导入，观察窗口拖动与任务管理器状态（本仓库规约禁止前台自动化，需人工验收）。

## P3

### 44#2 knowledge::search 全文扫描仍在主线程——大资料库搜索击键期间窗口拖动发涩

- 位置：`desktop/src-tauri/src/backend/knowledge/mod.rs:402-410`（search：笔记+资料全量取回后在内存逐条扫描配对）；消费方为全局搜索（`App.tsx` SearchLayer，120ms 防抖逐击键）与 Wiki 面板检索。
- **传递链条**：① 搜索框击键 → ② 防抖后 invoke `search` → ③ 主线程全量取回全部笔记与资料解析文本（39#1 已消除 1+N 连接，但单次全量加载仍在）→ ④ 逐条内存扫描期间主线程占用 → ⑤ 大库（数十万字文本）单次可达上百毫秒，连续击键时窗口拖动/点击有可感迟滞。
- **影响范围**：资料/笔记总量大的工作区；功能正确、无数据损害。与 44#1 同根（同步命令主线程），单列因为它是**高频交互路径**（每次击键）而非一次性操作。39#1 已把最痛的连接开销消掉，剩余为纯 CPU 扫描。修复方向：同 44#1 的 async 化，或前端把防抖提到 250ms+加最小长度。

## 正向结论（排查过的非问题）

- 生成类长任务（方案生成/Agent/练习/Wiki 问答/同步）全部走后台 job + 事件流（recover 家族），命令只做接受与查询，不在主线程跑长活——这是本应用多数按钮不卡的结构原因。
- providers 域四个真网络命令（upsert/test/stream/route）均为 `#[tauri::command(async)]` 或 `async fn`（providers/commands.rs:21/87/106/183），网络等待不占主线程。
- `read_material_media_chunk`（256KiB/次，media.rs:9）单次读小、频次由前端拉流控制，不构成阻塞点。
- 前端构建产物无阻塞主线程的同步 IPC 循环（38#2 已把事件翻页改为单快照）。

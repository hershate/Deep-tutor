### 102#2 half_open 悬挂无超时逃逸——探测未收尾且应用持续运行期间，该供应商在 routing 模式下一直 `circuit_probing`（重启可恢复）

- 位置：`desktop/src-tauri/src/backend/providers/routing.rs:681-684`（`"half_open"` 分支直接拒绝且不检查任何时间）、`:1079-1099`（permit 拒绝路径仅 save_attempt + continue，不调 record_circuit）、`startup.rs:408-409`（启动时 `routing::recover()` 把 half_open 复位为 open）。
- 传递链条：①routing 请求 A 的 permit 把 open→half_open 并放行探测 → ②A 在收尾前被异常打断（工作线程 panic、进程被杀等无人调 `record_circuit` 的路径）→ ③应用继续运行期间，后续所有 routing 请求命中 half_open 分支被拒（该分支不看时间），被拒路径也不回写 → 状态无人翻转，该供应商持续 `circuit_probing`、无 UI 自救 → ④应用重启时 `recover()` 无条件 half_open→open，opened_at 超过 cooldown 后放行新探测——**重启即恢复**（本条主审修正：探针报告曾称「重启无效」，经核 startup.rs:408 每次启动执行 recover，该说法不成立；实际影响收窄为单会话内悬挂）。99#7 修了「取消」、34#13 修了「本地 Err 回写」，panic/进程存活但任务丢失的窗口仍未覆盖。
- 影响范围：routing 模式 + 探测中断 + 应用不重启的组合；条件较窄但有界性缺失是状态机缺口。
- 修复方向：half_open 分支比较 opened_at（或新增探测发起时间列），超过 cooldown 视为探测过期——回 open 重新判定或放行新探测。

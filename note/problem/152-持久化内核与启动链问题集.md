### 152#1 user1 整库迁移两段 rename 主文件先行——第二次 rename 失败后迁移被跳过，静默丢失仅存 WAL 的提交

- 位置：`desktop/src-tauri/src/backend/store.rs:347-360`（`for suffix in ["", "-wal"]`
  按主文件 → `-wal` 顺序 rename，127#8 设计意图是复制 `-wal` 保住
  checkpoint 与 BEGIN 之间只落 WAL 的提交）；失败收尾 `:363-367`
  （`copy_result` Err 只 `remove_file(&staged)`——主文件已改名，删除落空）；
  跳过判定 `:283`（下次打开按 `!path.exists()` 决定是否重做迁移）。
- 传递链条：①user1 首迁执行，staged 主文件 rename 到
  `users/1/deep-tutor.db` 成功；②第二次 rename（`-wal`）失败——目标被
  占用/杀软锁定/IO 错误，或进程恰在两次 rename 之间崩溃（毫秒级窗口）；
 ③`path` 已存在但缺少 WAL 帧——127#8 要保住的提交不在主文件里；
  ④下次打开（含本次 assemble 失败后的自动 retry）`path.exists()` 为真
  → 迁移整段跳过 → 直接打开丢提交的库，且 `:369-374` 的
  checkpoint(TRUNCATE) 折叠永不执行。附带：残留的
  `*.migration-tmp`/`*.migration-tmp-wal`（`:320-325`）无任何清扫路径
  （`sweep_pointer_tmps` 只管指针 tmp），永久滞留。
- 影响范围：受影响=user1 整库迁移（单用户工作区首迁）失败/崩溃路径上的
  数据完整性；新建库与稳态打开不受影响。损害性质=静默丢提交（数据损失，
  窗口窄但不可逆）。
- 修复方向：先 rename `-wal` 再 rename 主文件（主文件未落位时
  `path.exists()`=false，下次打开自然重做迁移），或改目录级原子切换；
  补 `*.migration-tmp*` 的打开期清扫。

### 152#3 retry_storage_initialization 守卫到 running 置位的竞态窗

- 位置：`startup.rs:579-595`（守卫：running()/failure/pending 检查）在
  async 命令线程执行；`running=true` 在 `:597-601` spawn_blocking 闭包
  内才置位。对照冷启动 `initialize_background`（:406-408）在调用线程

- 传递链条：①错误页/目录面板的「重试」被双击（busy 禁用生效前的窗口）；
  ②两次 retry 调用先后都通过 `!running()` 守卫；③两路 spawn_blocking

- 影响范围：受影响=存储初始化失败后的重试路径（并发双击窗口）；
  不受影响=正常启动与单次重试。损害性质=初始化竞态（后果叠加 152#1
  放大）。需核 UI busy 禁用时序是否足以关窗。
- 修复方向：running 置位提到 spawn_blocking 之前（对齐冷启动写法）。

### 152#4 retry 重解析出的新 root 不回写 StartupState——data_root 陈旧

- 位置：`startup.rs:306-318`（`prepare()` 仅在 State 缺失时注册，不更新
  root）；`:587-588` retry 时重新 `configured_directory` 解析。
- 传递链条：①外部（另一进程/手工）修改指针文件指向新目录；②用户在
  错误页点重试 → retry 以新 root 建库装配成功；③进程内 StartupState
  仍持旧 root——`data_root()`（被导出路径遏制 08#2 与 reveal_path
  白名单使用）与 overview 的 `dataRoot` 指向旧目录直到重启，导出/reveal
  按旧根校验，新根下的导出被误拒或 reveal 失效。
- 影响范围：受影响=「外部改指针 + 进程内 retry」组合下的导出/reveal
  路径校验；不受影响=数据读写本体（BackendState 已是新 root）。
  损害性质=状态分裂（低频：进程内改指针本被 pending 守卫拦截，仅外部
  修改路径可达）。
- 修复方向：retry 成功后回写 StartupState.root。

### 152#5 next_free_id 的 +1ms 基数仍留 1ms 邻接撞号窗

### 152#7 备份导入是「配额与插入同事务」不变式的最大例外 + 长事务

  materials/notes/threads 导入不走 `ensure_quota_in_tx`（全后端 9 个
  配额调用点均同事务，唯备份导入旁路）。
- 传递链条：①GB 级备份导入期间持有写锁（文件复制+行插入同事务）；
  ②并发的用户写命令（保存笔记/任务）在 10s busy_timeout 内等不到锁
  → `database_busy`；③写路径前端弹错误 toast（读路径静默重试）——

  上限（配额行本身随包导入，archive.rs:427-435）。
- 影响范围：受影响=导入期间的并发交互与配额语义（共享/敌意备份可推高
  计数并塞满集合）；不受影响=导入自身的原子性与回滚（IMMEDIATE 事务
  保证）。损害性质=长事务可用性 + 配额旁路——是否属「自恢复/受信包」
  语义需产品定夺。
- 待定夺：文件 IO 移出写锁（两阶段）与配额复检是否引入。

# 86 号：数据层与健壮性问题集（第三十一轮·横切审计）

审计基线：`f0d7e54a`。范围：store.rs 全文、13 个域模块全部 CREATE TABLE/INDEX 逐条读、全部 WHERE/ORDER BY 查询对照索引、backup/maintenance/startup/main 全读。上轮 81#1/81#5 及 75#3、31#43/44、73#12 未重复。共 11 条：P3×2、信息×9。

## P3

### 86#1 provider_requests 永不裁剪 + 用量页全表物化，库龄越长越慢

- 位置：`desktop/src-tauri/src/backend/providers/usage.rs:300-313`（`entries()` 无 LIMIT 全表 SELECT + 4 个 LEFT JOIN + 逐行 JSON 解析，注释自认「provider_requests 是库中最大表」）；`maintenance/mod.rs:843-866`（vacuum 只裁 events 与 provider_route_runs）；`providers/mod.rs:358`（全库唯一 DELETE 出口是 reset）。
- 传递链条：①每次模型请求插入一行 provider_requests；②整理命令裁 events（90 天/2 万条）和 route_runs（1000 条），但最大表无任何保留策略；③每次打开用量页 `overview()` 调 `entries()` 整表载入内存（ledger 最后才 `take(200)`，usage.rs:442）——与 73 号「主线程/重 IO 移后台」修复的动机同源，但数据量本身无界增长。
- 影响范围：用量页延迟与内存随历史线性增长（数万行后单次调用秒级）；备份体积同步膨胀；每次请求的启动延迟叠加 86#2 后持续上升。
- 修复方向：`entries()` 改 SQL 聚合 + `ORDER BY rowid DESC LIMIT`；vacuum 增加 provider_requests 按天/条数裁剪（与 route_runs 同口径）。

### 86#2 每日预算聚合非索引化，每次模型请求前全表扫

- 位置：`desktop/src-tauri/src/backend/providers/usage.rs:465-491`（`date(r.created_at, ?1) = ?2`）；调用点 `usage.rs:502-529` ensure_budget ← `providers/mod.rs:1163`、`routing.rs:945`（每次直连/路由请求前必经）。
- 传递链条：①`date(created_at, 时区偏移)` 把列包进函数；②`provider_requests_created` 索引（providers/mod.rs:347）不可用；③SQLite 全表扫 provider_requests JOIN usage_rates——与 86#1 叠加，每个模型请求的启动延迟随库龄线性上升。
- 影响范围：所有供应商请求的启动延迟；重度使用数月后可感。
- 修复方向：改为可索引的区间比较（`created_at >= 当日本地边界 AND < 次日边界`，边界由 Rust 算好传入），命中 created_at 索引。

## 信息

### 86#3 数据库文件损坏与目录故障共用同一错误文案，无自愈指引

- 位置：`error.rs:29-43`（rusqlite 非 busy 错误一律 `storage_failed`「无法读写本地数据…」）；首次失败点 `store.rs:217-220`。
- 传递链条：①SQLite 文件头损坏/not a database 时 `pragma journal_mode` 读文件头即失败（或目录只读/磁盘满触发同类错误）→ ②`From<rusqlite>` 统一映射为 `storage_failed` → ③startup 进入 failure 态，UI 显示同一句通用文案——用户无法区分「库已损坏，应换目录并导入 .dtbackup」与「目录只读/磁盘满」，可能反复对同目录重试。
- 影响范围：库损坏场景下的自助恢复路径不明确；行为本身正确（startup.rs:608-616 有测试：拒绝打开、可 reset/重试），仅诊断信息缺失。
- 修复方向：`From<rusqlite>` 识别 SQLITE_NOTADB/SQLITE_CORRUPT 映射独立错误码（如 `database_corrupt`），文案指向「新建目录 + 导入全量备份」。

### 86#4 导入坏 .dtbackup 报「无法生成有效的压缩归档」（导出侧文案）

- 位置：`error.rs:57-61`（`From<ZipError>` 统一 export_failed）；触发点 `backup/archive.rs:559/566/595`。
- 传递链条：①用户选择截断/CRC 损坏的 zip → ②`ZipArchive::new` 或 by_name 失败，ZipError 经全局 From 映射为 export_failed → ③弹「无法生成有效的压缩归档」——导出侧的失败文案出现在导入场景。
- 影响范围：整单拒绝无半写（行为正确），但文案与场景相反，误导用户去检查导出流程而非怀疑备份文件本身。
- 修复方向：archive::open 内对 ZipError 自行映射 `invalid_backup`（「备份文件损坏或不是有效的归档」）。

### 86#5 备份导入文件安装先于事务提交，崩溃窗口留孤儿文件

- 位置：`backup/transfer.rs:1461-1465`（install_files 在 tx.commit() 之前）。
- 传递链条：①导入事务内先 `install_files` 把资料原件 hard_link 落盘 → ②随后 `tx.commit()` 提交行数据 → ③若在落盘后、commit 前进程崩溃：WAL 回滚使库内无行，但磁盘文件已存在——错误路径已有 installed 回滚删除（:1468-1472），仅崩溃窗口漏。
- 影响范围：不产生数据不一致（孤儿文件无行引用，运维扫描按孤儿报出可清理）；用户面板可能看到来历不明的文件。自愈机制存在。
- 修复方向：可接受现状；如收口可在 install 前把清单写入待提交行，或「先 commit 后 install + 失败补偿删」。

### 86#6 maintenance 失败路径的事件写入 `?` 覆盖原始错误

- 位置：`maintenance/mod.rs:629-637`（emit_result 的 Err 分支里 `Store::event(...)?`）。
- 传递链条：①整理/清理操作失败（如磁盘满）→ ②emit_result 尝试落 maintenance.failed 事件——同因（磁盘满）大概率也失败 → ③`?` 提前返回新错误，真正的失败原因被吞，调用方收到的是事件写入错误而非整理错误。
- 影响范围：极端条件下的诊断信息丢失；不影响数据与功能正确性。
- 修复方向：失败分支改 `if let Ok(event) = ... { emit }`，保证始终返回原始 error。

### 86#7 跨域引用清理不对称：项目/计划删除后域表行残留

- 位置：对照 `store.rs:681-683`（notes→learning_annotations 同事务清理，正确范本）vs `projects/mod.rs`（kv 项目集合 replace 后 project_versions、learning_plan_adoptions 无清理）、`review/mod.rs`（learning_plans 删除后 review_cards.plan_id 残留）、`reports/mod.rs`（focus_sessions.task_id 同理）。
- 传递链条：①用户删除项目或学习计划 → ②kv 集合 replace 只清主表行，project_versions/adoptions/review_cards/focus_sessions 等域表行保留 → ③视图按 project_id/plan_id 过滤自然隐藏（不可见残留），但行进入备份/导出并占用体积；review_cards 残留卡仍出现在到期复习队列。
- 影响范围：存储体积与备份膨胀；「删除计划后仍收到旧卡片复习」可能是产品有意（卡片为独立用户资产），需产品确认语义。
- 修复方向：确认语义后，在 replace_collection("projects") 事务内比照 notes 的做法补清理；review_cards 至少提供按 plan_id 批量删除入口。

### 86#8 乐观锁 revision 为 i64 递增，溢出仅理论存在

- 位置：`store.rs:402-410`（next_revision）、`:664-670`（守卫比较）。
- 传递链条：①每次同 namespace 写入 next_revision 加 1 → ②需 9.2×10^18 次写入才达 i64 上限 → ③溢出时 release 下 wrap 使守卫比较永久不匹配，该 namespace 写入全拒。
- 影响范围：实际不可达（宇宙年龄级写入量）；仅完备性条目。
- 修复方向：无需处理；如求完备可在 next_revision 达 i64::MAX 时报 typed 错误。

### 86#9 次要索引缺口（小配额表）

- 位置：`agent/mod.rs:463`（sessions ORDER BY updated_at，配额 200 行）、`:1243`（agent_tool_calls WHERE run_id AND status，恢复/取消路径）、`practice/mod.rs:1309`（mistakes ORDER BY last_wrong_at，错题配额间接约束）。
- 传递链条：①agent run 恢复/取消路径按 run_id+status 查 agent_tool_calls → ②该表无 run_id 索引（与已建的 agent_messages_run 不对称）→ ③随会话增长该查询退化为全表扫；另两处位于配额表内，影响可忽略。
- 影响范围：agent 会话较多的库上恢复/取消操作变慢；当前数据量无感。
- 修复方向：顺手补 `agent_tool_calls_run`，其余可不办。

### 86#10 状态/类型列缺 CHECK 约束（安全域除外）

- 位置：全域 schema 60+ 张表的 status/kind 列均为裸 TEXT；对照 `security/mod.rs:394-429`（local_users.role、quotas.item_limit 有 CHECK）。
- 传递链条：①外部篡改或旧版本缺陷写入非法 status（如拼写错误的 'runing'）→ ②schema 无 CHECK 拦截 → ③恢复/收口逻辑按已知值过滤（56#5 只翻 'running'），异常行成为「永无人翻」的悬挂行——74 号期处理过的 running 悬挂即此类实证。
- 影响范围：仅放大外部坏数据的存活期；代码读路径总体宽容。
- 修复方向：新增表的新 status 列带 CHECK；存量表不动（ALTER 代价高收益低）。

### 86#11 单实例互斥体对 ERROR_ACCESS_DENIED 误判可启动

- 位置：`main.rs:82-129`。
- 传递链条：①CreateMutexW 后仅判断 ERROR_ALREADY_EXISTS → ②若同名互斥体存在但 DACL 拒绝当前用户，GetLastError 返回 ERROR_ACCESS_DENIED → ③被误判为「无实例可启动」造成双开（双开对同一 SQLite 数据目录引发锁竞争）。
- 影响范围：极理论（需同名对象+特殊 ACL 的对抗场景）；正常部署防护有效。
- 修复方向：ERROR_ACCESS_DENIED 也视作已有实例。

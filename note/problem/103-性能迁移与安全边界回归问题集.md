### 103#1 94#2 回滚全程无事务——中断恰好落在 DELETE 与重插之间会清空全部供应商档案

- 位置：`desktop/src-tauri/src/backend/providers/sync_config.rs:245-268`（`DELETE FROM provider_profiles` + N 条 INSERT + meta DELETE/INSERT 均在 autocommit 连接上逐条各自提交，未包 `unchecked_transaction`）。

### 103#9 96#2 缺口：迁移复制丢弃 wal_checkpoint(FULL) 的 busy 结果——可拷出缺失最近提交的库

- 位置：`desktop/src-tauri/src/backend/store.rs:193`（`execute_batch("PRAGMA wal_checkpoint(FULL)")` 丢弃 busy/log/checkpointed 结果行）、`:199`（BEGIN IMMEDIATE 只阻塞新写者不驱逐既有读者）、`:207`（只复制主数据库文件，不带 -wal）。
- 传递链条：①user1 首次建工作区时从根库一次性复制 → ②FULL checkpoint 需等齐所有读者；此刻主应用若存在进行中的读事务（报表聚合/备份/流式大读），checkpoint 返回 busy=1，部分**已提交**的 WAL 帧未写回主文件——execute_batch 丢弃结果行无任何报错 → ③随后的 BEGIN IMMEDIATE 无法回置残留 WAL 帧 → ④`fs::copy` 只拷主文件 → user1 工作区库缺失自上次成功 checkpoint 以来的全部提交，且之后 root 与 user1 库静默分叉。同库 maintenance/mod.rs:884-889 已有 `query_row` 读三列结果并区分 busy 的先例，此处未采用。
- 影响范围：一次性迁移窗口内恰有并发活跃读事务 + WAL 存在未回置帧时，user1 工作区静默丢最近提交（96#2 修复的「页级撕裂」主路径本身成立）。
- 修复方向：改 `query_row` 读取 busy 列，busy=1 短暂重试，仍忙则报错拒绝本次迁移（下次打开重试），绝不带着未回置的 WAL 复制主文件。
